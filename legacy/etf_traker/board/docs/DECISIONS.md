## D-001. 수정주가 처리 — **미결**

CLAUDE.md 9장 미확정 1번. 역사적 신고가 판정이 여기 달려 있다.

**아직 검증하지 못했다.** 이 작업 환경은 외부 접속이 막혀 있어 네이버·공공데이터포털에
실호출을 넣을 수 없었다. 대신 두 가지를 해 뒀다.

1. **교차 검증 도구** — `python3 -m board.run --verify-adjust` 가 같은 종목의 같은 구간을
   두 소스에서 받아 겹치는 날짜의 종가를 대조한다. `DATAGO_KEY` 가 있으면 양쪽,
   없으면 네이버 단독 점검만 한다.
2. **미결 상태에서도 틀린 값을 내지 않는 가드** — `engine/newhigh.py` 의 `split_guard`.
   국내 가격제한폭이 ±30% 이므로 하루 사이 종가가 31% 넘게 변한 시계열은 실제 등락이
   아니라 액면분할·무상증자·주식병합이 반영되지 않은 것이다. 그런 종목은
   - 역사적 신고가 판정에서 **제외**하고,
   - 60일·52주 룩백 창을 **이상 지점 이후로 자르며**(자르지 않으면 분할 전 가격이
     최고가로 남아 몇 달간 거짓 음성이 된다),
   - 종목 수를 화면 상단 "빠진 데이터"에 노출한다.

**해야 할 일**: 액면분할 이력이 있는 종목으로 `--verify-adjust` 를 돌리고, 결과에 따라
소스를 고정한 뒤 이 항목을 확정으로 바꾼다. 판단 기준은 `docs/APIS.md` A1 참고.

부작용으로 알고 있을 것: 가드는 신규상장 첫날, 거래재개 첫날, 정리매매처럼 가격제한폭이
적용되지 않는 날도 함께 잡는다. 보수적인 쪽(판정 보류)으로 틀리므로 그대로 둔다.

## D-002. 저장소를 DuckDB 대신 sqlite3 로

CLAUDE.md 3장은 engine 을 "Python, DuckDB" 로 적었고 11장 2번은 "DuckDB 스키마 확정"을
착수 항목으로 뒀다. v0.1 은 **표준 라이브러리 sqlite3** 로 간다.

근거

- DB 가 하는 일이 일봉 캐시와 역사적 최고가 스칼라 보관뿐이다. 집계는 파이썬이 한다.
  분석용 컬럼 스토어의 이점을 쓸 자리가 없다.
- 같은 레포의 `etf_tracker_v9` 가 이미 sqlite + GitHub Actions 캐시로 돌고 있다.
  런타임을 하나로 맞추면 워크플로가 단순해진다.
- 의존성이 `requests` + `PyYAML` 로 끝난다. `etf_tracker_v9` 의 "requests 하나뿐" 방침과 가깝다.

되돌리는 조건

- 종목 수 × 일봉 행이 커져 집계가 수 분대로 늘어나거나,
- state JSON 대신 DB 에 직접 질의하는 분석 화면이 필요해지면.

**단계 간 계약은 바뀌지 않았다.** 각 단계는 여전히 `state/YYYYMMDD/*.json` 으로만
결과를 넘기고, `web/render.py` 는 DB 를 전혀 모른다.

## D-004. 업종·테마 등락률은 지수가 아니라 시가총액 가중 평균

## D-006. 거래량 배수와 20일 평균은 당일을 제외한다

CLAUDE.md 4장의 "당일 거래량 ÷ 20일 평균 거래량"에서 20일에 당일이 포함되는지가
불분명하다. **직전 20영업일(당일 제외)** 로 한다. 당일을 포함하면 급증한 날 분모가
같이 커져 배수가 눌린다.

## D-007. 근접 라벨은 임계 안에 드는 것 중 가장 상위를 고른다

기준 최고가는 역사적 ≥ 52주 ≥ 60일이므로, 역사적 갭이 5% 안이면 52주·60일 갭도
자동으로 5% 안이다. 셋 다 표시하면 표가 늘어나기만 하고 정보가 늘지 않는다.
임계 안에 드는 것 중 **가장 상위 라벨**(역사적 > 52주 > 60일)을 골라 한 줄로 낸다.

## D-008. 역사적 최고가 스칼라는 '당일 포함'과 '직전일까지' 두 값을 함께 들고 있는다

CLAUDE.md 4장은 "종목별 사상 최고가와 기록일을 스칼라로 저장하고 매일 당일 고가와
비교"라고 적었다. 그대로 구현하면 **역사적 신고가가 영원히 뜨지 않는다.** 수집이 당일
봉까지 받아오므로 스칼라 갱신 시점에 이미 당일 고가가 최고가로 들어가고, 그 뒤에
`당일 고가 > 스칼라` 를 물으면 항상 거짓이기 때문이다.

`alltime` 테이블에 `prev_hi` / `prev_cl`(직전 처리일까지의 최고가)을 함께 둔다.
엔진은 기준일이 스칼라의 `last_date` 와 같을 때 `prev_hi` 를 기준값으로 쓴다.
같은 날을 다시 수집해도 값이 흔들리지 않도록 `last_date` 이후 행만 반영한다.

이 결정의 대가: **과거 구간을 뒤늦게 채우는 백필은 이 경로로 안 된다.** 과거를 더
쌓으려면 `--init` 으로 다시 만들어야 한다.

## D-009. 재료 반납은 비율 조건 위에 크기 문턱을 둔다

CLAUDE.md 4장의 정의(`(고가-종가)/(고가-전일종가) >= 0.7`)와 6장 탐지기 3의 조건
(`+ 당일 등락률 3% 미만`)만으로는, 장중에 +0.5% 갔다가 -0.1% 로 끝난 종목까지
전부 '재료 반납' 으로 잡힌다. 하루 수백 건이 되어 리포트가 노이즈로 찬다.

**판정 정의는 그대로 두고**, 이벤트로 승격시킬 최소 반납 폭
(`config/settings.yaml` 의 `giveback.min_pp`, 기본 3.0%p)을 둔다.

리포트에 쓰는 표기도 비율이 아니라 %p 로 한다. 레퍼런스 코멘트가 그렇게 쓴다 —
"고가 대비 종가 괴리 11.2%p" 는 고가 등락률 +12.65% 에서 종가 등락률 +1.45% 를 뺀 값이다.

## D-010. 신고가 창을 20·60·120·252일로 넓힌다

CLAUDE.md 4장이 고정한 것은 60일·52주·역사적 셋이다. 여기에 20일과 120일을 더한다.

근거

- 레퍼런스 코멘트가 쓴다 — "제닉(+7.45%)이 52주·120일·60일·20일 동시 신고가"
- 탐지기 6(`multi_label_high`)이 "20일·60일·252일·역사적 중 3종 이상" 을 요구하는데
  20일이 없으면 3종을 채우려면 사실상 3종 전부여야 했다

고정 정의 셋의 의미는 바뀌지 않았다. 창이 늘었을 뿐이다. 20일 신고가는 하루 수백
종목이라 **계산만 하고 표에는 올리지 않는다** (`newhigh.min_display_kind`).

## D-013. 자격증명은 board/.env 에 두고 커밋하지 않는다

`.gitignore` 가 `*.env` 를 막고 `board/.env.example` 만 커밋된다.
GitHub Actions 에서는 레포 Secrets 를 환경변수로 주입한다. 두 경로 모두
`ingest/creds.py` 로 들어온다. 로그에는 `mask()` 를 거친 값만 찍는다.

이 파일도 `.gitignore` 에 넣는다 (0600).

## D-014. 1층 섹터를 48개 자체 분류(board48)로 넓힌다

CLAUDE.md 5장은 1층을 KRX 업종분류로 두고 "에프앤가이드·WICS 섹터분류는 사용하지

**5장의 금지는 유지한다.** 그 분류를 *받아오지* 않는다는 뜻으로 읽고, 같은 해상도의

("DART 사업의 내용 기반 배치 분류 + 상위 800종목 수동 검수") 그대로다.

- 체계: `knowledge/sectors.yaml` — 사용자 엑셀의 섹터 열에서 그대로 옮긴 48개
- 배정: `classify/sectors.py` — Batch API, haiku, 신뢰도 0.7 미만은 미분류
- 결과: `knowledge/sector_map.yaml` — 사람이 고치고 `locked: true` 를 달면 재분류가
  덮어쓰지 않는다
- KRX 업종은 버리지 않는다. `krx_hint` 로 후보를 좁히는 사전 필터로 쓴다

미분류 종목 수는 `rankings.json` 의 `missing` 과 화면 배너에 그대로 나온다.

## D-017. ETF·ETN 은 유니버스에서 뺀다

2026-08-27 첫 실데이터 실행에서 드러났다. 전 종목 3,924개 중 약 1,200개가
ETF·ETN 이었고, **역사적 신고가 49종목 중 44개가 채권형 ETF** 였다.

```
KODEX CD금리액티브(합성) · TIGER KOFR금리액티브(합성) · SOL 머니마켓액티브
ACE 5월만기자동연장회사채AA-이상액티브 · N2 KIS CD금리투자 ETN …
```

CD금리·KOFR·머니마켓·단기채 ETF 는 이자가 쌓여 구조적으로 매일 우상향한다.
매일 사상 최고가인 게 당연하고, 그건 신고가가 아니라 이자다. 전체 신고가
143행 중 81행(57%)이 이것이었다. 진짜 주식 신고가가 밀려났다.

`ingest/funds.py` 가 두 단계로 거른다.
1. ETF 는 네이버 `etfItemList` 로 **실제 코드 목록**을 받아 거른다 (추측 아님)
2. ETN 은 상품명에 반드시 'ETN' 이 들어가므로 이름으로 거른다

목록을 못 받으면 운용사 브랜드 접두사 + 상품 유형어(액티브·합성·레버리지·인버스)
패턴으로 떨어진다. 놓칠 수 있으므로 걸러낸 수를 리포트에 남긴다.

**근본 해결은 KRX 오픈API 전환이다** (D-011). `stk_bydd_trd` 는 주식만 준다.

## D-018. `--init` 은 상장 이후 전 구간을 받는다

같은 실행에서 **역사적 49 / 52주 56** 으로 거의 같게 나왔다. 정상이라면 역사적이
훨씬 드물어야 한다. 원인은 `--init --years 2` 라 `alltime` 스칼라가 '2년 최고가'
였던 것이다. 라벨이 '상장 이후'라고 적혀 있는데 실제로는 2년이었다.

기본값을 전 구간(1990-01-01~)으로 바꾼다. **HTTP 호출 수는 종목당 1회로 같고**
응답만 커진다. 받은 뒤 `prune()` 으로 최근 420일만 남기므로 DB 도 커지지 않는다.
CLAUDE.md 4장이 예정한 구조 그대로다 — 스칼라로 저장하고 전체 일봉을 매일
재계산하지 않는다.

`--years N` 을 주면 예전처럼 그 구간만 받는다. 급할 때 쓴다.

## D-019. 목록 API 가 안 주는 값은 일봉에서 채운다

같은 실행에서 **전 종목 거래대금이 0** 이었고, 그 결과 유동성 하한에 3,924종목
전량이 걸려 **랭킹 표 네 장이 통째로 비었다.** 네이버 목록 API 의 거래량·거래대금
필드명 추측이 틀린 것이다.

두 가지를 고쳤다.

- 목록 API 가 값을 안 주면 `0` 이 아니라 `None` 을 넣는다. 0 은 '거래 없음'이라는
  사실이고 None 은 '못 받음'이다. 둘을 섞으면 이런 사고가 조용히 지나간다.
- `engine/build.py` 가 `None` 일 때 일봉의 종가x거래량으로 채운다. 체결가 가중이
  아니라 추정치이므로 `turnover_is_estimate` 가 붙는다.

시가총액도 함께 고쳤다. '1e6 을 넘으면 원 단위'라는 추정으로 나누고 있었는데,
그러면 **시가총액 100조가 넘는 종목만 골라서 망가진다.** 실측으로 억원 단위임을
확인했으므로(GS 114,447 = 11.4조) 추정을 걷어냈다.

## D-020. 저항두께는 봉의 범위 겹침으로 센다 (D-005 뒤집음)

D-005 에서 "구간 판정은 종가 기준"으로 정했는데, 2026-08-27 실행에서 근접 종목
대부분이 **'얇음 0.0'** 으로 나왔다. 당연한 결과였다.

기본 기준이 고가라 구간이 `[당일 고가, 기간 최고가]` 인데, 종가는 체계적으로
고가보다 아래라 그 좁은 띠에 거의 들어오지 않는다. **기준과 판정에 서로 다른
가격을 쓴 것이 잘못이었다.**

이제 봉의 `[저가, 고가]` 범위가 구간과 겹치면 그 봉의 거래량을 센다. 기준(고가/종가)과
무관하게 같은 뜻이 되고, 매물대라는 개념과도 맞는다.

하루 안에서 어느 가격에 얼마나 체결됐는지는 일봉으로 알 수 없으므로 봉 전체
거래량을 세는 근사다. **추정치다.** 분봉이나 거래원별 데이터가 있으면 정확해진다.

## D-021. `or 0` 으로 `None` 을 삼키지 않는다

D-019 와 같은 뿌리다. 실데이터에서 터진 뒤 전 코드를 훑어 두 곳을 더 찾았다.

- **재료 반납 탐지기** — `(x.get('chg_pct') or 0) < 3.0`. 등락률을 모르는 종목이
  전부 '3% 미만' 조건을 통과해 재료 반납으로 잡혔다.
- **브레드스** — 등락률을 모르는 종목이 전부 '보합'으로 잡혀 브레드스가 실제보다
  중립으로 보였다. 이제 `unknown` 으로 따로 세고 `total` 에서 뺀다.

`or 0` 이 편해 보이는 자리는 거의 항상 `None` 과 `0` 을 섞는 자리다.

## D-022. 전 구간 적재는 흘려 보낸다 — 모으면 러너가 죽는다

D-018 로 `--init` 을 상장 이후 전 구간으로 바꾸자 바로 따라온 문제다.

```
2,800종목 x 수천 봉 = 약 1,400만 행
  튜플 버퍼   약 5.5 GB
  파싱 dict   약 10.8 GB
  합계        약 16 GB      ← GitHub 러너 메모리 7 GB
```

수집 결과를 전부 모은 뒤 한 번에 넣는 구조라 그대로면 OOM 이다.

두 가지를 고쳤다.

- `http.gather()` 에 `on_result` 콜백을 뒀다. 주면 결과를 **들고 있지 않고**
  넘기고 버린다. 메모리는 종목 하나 크기로 유지된다.
- `sync_px(keep_from=...)` 는 그 날짜 이후 봉만 `px` 에 넣는다. 그 이전 구간은
  스칼라를 만드는 데만 쓰고 저장하지 않는다. `--init` 이 끝난 뒤 따로 잘라낼
  필요도 없어졌다.

덤으로 콜백 예외를 그 항목의 실패로만 처리한다. 예전 구조였다면 마지막 종목
적재에서 터졌을 때 40분짜리 수집이 통째로 날아갔다.

## D-023. 5일 축소폭의 산식을 문서 쪽에서 고친다

CLAUDE.md 4장 표가 자기모순이었다 — 산식은 `5영업일 전 갭 − 현재 갭` 인데
설명은 "음수일수록 빠르게 좁혀짐" 이다. 그 산식대로면 좁혀질 때 **양수**가 된다.

레퍼런스 코멘트(`docs/reference-comment.md`)와 프로토타입 화면이 둘 다
좁혀진 종목을 `-9.8%p` 로 적고 있으므로 **설명이 맞고 산식 표기가 틀렸다.**
코드는 이미 설명 쪽을 따르고 있었다. 표기를 `현재 갭 − 5영업일 전 갭` 으로 고친다.

## D-024. 역사적 라벨의 5일 축소폭은 계산하지 않는다

`hist` 는 룩백 창이 아니라 스칼라라, 5영업일 전 갭을 재려면 그때의 사상최고가가
필요한데 우리는 오늘 값만 갖고 있다. 오늘 값을 쓰면 **그 사이에 최고가가 움직인
만큼이 통째로 축소폭으로 잡힌다.** 3일 전에 신고가를 낸 종목이 "5일 만에 20%p
좁혔다"로 나와 근접 표 맨 위를 먹는다(근접 표는 축소폭 오름차순 정렬이다).

`hist` 의 `narrow5` 는 `None` 으로 둔다. 근접 라벨이 `hist` 인 종목은 정렬에서
뒤로 밀리는데, 그건 계산되지 않은 값을 앞세우는 것보다 낫다.

## D-025. 수정주가 가드가 신고가만 지키고 랭킹은 안 지키고 있었다

이제 셋 다 `floor` 를 받고, 창이 이상 지점을 넘어가야 채워지면 `None` 을 낸다.

## D-026. `--init` 이 역사적 최고가 스칼라를 지우고 다시 만든다

`roll_alltime` 은 이미 본 날짜를 다시 보지 않는다(D-008). 재실행에 견디게 하려던
설계인데, 그 탓에 **D-018 이 기존 DB 에서는 아무 효과가 없었다.** `--years 2` 로
만든 '2년 최고가' 스칼라 위에 전 구간 `--init` 을 다시 돌려도 값이 그대로다.

`init` 은 처음부터 만드는 명령이므로 `alltime` 과 `px` 를 지우고 시작한다.

## D-027. '전일'은 직전 px 행이 아니다

`prev = rows[idx-1]` 은 달력상 전 영업일이 아니라 DB 에 남아 있는 직전 행이다.
거래정지 15일 뒤 재개한 종목의 **15일치 수익률이 '당일 등락률'** 로 나가 섹터
시총가중 평균에 들어갔다. 30% 는 `split_guard_ratio` 0.31 바로 아래라 의심
플래그도 안 붙는다.

두 가지를 고쳤다.
- 소스(목록 API)가 준 등락률을 **먼저** 쓴다. 거래소가 계산한 정확한 전일 대비다.
  예전에는 일봉 파생값을 우선하고 이걸 폴백으로만 썼다 — 맞는 값을 버리고 있었다.
- 소스 값이 없고 직전 봉이 5일 넘게 떨어져 있으면 `None`. 당일 등락률로 쓸 수 없다.

## D-028. 역사적 라벨의 5일 축소폭은 미래를 봤다 → 계산하지 않는다

D-024 로 별도 기록. 근접 표가 축소폭 오름차순 정렬이라 이 허수가 표 맨 위를 먹었다.

## D-029. 탐지기 6의 판정 집합을 사양대로 고정한다

CLAUDE.md 6장은 `{20일, 60일, 252일, 역사적}` 중 3종 이상이다. D-010 으로 120일을
더한 뒤 `hits` 전체를 세고 있어서 **120일 하나만 뚫어도 60일·20일이 따라와 자동으로
3종**이 됐다. 실측에서 이 이벤트 61건이 120일 신고가 종목 수와 정확히 일치했다.
판정 집합을 `MULTI_LABEL_SET` 으로 못박고, 임계값은 `settings.yaml` 로 뺐다.

## D-030. 자격증명은 예외 메시지에서도 지운다

`requests` 의 연결 예외 메시지에는 **요청 URL 이 통째로** 들어 있다. 텔레그램은
토큰을 URL 경로에, DART·공공데이터포털은 인증키를 쿼리에 담으므로, 네트워크 실패
한 번에 자격증명이 Actions 로그와 `run_log` 에 영구히 남았다. D-013 의 마스킹
규칙이 이 경로만 비껴 있었다.

`http.scrub()` 과 `telegram._safe_err()` 가 사유를 만들기 전에 지운다. 파라미터를
못 받은 경로에서도 URL 안의 `key=value` 형태를 잘라낸다.

## D-031. 대시보드를 `docs/` 루트의 정적 사이트로 낸다

"링크 하나로 접속" 요구. `docs/board/index.html` 단일 파일이던 것을 정적 사이트로
바꿨다(`web/site.py`).

- **루트에 놓는다.** `docs/index.html`. `board/` 한 단계를 없앴다. 호스트를 옮겨도
  (Pages ↔ Cloudflare Pages ↔ S3) 도메인만 갈아끼우면 되고, 경로가 안 바뀐다.
  옛 주소 `docs/board/` 는 meta refresh 리다이렉트만 남긴다.
- **보관본은 `d/YYYY-MM-DD.html`.** 어제 화면을 다시 볼 수 있어야 주장 검증이 된다.
- **날짜 목록을 페이지에 박지 않는다.** 헤더 선택기가 `d/index.json` 을 런타임에
  fetch 한다. 박으면 어제 만든 보관본의 선택기가 어제에서 멈춘다.
- **90일치만 남긴다.** 하루 약 200KB. 안 지우면 레포가 계속 커진다.
- **빌드 단계를 두지 않는다.** D-002 와 같은 이유다. 정적 파일을 그대로 올린다.

배포는 `.github/workflows/pages.yml`. 다만 이 레포는 Private 이고, **Pages 는
Private + Free 에서 불가**하며 Pro 를 써도 **사이트 URL 자체는 공개**다(접근 제어는
Enterprise 전용). 진짜 비공개가 필요하면 Cloudflare Pages + Access 를 쓴다.
선택지는 `docs/GITHUB.md` 5장에 정리했다.

## D-032. 로컬 실행을 1급 경로로 만든다

D-031 에서 사이트는 만들었지만 띄울 데가 마땅치 않았다. 이 레포는 Private 이고,
GitHub Pages 는 Pro 가 필요하며 **Pro 를 써도 URL 자체는 공개**다. 종목·수치가
그대로 있는 화면을 그 조건으로 올릴 이유가 없다. 로컬을 곁다리가 아니라 기본 경로로 둔다.

- **`run.py --serve`** (`web/serve.py`). `docs/` 를 로컬 HTTP 로 띄운다.
  `docs/index.html` 을 더블클릭해도 화면은 뜨지만, 날짜 선택기가 `d/index.json` 을
  fetch 하므로 `file://` 에서는 CORS 로 막혀 과거 날짜로 못 넘어간다. 서버가 필요하다.
- **기본 바인딩 `127.0.0.1`.** 기본값이 조용히 `0.0.0.0` 이면 안 된다. 같은 네트워크의
  다른 기기에 열려면 `--host` 로 명시해야 하고, 그때 경고를 찍는다.
- **`Cache-Control: no-store`.** daily 를 다시 돌렸는데 어제 화면이 보이면 안 된다.
- **포트 자동 이동.** 8787 이 물려 있으면 다음 포트로. 흔한 일로 막히지 않게 한다.
- **`local.sh` / `local.ps1`.** venv → 의존성 → `.env` 틀 → 테스트까지 한 번에.
  파이썬 환경 구성이 실제 진입 장벽이라 문서로만 두지 않았다.

**글꼴 CDN 을 비동기로 바꿨다**(`render.py` 의 `FONT_CSS`). 로컬은 오프라인일 수
있는데 `<link rel=stylesheet>` 가 동기라 CDN 이 안 잡히면 첫 페인트가 그만큼 늦었다.
`media="print"` + `onload` 로 걸고 `<noscript>` 폴백을 둔다. 못 받으면 `board.css` 의
대체 글꼴로 떨어질 뿐 화면은 성립한다. favicon 도 인라인 SVG 로 넣어 404 를 없앴다.

## D-033. --init 이 실제로는 아무것도 다시 쌓지 않았다

D-026 에서 "init 은 alltime 을 지우고 다시 쌓는다"고 정해 놓고 **코드에 넣지
않았다.** 문서만 있고 구현이 없었다.

`roll_alltime` 은 같은 날짜를 두 번 넣어도 값이 안 변하도록 `last_date` **이후**
행만 반영한다. 그래서 기존 스칼라(2년치, last_date=어제)가 남아 있으면 1990년부터
전 구간을 내려받아도 전부 걸러진다. **전 종목 전 구간을 받고도 값이 그대로인 채
"완료" 로 끝난다.** 실행 8을 그 상태로 큐에 넣었다가 취소했다.

`init()` 이 `DELETE FROM alltime` · `DELETE FROM px` 를 먼저 하도록 넣었다.
지운 양을 로그에 찍는다 — 조용히 지우면 이번엔 반대 사고가 난다.

검증은 세 겹이다. (1) `roll_alltime` 이 과거 행을 무시한다는 것 자체를 시험으로
못박아 왜 지워야 하는지를 남기고, (2) 비운 뒤에는 1995년 최고가가 들어오는지 보고,
(3) `inspect.getsource(pipeline.init)` 에 삭제문이 실제로 있는지 본다. 같은 사고가
"문서에는 있는데 코드에 없음" 이었으므로 소스를 직접 확인하는 시험을 넣었다.

곁가지로 `--init` 로그가 `최근 None년` 으로 찍히고 있었다. 기본값이 전 구간
(years=None)으로 바뀌었는데 문구가 안 따라갔다.

## D-034. 소스가 보낸 거래대금 0 은 값이 아니라 결측이다

실데이터 첫 보드(2026-08-28)에서 랭킹 표 두 장이 통째로 비었다. 화면의 신고가 표에는
전 종목 거래대금이 `0억` 으로 찍혔다. 등락률과 거래량 배수는 정상이었다.

경로는 이렇다. 네이버 시가총액 목록 API 는 거래대금을 **키에서 빼는 게 아니라 0 을
채워** 보낸다. `turnover = tv/1e8 = 0.0` 이 되고, `_turnover` 의 폴백 조건이
`snap_val is not None` 이라 **0.0 은 통과해 버려** 종가x거래량 폴백이 발동하지 않는다.
전 종목 거래대금 0 → 유동성 하한(1억) 에 2,688종목 전부 탈락 → 표가 빈다.

D-021 에서 이 증상을 한 번 고쳤는데, 그때는 "소스가 키를 안 준다(None)" 로 진단했다.
실제로는 "0 을 준다" 였다. 고친 것이 증상의 절반뿐이었다.

가르는 기준은 거래량이다. **거래량이 있는데 거래대금이 0 인 것은 물리적으로 불가능**
하므로 결측으로 본다. 거래량도 0 이면 0 이 사실이다 — 거래정지 종목을 추정으로 덮으면
안 된다. 수집기(`naver.py`)와 엔진(`build.py`) 양쪽에 넣었다. 수집기만 고치면 다른
소스가 같은 짓을 할 때 또 뚫리고, 엔진만 고치면 universe.json 원본이 거짓말을 한다.

기존 시험 `test_zero_snapshot_is_kept_not_replaced` 가 옛 가정("0 은 거래 없음이라는
사실")을 못박고 있어서 함께 고쳤다. 그 시험의 데이터는 거래량이 100만주였다 — 애초에
성립할 수 없는 조합을 참으로 단정하고 있었다.


## D-035. 거래대금은 소스가 백만원으로 준다 — D-034 의 진단은 틀렸다

D-034 에서 "소스가 0 을 보낸다" 로 진단하고 고쳤는데, **원인이 아니었다.**
값은 0 이 아니라 `0.0011` 이었고 화면 포맷(`{v:,.0f}억`)이 그걸 `0억` 으로 찍었을
뿐이다. 눈에 0 으로 보인다고 0 이라고 단정한 것이 잘못이었다.

실제 원인은 단위다. 네이버 시가총액 목록 API 의 거래대금은 **백만원**이다.

| 종목 | 원본 | 시총(억) | ÷100 (백만원→억) | 회전율 |
|---|---:|---:|---:|---:|
| 실리콘투 | 110,338 | 34,952 | 1,103억 | 3.2% |
| 코스맥스 | 97,859 | 34,389 | 979억 | 2.8% |
| 아모레퍼시픽 | 67,114 | 88,090 | 671억 | 0.8% |

원 단위로 보고 `1e8` 로 나누면 3.5조 기업의 하루 거래대금이 11만원이 된다.
`÷100` 이면 대형주 회전율이 0.6~3.2% 로 앞뒤가 맞는다. KIS 도 수급을 백만원으로
주므로(`v / 100.0`) 국내 소스의 공통 관례로 보인다.

**왜 아무 데서도 안 걸렸나.** 값이 `None` 도 `0` 도 아닌 '그럴듯하게 작은 수' 였다.
필드 하나만 보는 검사로는 잡을 수 없다. 시총과의 관계로 봐야 한다 — 시총 1조가
넘는 기업이 하루 1억도 거래되지 않는 것은 물리적으로 불가능하다. `unit_sanity()` 를
넣어 대형주 거래대금 중앙값이 1억 미만이면 리포트 상단에 사유를 올린다. 표본이
20종목 미만이면 판단하지 않고, 중앙값을 써서 거래정지 몇 종목에 흔들리지 않는다.

D-034 의 0 판정 가드는 남긴다. 원인은 아니었지만 다른 소스가 0 을 채워 보낼 때를
막는 방어로는 유효하다. 다만 그것이 이번 사고의 원인이었다고 적었던 부분은 틀렸다.

## D-036. 구성종목이 적은 섹터는 순위표에서 뺀다

실데이터 보드에서 `컴퓨터`(3종목)가 금일 섹터 상승률 1위로 올라왔다. 상승 2 /
하락 1 이었고, 사실상 한 종목이 순위를 만들었다. 48종목짜리 `식품,음료` 와 같은
표에 놓으면 "오늘 컴퓨터 섹터가 가장 강했다" 로 읽힌다.

`rankings.min_sector_members` (기본 5) 미만은 순위에서 빼되, **지우지 않고**
'빠진 데이터'에 이름과 종목수로 남긴다. 몇 개가 왜 빠졌는지 안 보이면 그게 또
다른 종류의 거짓말이다. `미분류` 버킷은 섹터가 아니라 잔여 묶음이므로 수가 적어도
남긴다 — 몇 종목이 분류 밖에 있는지가 정보다.

설정 한 줄로 끌 수 있다(`min_sector_members: 1`).

곁가지로 '섹터 미배정' 안내 문구가 분류를 이미 돌린 뒤에도 "`--classify` 로
배정하세요" 라고 말하고 있었다. 목표 분류와 실제 분류가 같으면(=이미 돌렸으면)
원인은 신뢰도 미달이므로, `sector_map.yaml` 을 손보라고 안내를 바꾼다.

## D-037. 자동 보충한 파라미터가 만든 0 은 사실이 아니다

D-032 에서 KIS 의 `INPUT FIELD NOT FOUND [X]` 를 읽어 X 를 빈 값으로 채워 다시
부르게 했다. 점검은 PASS 로 바뀌었지만 **값이 전부 0 이었다.** 화면 헤더에
`기관계 +0억원 · 외국인 +0억원 · 개인 +0억원` 이 사실처럼 찍혔다.

빈 값으로 채운 필수 파라미터는 질의를 성립시키지 못한다. API 는 200 을 돌려주되
0 만 채워 보낸다. **호출이 성공했다는 것과 질의가 성립했다는 것은 다르다.**
실패보다 나쁘다 — 실패는 "빠진 데이터"에 남지만 0 은 수치로 남는다.

어느 영업일이든 개인·외국인·기관 순매수가 셋 다 정확히 0 일 수는 없다. 셋은
서로를 상쇄해 합이 0 에 가까울 뿐 각각은 수천억이다. 최신일 세 값이 모두 0 이면
`Fetch` 로 올리고, 자동 보충한 파라미터 이름을 사유에 함께 적는다. 그러면 화면은
'투자자별 수급 소스 미확보' 로 정직하게 빈다 (CLAUDE.md 2장 1번·6번).

자동 보충은 **필드 이름을 알아내는 진단 장치**로만 쓴다. 알아낸 이름에 올바른 값을
넣는 것은 별개의 일이고, 그 값은 KIS 문서나 실측으로 확정해야 한다.
`FID_INPUT_ISCD_2` 의 올바른 값은 아직 모른다 — 미확정으로 남긴다.

## D-038. KIS 시장 수급 파라미터 — 후보 5개를 실측했고 전부 아니었다

D-037 이후 값을 실측으로 좁히려 다섯 조합을 실제로 눌러 봤다(run 19, 2026-08-29).
**결과가 두 갈래로 갈리는데 둘 다 틀렸다.**

매매 상위는 정상 동작한다** — 시장 전체 합계만 빠진 것이다. 종목별 값을 더해
시장 합계를 만들지는 않는다. 조회한 종목만 더한 값은 시장 전체가 아니다.

## D-039. 파일이 있다는 것과 내용이 맞다는 것은 다르다

PR #2 를 머지하고 `main` 에서 `daily` 를 돌렸더니 **고치기 전과 같은 화면**이 나왔다.
역사적 신고가 43(브랜치에선 5), 거래대금 전 종목 `0억`, 등락률이 음수인데 신고가.

코드는 분명히 고쳐져 있었다(`origin/main` 에서 `MWON_PER_EOK` 와
`DELETE FROM alltime` 을 직접 확인했다). 문제는 **데이터**였다.

워크플로가 이랬다.

```
restore-keys: board-db-                     # main 의 옛 캐시가 복원된다
if [ ! -f board/board.db ]; then --init     # 파일이 있으니 건너뛴다
```

Actions 캐시는 브랜치 단위라 브랜치에서 만든 새 DB 는 `main` 이 못 본다. 대신
`main` 이 예전에 남긴 **옛 코드로 만든 DB** 가 복원됐고, 파일이 존재하니 `init` 을
건너뛰었다. 고쳐진 코드가 옛 규약의 값 위에서 돈 것이다. alltime 은 2년 최고가
그대로, snapshot 은 옛 단위 그대로.

**"파일이 있느냐"는 정합성의 근거가 못 된다.** DB 에 어떤 규약으로 만들었는지를
새긴다.

- `meta` 테이블에 `data_version` 을 두고 `init` 이 새긴다
- `stale_reason()` 이 코드의 `DATA_VERSION` 과 대조한다. 값이 없으면(옛 DB)
  역시 stale 이다 — 이번 사고의 DB 가 정확히 그 경우다
- `cmd_daily` 가 stale 이면 사유를 찍고 **스스로 다시 쌓는다.** 로컬에서도 같은
  일이 생기므로 워크플로가 아니라 코드에 넣었다
- 캐시 키에도 버전을 넣어 애초에 옛 DB 가 복원되지 않게 한다. 숫자를 워크플로에
  박지 않고 `pipeline.DATA_VERSION` 을 읽는다 — 단일 출처

빈 DB 는 stale 이 아니다. 아직 안 쌓은 것과 잘못 쌓은 것은 구분해야 한다.

**수집 단위나 스칼라 의미를 바꾸면 `DATA_VERSION` 을 올린다.** 안 올리면 이 사고가
그대로 재현된다.


## D-040. 재적재는 별도 프로세스로 돌린다

D-039 로 "stale 이면 스스로 다시 쌓는다"를 넣고 브랜치에서 먼저 돌려 봤다.
**11분 뒤 트레이스백 없이 죽었다.** 산출물은 4개(정상 19개), `결과 커밋` 단계는
건너뛰어졌다.

11분은 전 종목 전 구간 적재에 걸리는 시간 그대로다. 즉 재적재는 **끝까지 돌았고**
그 다음에 죽었다. 트레이스백이 없다는 것이 단서다 — 파이썬 예외였다면 스택이
찍힌다. 조용한 죽음은 프로세스가 밖에서 종료됐다는 뜻이고, 이 프로젝트에는
`sync_px` 로 러너 메모리를 넘긴 전력이 있다.

원인은 내가 만든 것이다. `cmd_daily` 가 같은 프로세스에서 `init()` 을 부르고 이어
`daily()` 를 불렀다. 적재만 하는 실행도, 수집만 하는 실행도 각각은 통과했지만
둘을 한 프로세스에 넣으면 한도를 넘는다.

`subprocess` 로 나눈다. 적재가 끝나면서 그 프로세스의 메모리가 통째로 반환되고,
커넥션 상태가 섞이는 문제도 같이 사라진다. 원인이 둘 중 무엇이든 막힌다.

**재적재가 실패하면 거기서 멈춘다.** 깨진 DB 위에서 보드를 만들면 틀린 수치가
사실처럼 나간다 — 이번 사고 전체가 그 형태였다(D-035, D-037, D-039).

교훈은 절차 쪽이다. 이 실패는 **머지 전에 브랜치에서 돌려 봤기 때문에** 잡혔다.
D-039 를 그대로 머지했으면 `main` 의 예약 실행이 매일 11분을 쓰고 죽었을 것이다.


## D-041. 스냅샷 날짜는 실행한 날이 아니라 장 세션 날짜다

D-040 을 넣고 다시 돌렸더니 이번엔 2분 만에, 이번에는 **트레이스백을 남기고** 죽었다.

```
RuntimeError: 기준일 2026-08-28 이하의 종목 스냅샷이 없다
```

토요일(2026-08-29)에 새로 적재한 결과다. 네이버가 토요일에 돌려주는 값은 **금요일
종가**인데, 수집기는 스냅을 **실행한 달력 날짜**인 토요일로 찍는다. 기준일은 일봉의
마지막 날짜라 금요일이고, `DB.snapshot()` 은 기준일 **이하**를 찾으므로 토요일 스냅을
못 본다.

거래일 장 마감 뒤에 돌리면 두 날짜가 같아서 여태 드러나지 않았다. 휴장일에 **새로
적재**할 때만 나온다 — 기존 DB 에는 직전 거래일 스냅이 남아 있어 '이하' 규칙이
그걸 골라 줬기 때문이다.

`align_snapshot()` 이 적재 뒤 스냅 날짜를 일봉의 마지막 날짜로 맞춘다.

**단, 그 세션의 스냅이 이미 있으면 건드리지 않는다.** 장 마감 전 평일에 돌리면
일봉의 마지막 날짜가 어제인데, 오늘 장중 값을 어제 종가 위에 덮어쓰면 전일 종가가
오염된다. 그 경우는 '이하' 규칙이 알아서 어제 스냅을 고른다.

스냅 날짜의 의미가 바뀌었으므로 `DATA_VERSION` 을 3 으로 올린다. 휴장일에 적재된
v2 DB 는 이 상태 그대로라 그냥 두면 못 쓴다.

이번에도 **머지 전 브랜치 실행**이 잡았다. D-039·D-040·D-041 셋 다 같은 방식으로
드러났고, 세 번 모두 `main` 에 그대로 갔으면 예약 실행이 매일 죽었을 것이다.

## D-042. 링크는 아티팩트로 낸다 — 정적 호스팅은 선택지로 남긴다

"깃허브 실행으로 나오면 안 되고 대시보드로." 요구는 **주소 하나를 누르면 그날
보드가 뜨는 것**이다. Actions 탭, Artifacts zip, 로컬 서버는 전부 그게 아니다.

정적 사이트(`docs/`)는 이미 완성돼 있는데 **올릴 곳이 없다.** 레포가 Private 이라
GitHub Pages 는 Free 플랜에서 아예 안 되고, Pro($4/월)를 결제해도 **사이트는
공개**다(접근 제어는 Enterprise 전용). Cloudflare Pages + Access 는 무료로 진짜
비공개가 되지만 계정 연결·정책 설정이 사용자 손을 탄다. 셋 다 "지금 링크를 준다"가
안 된다.

Claude 아티팩트는 된다. 주소가 고정이고, 기본이 비공개이고, 요금제도 배포 설정도
없다. 그래서 **아티팩트를 기본 경로로 삼는다.**

갱신은 두 단계로 나눴다. 만드는 쪽은 GitHub Actions(`board.yml`, 평일 16:10 KST),
올리는 쪽은 루틴(평일 17:00 KST)이 레포의 `docs/artifact.html` 을 같은 주소에
다시 올린다. Actions 에서 직접 아티팩트를 게시할 방법이 없어서다.

### 왜 변환기가 필요한가

`docs/index.html` 을 그대로 올리면 안 된다. 두 가지가 조용히 깨진다.

1. 아티팩트가 올린 파일을 자기 껍데기(`<!doctype>…<head>…</head><body>`) 안에
   넣는다. 완성 문서를 넣으면 문서가 문서를 감싸고 `<head>` 내용이 본문으로 샌다.
2. CSP 상 `fonts.googleapis.com` 외의 스타일시트는 **에러 없이** 막힌다. jsdelivr
   에서 받던 Pretendard 가 사라지고 한글이 시스템 기본 글꼴로 떨어진다. 화면을
   보기 전에는 모른다.

`web/artifact.py` 가 껍데기 태그를 벗기고, 막히는 링크를 빼고, Pretendard 자리를
구글 폰트의 `IBM Plex Sans KR` 로 바꾼다(이미 쓰는 IBM Plex Mono 와 같은 집안이다).
상대 경로가 필요해 아티팩트에서 동작하지 않는 날짜 선택기와 엑셀 링크도 뗀다 —
눌리는 척하는 컨트롤을 남기지 않는다.

`site.publish()` 안에서 매번 함께 만들어진다. 사람이 기억해야 하는 단계가 하나
늘면 언젠가 빠진다.

### 곁다리로 드러난 것

살아 있던 아티팩트에는 한글 대체 글꼴(`Apple SD Gothic Neo`·`맑은 고딕`)이 있는데
`board/web/board.css` 에는 없었다. 지난번 손으로 조각을 고쳐 올리면서 원본에 되돌려
놓지 않은 것이다. 손으로 만든 산출물은 이렇게 조용히 갈라진다. 이번에 원본으로
병합했고, 앞으로는 변환기만 고치면 된다.

정적 사이트를 버리지는 않는다. 지난 90일 날짜 선택기와 랭킹 엑셀은 사이트에만
있고, 나중에 Cloudflare 나 Pages 로 옮길 때 그대로 쓴다(`GITHUB.md` 5장).

### 루틴을 새 세션으로 띄우면 안 된다 — 레포가 없다

처음엔 매 실행마다 새 세션을 띄우게(`create_new_session_on_fire`) 만들었다.
예행으로 두 번 돌려 봤더니 첫 번째는 결과를 확인할 길이 없었고, 두 번째는
상태가 `REQUIRES_ACTION` 이었다. 붙잡혀 있던 것은 이것이다.

```
git clone git@github.com:<owner>/ETF-Traker.git ~/ETF-Traker
```

**그 세션에는 레포가 없다.** 스스로 받으려다 권한 프롬프트에 걸렸고, 아무도 안
보는 자동 실행이라 거기서 멈췄다. 실패로 찍히지도 않는다 — 매일 조용히 아무 일도
안 일어났을 것이다. 예행을 안 돌렸으면 링크가 8월 28일에 굳어 있는 걸 며칠 뒤에나
알았다.

루틴을 이 작업 대화에 묶었다(`persistent_session_id`). 그 대화에는 레포가 이미
있고 아티팩트 게시 이력도 있어서, 새 세션이면 반드시 거쳐야 하는 "처음 보는
아티팩트라 첫 publish 는 거부" 단계까지 통째로 없어진다.

**자동화는 한 번 돌려 보기 전까지 돌아간다고 말하지 않는다.** D-039·D-040·D-041 이
전부 같은 교훈이었고 이번 것도 같다.

## D-043. 신고가 줄마다 종가 기준 결과를 함께 적는다

"금요일 기준 GS 랑 혜인만 있는데 뭔소리야." 우리 보드는 같은 날 코스맥스·한국콜마를
역사적 신고가로 올렸다. 둘 다 맞다 — **기준이 다르다.**

CLAUDE.md 4장은 고가·종가 둘 다 계산하고 리포트 기본값은 **고가 기준**이라고
정해 뒀다. 당일 장중 고가가 기준 최고가를 넘으면 신고가다. 그런데 증권사 스크리너
상당수는 **종가 기준**이다. 장중에 뚫고 밀려서 마감한 종목은 저쪽 목록에 없고
우리 목록에는 있다. 화면에는 "고가 기준"이라고 한 줄 적혀 있었을 뿐이라, 어느
종목이 그 차이 때문에 올라온 건지 볼 수가 없었다.

판정은 바꾸지 않는다. 대신 달성 표의 각 줄에 종가 기준 결과를 붙인다.

- 종가로도 같은 라벨이면 아무것도 안 붙는다 (대부분이 여기다)
- 종가로는 더 낮은 라벨까지면 `종가 52주` 처럼 그 라벨을 적는다
- 종가로 기준 최고가를 못 넘었으면 `종가 미달`

표 머리말에도 "67종목 중 45종목" 처럼 합계를 적는다. 이 숫자만 보면 두 기준이
얼마나 갈라졌는지 한눈에 나온다.

데이터는 이미 있었다. `build.py` 가 줄마다 `close_basis` 를 넣고 있었고 화면만
안 쓰고 있었다. 계산이 아니라 표시 문제였다.

### 곁다리 — 머리말 문구가 거짓말을 하고 있었다

`'장중 고가' if basis == 'high' else '종가'`. "장중 고가 기준"은 **데이터가
장중 값**이라는 뜻으로 읽힌다. 실제로는 확정 종가 데이터를 받아 당일 고가로
판정하는 것이다. 용어집에 있는 이름은 그냥 "고가 기준"이다. 문구를 고쳤다.

(재료 반납 설명의 "장중 고가 +2.07% 까지 갔다가 종가 −1.2%" 는 원래 맞는
표현이라 그대로 둔다.)

## D-044. 섹터 뉴스를 붙인다 — 클러스터링 없이 테마 질의로 먼저

'섹터 뉴스' 탭이 "미구현" 한 장으로 비어 있었다. 가격과 거래량은 **무엇이**
일어났는지만 말한다. 왜인지는 재료에 있고, 레퍼런스 코멘트의 문장 대부분이
거기 걸려 있다 — "웨스팅하우스 지분 공동인수설로 시작된 자금 유입", "리아노보스티의
휴전 합의 보도가 트리거".

`ingest/news.py` 에 검색 함수는 이미 있었고(실호출 통과 2026-08-28) 수집 단계만
없었다. `collect()` 를 붙였다. `sectors.json` · `universe.json` 을 읽어
`news.json` 을 쓴다 — CLAUDE.md 3장 계약 그대로다.

### 어느 테마에 붙이나

오늘 실제로 움직인 것만. 신고가가 있거나 등락률 절대값이 문턱(기본 2%) 이상인
테마를 점수순으로 상위 8개. 점수는 `신고가 수 × 10 + |등락률|` 이다.

거래대금 배수를 점수에 안 넣은 이유: 배수는 시총이 작을수록 쉽게 튀어서 아무도
안 보는 소형 테마가 상위를 채운다.

### 검색어

테마명 하나 + 대표 종목명 셋. 종목명을 섞어야 테마명으로는 안 걸리는 개별 재료가
잡힌다. 종목은 **거래대금** 상위로 고른다 — 등락률로 고르면 시총 30억짜리 상한가가
뽑히고, 그 이름으로 검색해 봐야 그날 시장이 반응한 재료는 안 나온다.

### 세 가지 결과를 구분해 적는다

| 상태 | 화면 |
|---|---|
| 기사를 받았다 | 제목·매체·요약·링크 |
| 검색은 됐는데 그날 기사가 없다 | "2026-08-28 자 기사를 찾지 못했습니다 (검색어 …)" |
| 검색이 실패했다 | 상단 '빠진 데이터' 에 테마명과 사유 |

둘째와 셋째를 같게 그리면 화면이 **"오늘 재료가 없었다"는 사실 주장**을 하게 된다
(CLAUDE.md 2장 6번). 자격증명이 없을 때도 마찬가지로 사유를 적는다.

### 아직 아닌 것

7장의 뉴스 클러스터링·테마 매칭(Haiku Batch)은 안 붙였다. 지금은 "이 테마를
검색해서 나온 기사"를 그 테마에 매다는 결정론적 방식이다. 그래서 탐지기 2
(opposite_reaction — 같은 뉴스 클러스터에 걸린 두 테마의 부호가 반대)는 여전히
못 돈다. 클러스터가 없기 때문이다. 9장 미확정 3번을 그 내용으로 고쳐 뒀다.

먼저 붙인 이유는 단순하다. 클러스터링이 없어도 "왜 올랐나"의 8할은 링크 하나로
해결되고, 클러스터링은 그 위에 얹으면 된다.

### 저작권

제목·요약(description)·링크·매체명만 저장한다. 원문은 긁지 않는다. 서술에 인용할
때 매체명과 링크를 함께 남긴다.

## D-045. 신고가 목록은 두 기준의 합집합이어야 한다

D-043 에서 줄마다 종가 기준 결과를 적었더니 다음 질문이 바로 나온다 — "그럼
종가 기준 목록만 보고 싶다". 화면에 토글을 달았다.

거기서 함정이 하나 있었다. 고가 기준으로 만든 목록을 화면에서 종가 라벨로 다시
거르면 될 것 같지만 **안 된다.** 종가 기준의 참조 최고가(과거 종가들의 최고)는
고가 기준의 참조 최고가(과거 고가들의 최고)보다 **낮다.** 그래서 종가로는 뚫고
고가로는 못 뚫는 날이 나온다. 합성 데이터 310종목에서 실제로 2종목이 그랬다.
고가 목록을 거르는 방식이면 그 2종목은 화면에서 조용히 사라진다.

`achieved_rows()` 가 **두 기준 중 하나라도** 표시 등급에 드는 종목을 담는다.
필터는 화면이 하고 데이터는 둘 다 갖는다.

정렬은 고가 라벨 등급 우선, 고가 라벨이 없으면 종가 라벨 등급으로 줄 세운다.

### 라벨은 서버가 그린다

토글은 **보이기만** 바꾼다. 두 기준의 라벨을 서버가 미리 그려 두고 자바스크립트는
어느 쪽을 보일지만 고른다. 브라우저에서 라벨을 만들어 내면 화면과 `newhigh.json`
이 갈라질 자리가 생긴다.

알약의 종목수도 두 기준을 함께 싣고(`counts` · `counts_close`) 토글이 바꾼다.
수를 하나만 실으면 기준을 바꿨을 때 알약과 표의 행수가 어긋난다.

머리말의 "고가 기준" 표기도 함께 바뀐다. 표는 종가인데 위에는 고가라고 적혀
있으면 그 화면 전체를 못 믿게 된다.

### 실측으로 잡은 것

처음 구현에서 종가 모드의 행수(65)가 종가 카운트(62)보다 많았다. 원인은
`min_display_kind`(60일) 아래인 20일 라벨이었다 — 20일 알약이 없으니 필터에
걸리지 않고, 알약이 없으니 끌 수도 없다. 알약에 없는 등급은 표에서도 뺀다.

## D-046. themes.yaml 의 비상장 시드에 사유를 적는다

"themes.yaml 시드 35건이 상장 종목 마스터에 없습니다 (비상장·사명변경 추정)"
가 매일 리포트 상단에 떠 있었다. 그중 다섯은 **영원히 안 붙는다** — 세메스·
삼성디스플레이·SK온·토스뱅크는 비상장이고 앰코는 국내 미상장이다.

지우면 안 된다. 이들은 밸류체인의 실제 구성원이고, 세메스 없는 반도체 전공정
시드는 그 자체로 틀린 기록이다. 그대로 두면 매일 결손으로 세어져 **진짜 오타나
사명 변경이 그 숫자에 묻힌다.**

`themes.yaml` 에 `unlisted:` 를 두고 이름마다 사유를 적는다. 화면은 사유가 적힌
것과 안 적힌 것을 나눠 세고, **사유 없는 것만** 이름까지 붙여 노출한다. 그 줄을
보고 사람이 이 표에 추가하거나 seeds 를 고친다.

시험이 두 가지를 못박는다. 사유 없는 면제는 그냥 은폐이므로 사유가 비면 실패하고,
seeds 에 없는 이름을 면제 목록에만 남기면(다음 사람이 어디 쓰이는지 찾다 시간을
버린다) 역시 실패한다.

나머지 30건은 실데이터의 목록을 봐야 판단할 수 있다. 다음 실행의 '빠진 데이터'
줄에 이름이 찍힌다.

## D-047. 푸시 거부를 삼키면 잡은 초록색인데 보드가 사라진다

`main` 머지 뒤 첫 실행(run 26)은 제대로 돌았다. 스테일을 감지해 다시 쌓고,
2026-08-31 보드를 만들고, `docs/d/2026-08-31.html` 과 랭킹 엑셀까지 커밋했다.
그리고 푸시에서 거부됐다.

```
! [rejected]  HEAD -> main (fetch first)
```

실행 중에 다른 푸시가 들어왔다. `git push ... || true` 가 그걸 삼켰고 잡은
성공으로 끝났다. **보드만 없어졌다.**

이 레포에서 같은 형태가 세 번째다.

| | 삼킨 것 | 증상 |
|---|---|---|
| D-036 | `git add` 의 pathspec 오류 | 성공했는데 아무것도 안 올라감 |
| D-039 | 캐시 DB 의 규약 불일치 | 고쳐진 코드가 옛 값 위에서 돎 |
| D-047 | 푸시 거부 | 보드를 만들어 놓고 사라짐 |

원격 위로 다시 얹어 세 번까지 재시도한다. 충돌은 `docs/` 생성물뿐이고 방금 만든
쪽이 최신이므로 `-X theirs` 로 잡는다(리베이스에서는 얹는 쪽이 우리 커밋이다).
세 번 다 실패하면 `::error::` 를 찍고 잡을 빨갛게 만든다. 그 실행의 보드는
산출물에만 남는다는 사실도 함께 적는다.

**거부를 삼키면 실패보다 나쁘다.** 실패는 눈에 띄지만 이건 안 띈다.

## D-048. daily 가 매일 48섹터 배정을 지우고 있었다

보드 상단에 매일 이 줄이 있었다.

> 섹터 미배정 916종목 — 목표 분류는 board48 인데 실제로 붙어 있는 분류는
> naver_upjong 입니다. `python3 -m board.run --classify` 로 배정하세요

분류를 안 돌려서인 줄 읽힌다. **돌렸다.** `knowledge/sector_map.yaml` 에 2,800종목
배정이 576KB 로 들어 있고 레포에 커밋돼 있다. 그런데 `sync_sectors()` 가 매
daily 마다 네이버 업종 14개를 이렇게 밀어 넣는다.

```python
conn.executemany('INSERT OR REPLACE INTO sector_map VALUES(?,?,?,?)', buf)
```

`code` 가 PK 라 REPLACE 가 board48 행을 통째로 덮는다. 분류를 돌린 그날은 48섹터가
붙고, 다음 daily 가 지운다. 그리고 화면은 "분류를 돌리세요" 라고 말한다. 시키는
대로 다시 돌려도 다음 날 같은 자리로 돌아온다.

CLAUDE.md 5장이 정해 둔 것은 반대다 — **1층 분류는 자체 48섹터**이고, KRX·네이버
업종은 버리지 않되 배치 분류의 후보를 좁히는 사전 필터(`krx_hint`)로 쓴다.
14개로는 랭킹 표 해상도가 안 나온다(비철금속과 철강이 둘 다 '철강금속'이다).

`ON CONFLICT(code) DO UPDATE ... WHERE sector_map.taxonomy IS NOT 'board48'` 로
바꿨다. 배정이 없는 종목(신규 상장 포함)에는 그대로 채운다 — 그게 없으면
`--classify` 가 후보를 좁힐 힌트도 없어진다.

그리고 **줄어들면 예외를 던진다.** board48 행 수를 앞뒤로 세어 줄었으면
`RuntimeError` 다. 조용히 넘기면 다음 보드가 성긴 분류로 나가고, 화면은 또
"분류를 돌리세요" 라고 말한다.

재적용은 공짜다. `classify/sectors.run()` 이 `sector_map.yaml` 에 이미 있는 코드는
묻지 않으므로, `--classify` 를 한 번 더 돌리면 API 호출 없이 DB 에만 다시 쓴다.

## D-049. 투자자별 매매동향 — 빈 조회일과 밀린 열

D-047 의 `shape()` 진단이 한 줄로 답을 줬다.

```
1,682자 · tr 4개 · th ['날짜','개인','외국인','기관계','기관','기타법인'] · 첫칸 ['1']
```

두 가지가 한꺼번에 드러났다.

### ① 값 행이 아예 없다

1,682자에 `tr` 4개, 그리고 `<td>` 의 첫 칸으로 잡힌 것은 페이지 번호 `'1'` 하나뿐이다.
**머리글은 왔는데 값 행이 없다.** 지금 요청은 `bizdate=''` 로 부르고 있었다.
'일별' 조회에 조회일이 비어 있으니 질의가 성립하지 않는다.

올바른 값을 문서 없이 맞히지 않는다. 후보를 순서대로 눌러 보고 **실제로 값이
오는 것**을 쓰며, 어느 것이 통했는지 `params` 에 남긴다(KIS 파라미터를 좁힐 때
쓴 D-038 과 같은 방식). 지금 쓰던 `bizdate=''` 는 마지막에 둬서, 그게 왜 안
되는지가 로그에 남게 했다.

### ② 열이 한 칸 밀 뻔했다 — 이쪽이 더 위험하다

머리글에 `기관계` 와 **`기관`** 이 둘 다 있다. 네이버 표는 머리글이 두 줄이고
'기관' 이 하위 구분(금융투자·보험·투신…) 위에 `colspan` 으로 걸려 있다.

옛 `_header_cols` 는 **아는 이름만 모아 압축한** 목록을 돌려줬다. 그러면 모르는
열이 하나 끼는 순간 그 뒤가 전부 한 칸씩 밀린다 — `zip(cols, vals)` 가 위치로
짝을 맞추기 때문이다.

| 표 | 날짜 | 개인 | 외국인 | 기관계 | 금융투자 | 보험 | 투신 | 기타법인 |
|---|---|---|---|---|---|---|---|---|
| 값 | 26.08.28 | -20,145 | 1,162 | 7,604 | 100 | 200 | 300 | 10,203 |
| 압축한 열 이름 | | 개인 | 외국인 | 기관계 | **기타법인** | | | |

**기타법인이 100 을 받는다.** 실제 값은 10,203 이다. 리포트 첫 단락의 주어가
"기타법인이 1조 넘게 순매수" 인 문서라 이건 문서를 통째로 거짓말로 만든다.
값 행이 안 와서 여태 드러나지 않았을 뿐, 오는 순간 틀린 수치가 사실처럼 나갔다.

`colspan` 을 폭만큼 펴고, 모르는 열은 **`None` 으로 자리를 남긴다.** 열 폭이
머리글과 다른 행은 넣지 않고 버린다. 어긋난 채 넣느니 없는 게 낫다.

진단의 상한도 올렸다. `th` 를 6개에서 끊고 있어서 머리글 전체를 못 봤다 —
이번에 보인 6개가 마침 전부처럼 보였을 뿐이다.

## D-050. 순매수 합이 0 인지 본다 — 열이 밀렸는지는 그것으로만 안다

D-049 를 고치고 실데이터로 돌리니 2026-08-31 수급이 처음으로 채워졌다.

| 개인 | 외국인 | 기관계 | 기타법인 | 합 |
|---|---|---|---|---|
| −1,464억 | −6,434억 | −7,891억 | **+1.58조** | **+11억** |

합이 +11억이다. **한 사람이 산 만큼 다른 사람이 팔았으므로** 네 구분의 순매수
합은 회계적으로 0 이고, 억원 단위 반올림만큼만 어긋난다.

이 성질이 중요한 이유는 하나다 — **열이 제자리에 있어야만 성립한다.** 열이 한 칸
밀려 기타법인 자리에 금융투자 값(300억쯤)이 들어가면 합이 −1.5조가 된다. 값
자체는 `None` 도 `0` 도 아닌 그럴듯한 수라서, 필드 하나만 보는 검사로는 절대
못 잡는다. D-035(거래대금 백만원)와 정확히 같은 종류의 실수다.

`_check_zero_sum()` 이 최신일 한 줄을 보고 합이 3,000억을 넘게 벗어나면 `Fetch`
로 올린다. 화면은 '수급 미확보' 로 정직하게 빈다. 옛 날짜까지 다 보지 않는 이유는
반올림 누적으로 잡음만 늘기 때문이다 — 열이 밀리면 모든 날이 같이 깨진다.

네 구분이 다 없으면 검사하지 않는다. 판단할 근거가 없는 것과 틀린 것은 다르다.

## D-051. 못 찾은 시드에 후보를 붙인다 — 대부분은 사명 변경이었다

D-046 으로 사유 없는 미해결 시드만 이름과 함께 노출하게 했더니, 실데이터에서
30건의 이름이 처음 보였다.

> 한국조선해양, HD현대미포, LIG넥스원, 삼화에이스, 리노스, 뉴로스…

**전부 상장사다.** 비상장 추정이 아니었다. 한국조선해양은 HD한국조선해양으로
사명이 바뀌었고, 나머지도 표기 차이로 보인다. "비상장·사명변경 추정" 이라고
뭉뚱그려 적어 두는 동안 30건이 전부 고칠 수 있는 것이었다.

이름만 보여 주면 사람이 하나씩 검색해야 한다. `difflib` 로 상장 마스터에서 가장
비슷한 이름을 찾아 `near` 에 담고, 화면에는 `한국조선해양→HD한국조선해양` 형태로
적는다. 몇 건에 후보가 있는지도 함께 센다.

**비상장이라 적어 둔 이름에는 후보를 붙이지 않는다.** 안 붙는 게 정상인데
"혹시 이건가" 를 띄우면 그건 노이즈다.

후보를 그대로 `themes.yaml` 에 반영하지는 않는다. 이름이 비슷하다는 것과 같은
회사라는 것은 다르다 — 사람이 보고 고친다. 기계는 좁히는 데까지만 한다.

### 비율만으로는 못 거른다 (실측)

첫 판은 `difflib` 비율 0.6 을 문턱으로 썼다. 실데이터에서 이렇게 나왔다.

| 시드 | 후보 | 비율 | 실제 |
|---|---|---|---|
| 한국조선해양 | HD한국조선해양 | 0.857 | **개명 맞음** |
| 현대미포조선 | HD현대미포 | 0.667 | **개명 맞음** |
| 삼화에이스 | 에이럭스 | 0.667 | 관계 없음 |
| 리노스 | 노머스 | 0.667 | 관계 없음 |
| 뉴로스 | 로스웰 | 0.667 | 관계 없음 |

진짜와 가짜가 **같은 0.667** 에 있다. 문턱을 올리면 진짜 개명이 같이 잘린다.
짧은 이름끼리 글자가 우연히 겹친 것이라 비율로는 구분이 안 된다.

개명에는 다른 성질이 있다 — **옛 이름이 거의 통째로 남는다.** 가장 긴 공통
부분문자열이 짧은 쪽 이름의 60% 이상이고 3글자 이상일 때만 후보로 본다. 위
가짜 셋은 공통 부분이 2글자 이하라 전부 떨어지고 진짜 둘은 남는다.

두산중공업 → 두산에너빌리티처럼 이름을 통째로 바꾼 개명은 이 규칙으로 못 찾는다.
못 찾는 것과 틀린 것을 고르라면 못 찾는 쪽이다.

### 그래도 남는 오탐 — 그래서 단정하지 않는다

부분문자열 규칙을 넣고 다시 돌렸더니 가짜 셋(리노스·뉴로스·삼화에이스)은
'후보 없음' 으로 내려갔지만, 이런 것들이 남았다.

| 시드 | 후보 | 겹치는 부분 |
|---|---|---|
| SK머티리얼즈 | 하나머티리얼즈 | 머티리얼즈 |
| 에이피티씨 | 에이피알 | 에이피 |

업종 접미사가 겹친 것이지 같은 회사가 아니다. 규칙을 더 조이면 진짜 개명이
같이 잘린다. **여기서 규칙 손보기를 멈춘다.**

대신 화면이 하는 **주장**을 고쳤다. "19건은 사명 변경으로 보입니다" 는 19건에
대한 단정인데 확인한 건 두어 건뿐이다. "이름이 비슷한 상장 종목이 있습니다
(같은 회사인지는 확인이 필요합니다)" 로 바꿨다. 기계는 찾을 자리를 좁혀 줄 뿐이고
판단은 사람이 한다 — CLAUDE.md 2장 1번.

같은 이름이 여러 테마에 있으면 목록에 두 번 뜨던 것도 고쳤다. 세는 건 시드
기준이 맞지만 보여 주는 건 이름 기준이다. 같은 이름을 두 번 고칠 일은 없다.

### 남은 것

'비슷한 이름조차 없는' 11건 중 상당수는 상장폐지·비상장으로 보인다
(SK머티리얼즈는 2021년 SK 합병, 뉴로스는 상장폐지). 확인해서 `unlisted:` 에
사유와 함께 적으면 목록에서 빠진다. `LIG넥스원` 만은 지금도 상장돼 있어 다른
질문이다 — D-052 참조.

### 후보가 없는 것은 다른 질문이다

`LIG넥스원` 은 상장돼 있는데 비슷한 이름조차 안 나왔다. 이름 문제가 아니라
**그날 스냅샷에 그 종목이 없었다**는 뜻이다. 화면이 두 경우를 나눠 적는다 —
앞쪽은 이름만 고치면 되고, 뒤쪽은 시세 수집 커버리지 문제다.

## D-052. 전 종목 수가 조용히 줄면 보드는 정상처럼 나온다

D-051 에서 `LIG넥스원` 이 상장 마스터에 없다는 것이 드러났다. 상장돼 있는
회사인데 비슷한 이름조차 안 나왔다 — 이름 문제가 아니라 **그날 스냅샷에 그
종목이 없었다.**

`fetch_universe()` 는 시가총액 목록을 페이지 단위로 훑다가 빈 페이지를 만나면
멈춘다.

```python
rows = pick(js, 'stocks', 'result', 'datas', default=[])
if not rows:
    break
```

중간 한 페이지가 일시적으로 비면 **그 뒤가 통째로 빠진다.** 그리고 예외가 나지
않는다. 보드는 종목이 적은 채로 정상 생성되고, 빠진 종목은 신고가에도 랭킹에도
히트맵에도 없다. 화면 어디에도 "덜 받았다" 는 말이 없다.

"몇 개 받아야 정상인가" 를 절대값으로 박을 수는 없다. 상장 수는 계속 변한다.
**직전 영업일과 비교한다** — 5% 넘게 줄면 사유를 리포트 상단에 올린다. 상장폐지·
거래정지로 하루에 5% 넘게 줄 일은 없다.

예외로 올리지 않고 경고로 두는 이유는, 덜 받았어도 받은 것까지는 맞는 값이기
때문이다. 무엇을 보고 있는지만 정확히 적으면 된다 — CLAUDE.md 2장 6번.

첫 실행에는 비교할 어제가 없으므로 조용하다. 같은 날 다시 돌리면 자기 자신과
비교하게 되므로 `asof < ?` 로 이전 날짜만 본다.

### 비교만으로는 부족하다 — 절대 하한도 본다

어제와 비교하는 검사에는 구멍이 있다. **매일 똑같이 덜 받고 있으면 변화가 없어서
영원히 조용하다.** 실제로 `LIG넥스원` 이 스냅샷에 없는데 경고가 안 떴다.

코스피·코스닥 상장사는 2010년대 이후 줄곧 2,000곳을 넘는다(코스피 약 950 +
코스닥 약 1,700). 펀드를 뺀 주식 수가 2,000 미만이면 목록을 덜 받은 것이다.
이 하한을 어제와의 비교보다 **먼저** 본다.

그리고 종목 수를 화면 머리말에 적는다 — "고가 기준 · 종목 2,703 · 생성 …".
검사에 안 걸리는 수준으로 덜 받아도 눈에는 보인다. 세 자리가 갑자기 네 자리로
바뀌는 건 숫자를 매일 보는 사람이 제일 먼저 알아챈다.

| ③ 이름이 바뀌었다 | — | **맞음.** `079550` = **LIG디펜스앤에어로스페이스** |

원시 목록 3,923종목(펀드 포함)에 표본 대형주 8개가 전부 있었다. 커버리지 문제가
아니었다. 두 번 다 **없는 것을 없다고 단정**한 것이 문제였고, 코드로 직접 찌르는
검사 한 줄이 그걸 끝냈다.

### 왜 후보로도 안 나왔나

`near` 는 "옛 이름이 거의 통째로 남는다" 는 규칙을 쓴다(D-051). 그런데
`LIG넥스원` 과 `LIG디펜스앤에어로스페이스` 의 공통 부분은 `LIG` 3자뿐이고,
짧은 쪽(6자) 대비 0.50 이라 문턱 0.6 에 걸려 떨어졌다.

문턱을 0.5 로 내리면 D-051 에서 걸러 낸 가짜들(리노스→노머스 등)이 다시 들어온다.
**이름만으로 하는 대조는 여기가 한계다.**

### 진짜 고칠 곳은 대조 방식이다

종목명은 바뀌고 종목코드는 안 바뀐다. `themes.yaml` 시드를 코드로 적으면 사명
변경이 아예 문제가 되지 않는다. 지금은 시드가 310개짜리 이름 목록이라 한 번에
바꿀 일이 아니므로 `BACKLOG.md` 에 올린다.

당장은 확인된 것 하나만 고쳤다 — `LIG넥스원` → `LIG디펜스앤에어로스페이스`.
나머지 후보는 코드로 확인하기 전에는 손대지 않는다. 이름이 비슷하다는 것과 같은
회사라는 것은 다르다.

### 잡 로그가 진단을 가리고 있었다

이 결과를 읽으려고 로그를 세 번 다시 받았다. 점검 출력이 '결과 커밋' 앞에 있어서,
그 단계의 스크립트(주석 포함 30줄)가 tail 을 다 차지했다. 점검 출력을 잡 맨
마지막으로 옮기고 커버리지 줄도 함께 찍게 했다. **진단은 읽히는 자리에 있어야
진단이다.**

## D-055. daily 가 48섹터 배정을 스스로 되살린다

PR #4 를 머지하고 `main` 에서 `daily` 를 돌렸는데 섹터 미배정이 그대로 916종목이었다.

D-048 은 daily 가 board48 을 **덮어쓰는** 것을 막았을 뿐, **이미 지워진 것을
되살리지는 않는다.** Actions 캐시는 브랜치 단위라, 브랜치에서 `--classify` 로
다시 붙여도 `main` 은 지워진 DB 를 그대로 물려받는다. 코드를 머지해도 데이터는
안 따라온다 — D-039 와 정확히 같은 모양이다.

### 절차로 풀려다 또 조용히 실패했다

`--classify` 를 따로 태우면 되겠다 싶어 `daily` · `classify` · `daily` 를 연달아
큐에 넣었다. 결과가 이랬다.

```
run 38 (daily)     in_progress
run 39 (classify)  cancelled   ← run 40 이 큐에 들어오면서 밀어냈다
run 40 (daily)     pending
```

`concurrency` 그룹에는 pending 이 **하나만** 남는다(`cancel-in-progress: false`
는 진행 중인 것을 지키는 설정이지, 대기열을 지키지 않는다). 뒤에 하나 더 넣는
순간 가운데가 취소된다. 실패로 찍히지도 않고 그냥 사라진다.

**사람이 순서를 지켜야 하는 절차는 언젠가 어긋난다.** 코드가 자기를 고치게 둔다.

`cmd_daily` 가 수집 전에 `restore_sectors()` 를 부른다. board48 행이 하나도
없으면 `knowledge/sector_map.yaml` 을 읽어 테이블에 쓴다. 네트워크도 API 도
쓰지 않는다.

**이미 board48 인 행은 건드리지 않는다.** 사람이 손본 배정이나 새 분류 결과를
옛 yaml 로 덮으면 안 된다 — 되살리는 것과 덮어쓰는 것은 다르다. 네이버 업종만
붙어 있던 행은 yaml 값으로 올려 준다.

이걸로 캐시가 날아가든 새 러너에서 처음 돌든 다음 daily 한 번이면 제자리로
돌아온다. `--classify` 는 새 종목을 분류할 때만 쓴다.

### 첫 판은 "전부 아니면 전무" 라 또 안 먹었다

처음엔 `board48 행이 하나라도 있으면 건너뛴다` 로 만들었다. 넣고 돌렸더니
섹터 미배정이 916 → 387 로 줄긴 했는데 안내는 그대로였다.

> 섹터 미배정 387종목 — 목표 분류는 board48 인데 실제로 붙어 있는 분류는
> naver_upjong 입니다

표의 섹터 이름은 48섹터(해운사·전기유틸리티·창업투자)인데 '실제 분류는
naver_upjong' 이라고 적는 모순된 상태다. `main` 의 DB 에 옛 분류 행이 **일부**
남아 있어서 복원이 통째로 건너뛰어졌고, 나머지 종목은 네이버 업종 이름을 단
채로 남은 것이다.

**빠진 것만 채운다.** `sync_sectors` 와 같은 upsert 를 쓴다 — 이미 board48 인
행은 그대로 두고, 네이버 업종만 붙어 있던 행은 yaml 값으로 올린다. 두 번 돌려도
아무것도 안 바뀐다.

## D-057. 공시 판정을 진단이 아니라 파이프라인에 넣는다

D-056 은 `--verify-adjust` 로 손으로 돌려 답을 얻은 것이다. 그대로 두면 다음
분할·병합 때 똑같은 12종목 문제가 다시 생기고, 또 사람이 돌려야 한다. 절차로
푸는 것은 언젠가 어긋난다(D-055 에서 이미 겪었다). 코드가 스스로 하게 둔다.

`daily` 가 적재 뒤에 두 단계를 순서대로 돈다.

    refresh_suspects()   의심 종목의 보관 구간을 다시 받아 덮는다.
                         낡은 값이 원인이면 여기서 사라진다.
    confirm_suspects()   그러고도 남은 것만 공시에 묻는다.

DART 호출은 다시 받고도 남은 종목에만 든다. 낡은 값이 원인인 쪽이 먼저 걸러지니
호출이 몇 건으로 줄고, 진짜 의심에만 쓴다.

### verdict 세 갈래

`split_check` 테이블에 코드별로 남긴다.

    action    분할·병합·감자·무상증자 공시가 있다   → 가드 유지
    none      그런 공시가 없다                    → 가드를 푼다
    unknown   조회 실패·corp_code 없음            → **가드를 풀지 않는다**

`DB.split_cleared()` 는 `none` 만 돌려준다. `unknown` 을 섞으면 조회가 실패한 날
가드가 통째로 풀린다 — 못 본 것과 아닌 것은 다르다(CLAUDE.md 2장 6번).

같은 점프일에 대해서는 다시 묻지 않는다. 점프일이 바뀌면 새 사건이므로 다시 묻는다.

### 가드를 푼다는 것의 의미

`evaluate(..., split_cleared=True)` 는 `suspect` 를 내리고 `floor` 를 0 으로
되돌린다. 계단이 실재하는 등락이면 그 이전 구간도 지금 주가와 같은 단위이므로
룩백을 자를 이유가 없다. 사유 문자열은 지우지 않고 뒤에 근거를 덧붙인다 —
화면이 왜 통과시켰는지 설명할 수 있어야 한다.

### 화면에도 적는다

제외한 수만 적으면 어제보다 의심이 줄어도 이유를 알 수 없다.
`n_split_cleared` 를 함께 실어 "N종목은 계단이 있었지만 공시가 없어 실제 등락으로
보고 판정에 포함했습니다" 를 나란히 적는다.


## D-058. 산출물이 스스로와 맞는지 매일 본다

이 프로젝트에서 실제로 사람을 문 버그를 다시 세어 보면 한 종류다.

    1. 상위 라벨이면 하위도 갱신이다      4장 '상위가 하위를 포함'
    2. 갱신한 종류의 갭은 0 이하다        갱신 = 이미 넘겼다
    3. label 은 갱신한 것 중 최상위다     4장 라벨 우선순위
    4. 근접은 갭 임계 안에 있다           4장 근접 정의

임계값 튜닝이 아니다. 이게 어긋나면 계산이 틀린 것이지 시장이 이상한 게 아니다.
그래서 문턱을 고를 여지가 없고, 고를 여지가 없는 검사만 여기 넣는다.

위반은 예외가 아니라 배너다. 어긋난 것도 받은 것까지는 맞는 값이므로 화면을
지우지 않고, 무엇이 어긋났는지와 예시 종목 3개를 그대로 적는다. run_log 에도
실패로 남는다.

실데이터 합성 310종목에 걸어 네 가지 모두 통과하는 것을 확인하고 넣었다.

### 첫 실행에서 바로 하나 잡았다 — 그리고 절반은 검사가 틀렸다

브랜치 daily 에 처음 걸었더니 090410 이 '상위 라벨인데 하위가 미갱신' 으로
찍혔다. 두 가지가 겹쳐 있었다.

**검사 쪽 잘못.** `hits[k]` 는 '갱신 못 했다' 와 '계산하지 못했다' 를 둘 다
False 로 적는다. px 는 420일치만 들고 있으므로 최근 상장 종목은 252영업일을 못
채워 w52 를 계산하지 못하는데, 역사적 최고가는 스칼라가 들고 있어 hist 는
판정된다. 그건 모순이 아니라 창이 짧은 것이다. `gap[k]` 가 None 인지로
'계산했는가' 를 가르도록 고쳤다.

**엔진 쪽 잘못 (D-056 의 남은 절반).** `refresh_suspects` 가 px 만 다시 받고
`alltime` 스칼라는 그대로 뒀다. `roll_alltime` 은 last_date 이후 행만 반영하므로
(그 독스트링이 "백필은 --init 으로" 라고 적어 둔 그대로) 과거를 다시 받아도
스칼라는 낡은 값 그대로다. px 와 alltime 이 서로 다른 시계열을 가리키게 되고,
그 상태에서 가드까지 풀리면 '역사적 갱신인데 52주는 아님' 이 나온다.

스칼라 행을 지우고 상장 이후 전 구간을 받아 다시 세운다. px 에는 보관 구간만
남긴다(`keep_from`) — 4장이 말한 구조 그대로다. 의심 종목 십여 건이라 init
전체(2,800종목)에 비하면 값이 싸다.

검사를 넣지 않았으면 둘 다 조용히 지나갔다.


## D-059. 역사적 최고가가 52주 최고가보다 42% 낮았다

D-058 이 잡은 090410 을 두 번 추측하고 두 번 틀렸다. 세 번째로 추측하는 대신
위반 메시지가 종류와 값을 말하게 고쳤고, 그러자 한 줄로 드러났다.

    상위 라벨인데 하위가 미갱신 1종목: 090410 hist 인데
      w52 갭 +42.23%, d120 갭 +33.24%, d60 갭 +31.65%

역사적 신고가를 냈는데 52주 최고가보다 42% 아래다. 상장 이후 전체가 직전 252일을
포함하므로 이건 정의상 불가능하다. 갭이 아니라 **기준값**이 어긋나 있었다.

### 원인 — 스칼라와 일봉이 다른 fetch 에서 나왔다

`refresh_suspects`(D-056)는 `alltime` 행만 지우고 전 구간을 다시 받았다. `px` 는
지우지 않았다. `INSERT OR REPLACE` 는 새 응답에 있는 날짜만 덮으므로, 응답이
짧게 오면 그 밖의 옛 행이 그대로 남는다. 그러면

    alltime   다시 받은 (짧은) 구간의 최고가
    px 창     남아 있던 옛 행에서 나온 최고가

둘이 서로 다른 시계열을 가리킨다. 라벨 판정이 통째로 어긋난다.

`px` 도 함께 지운다. 둘을 한 번의 fetch 에서만 만들면 어긋날 자리가 없다.
지웠는데 못 받으면 그 종목은 그날 보드에서 빠지므로, 사유를 화면과 run_log 에
남긴다 — 어제까지 있던 종목이 이유 없이 사라지면 안 된다.

### 정의상 불변식을 하나 더 건다

`역사적 최고가 >= 모든 창의 최고가`. 이게 D-058 1번(포함관계)의 **원인 자리**다.
갭은 결과고 기준값이 원인이므로 원인 쪽을 직접 본다. 어긋나면 기준값을 나란히
적는다 — `hist 1,000 < w52 1,730`.

### 배운 것

세 번 추측하는 동안 두 번의 왕복을 썼다. 메시지가 "무엇이 얼마로" 를 말했다면
한 번에 끝났다. 오늘 아침 `HTTP 403` 이 사유 없이 상태코드만 남긴 것과 같은
실수를 검사 메시지에서 반복했다. **판정을 적는 자리에는 판정의 근거도 적는다.**

## D-062. 섹터 뉴스 탭에 레퍼런스 양식의 서술을 얹는다

사용자 지적 — "섹터 뉴스도 처음 준 예시대로 안 나오고 있다". 레퍼런스
(docs/reference-comment.md)의 테마 섹션은 트리거 문장으로 시작한다:
"전일 웨스팅하우스 지분 공동인수설로 시작된 자금 유입이 이틀째 지속."

안 나온 이유는 프롬프트가 아니라 데이터였다. THEME 프롬프트는 이미 "`news` 가
있으면 트리거를 적고, 없으면 적지 마라" 라고 돼 있는데, facts.py 가
`news=None  # 뉴스 소스 미확보. 자리만 둔다` 로 수집된 뉴스를 팩에 싣지 않았다.
수집기(D-044)가 기사를 붙여도 서술 모델에는 한 건도 안 들어갔고, 모델은 규칙대로
트리거를 쓰지 않았다. **재료를 안 주고 양식을 바랐던 것이다.**

- facts.py 가 news.json 을 테마별로 잇는다. url 은 뺀다(서술에 주소를 옮겨 적을
  일이 없다). outlet 은 남긴다 — 단독 보도·미확인 루머 명시(7장 문체 규칙)의
  재료다. 기사가 없으면 빈 리스트가 아니라 None — 프롬프트의 분기가 그걸 본다.
- compose 가 테마 섹션을 narratives.json 으로 따로 남긴다. draft.md 전체를
  다시 파싱하게 두면 조립 형식이 바뀔 때마다 깨진다.
- 뉴스 탭 카드가 서술을 맨 위에, 근거 기사를 아래에 싣는다. 서술이 없으면
  지금처럼 헤드라인만 — 있으면 좋은 것이지 없다고 탭이 비면 안 된다.
- 서술은 verify(2장 4번)를 통과한 본문에서 잘라낸 것이라 다시 검증하지 않는다.
  뉴스가 팩에 들어가므로 트리거 인용의 이름·수치도 검증 사전에 자동으로 잡힌다.


## D-063. 매일 17:30 최종 산출물을 텔레그램으로 보낸다

사용자 요청. 매 영업일 17:30 KST 에 보드 HTML 과 랭킹 엑셀 두 파일을 텔레그램
첨부로 보낸다.

### 두 크론으로 나눈다

    07:10 UTC (16:10 KST)   daily — 보드를 만들어 커밋 (기존)
    08:30 UTC (17:30 KST)   send-files — 커밋된 docs/ 를 그대로 발송 (신규)

발송 크론이 보드를 다시 만들지 않는다. 16:10 산출물이 이미 레포에 있고, 다시
만들면 16:10 과 17:30 화면이 미묘하게 달라질 수 있다 — 보낸 것과 보관된 것이
같아야 한다. GitHub 예약 실행은 기본 브랜치에서만 돌므로 이 자동화는 main 에
머지돼야 산다.

### 기준일은 DB 가 아니라 사이트에서 읽는다

보내는 대상이 docs/ 이므로 기준일도 docs/d/index.json 의 latest 다. DB 캐시가
빈 러너에서도 발송은 성립해야 하고, 캐시가 낡았을 때 DB 날짜로 판단하면 멀쩡한
사이트를 낡았다고 오판한다.

### 휴장일 가드 (--only-fresh)

휴장일에도 크론은 돌고 보드 기준일은 직전 거래일로 남는다. 그대로 보내면 같은
파일이 휴일마다 다시 온다. 예약 발송은 기준일이 오늘(KST)이 아니면 생략하고
생략 사실을 로그에 남긴다. 손으로 부르는 `--send files` 는 가드 없이 보낸다.

### 파일 이름과 결손

index.html 은 채팅방에서 무슨 파일인지 안 보인다. `신고가보드-YYYY-MM-DD.html`
사본을 만들어 보낸다. 엑셀이 없으면 HTML 만 보내되 **없다는 사실을 함께
보낸다** — 조용히 한 개만 오면 받은 쪽은 원래 한 개였다고 믿는다.

## D-065. ETN 이 한글에 붙어 있으면 필터가 놓쳤다

D-064 로 빨강에 혼자 남은 `520101` 의 정체를 물었다.

    520101  "미래에셋 레버리지 SK하이닉스 단일종목ETN" · KOSPI · 종가 8,965

ETN 이 맞다. 그런데 왜 안 걸렸나 — `\bETN\b` 가 원인이다. 파이썬 정규식에서
한글은 낱말 문자라 '단일종목ETN' 의 '목' 과 'E' 사이에 경계가 생기지 않는다.
띄어 쓴 `KB BYD 밸류체인 ETN` 만 걸리고, 붙여 쓴 상품명은 통째로 빠져나갔다.

한 줄이 세 겹으로 샜다. 레버리지 ETN 이 주식 유니버스에 있었고(funds.py 를 쓴
이유 그 자체다 — 첫 실행에서 역사적 신고가 49종목 중 44개가 채권형 ETF 였다),
가드가 그 계단을 잡았고, DART 에 물어보니 corp_code 가 없었고, 그 실패가
배너에 남았다. **가장 바깥 증상(배너 한 줄)부터 따라 들어가니 가장 안쪽
원인(정규식 한 줄)이 나왔다.**

라틴 글자·숫자에 붙은 것만 거른다. `ETNA바이오`·`한국ETNC` 는 안 잡아야 한다.

    _ETN = re.compile(r'(?<![A-Za-z0-9])ETN(?![A-Za-z0-9])', re.I)

ETF 쪽도 같은 구멍이라 함께 고쳤다. 고친 뒤 제외 수가 372 → 373 종목으로 늘었다.


## D-066. 시드 사명 변경은 표로 남기고, 판정은 마스터가 한다

`themes.yaml` 시드 29건이 "상장 마스터에 없습니다" 로 매일 떴다. 정체를 코드로
물어 확인했더니 대부분 결손이 아니라 **사명 변경**이었다.

    LIG넥스원    코드 079550 있음 · 이름 "LIG디펜스앤에어로스페이스"

이름만 보면 사명 변경과 수집 결손이 똑같은 '없음' 으로 나온다. 처방이 완전히
다르므로(전자는 표 한 줄, 후자는 수집기 수리) 진단은 **이름과 코드를 따로**
본다. 하마터면 D-051 처럼 수집 문제로 읽을 뻔했다.

고칠 자격은 마스터가 증명한 것에만 준다. 현재 이름이 옛 이름을 통째로 담고
있는(접두·접미 브랜드가 붙은) 일곱만 `renames:` 표에 넣었다.

    한국조선해양 → HD한국조선해양   금호석유 → 금호석유화학
    나스미디어 → KT나스미디어       티라유텍 → LS티라유텍
    파수 → 파수AI                  만도 → HL만도
    효성첨단소재 → HS효성첨단소재

나머지 20건은 남긴다. 후보를 내고 마스터에 물어보니 틀린 것이 여럿이었다 —
`089970` 을 '에이피티씨' 로 알고 물었더니 '브이엠' 이 돌아왔다. **기억은 후보를
낼 뿐이고 판정은 마스터가 한다**(규칙 4). 틀린 매핑은 빈칸보다 나쁘다. 빈칸은

남은 20건은 상장 마스터에도 저장소에도 옛 이름이 없어 자동으로는 못 푼다.
사람이 이름별로 판단해 `renames:` 나 `unlisted:` 에 적어야 한다.

## D-067. 섹터 순위에 전일 대비 변동을 붙인다

순위만 있으면 '오늘 반도체가 3등' 까지만 안다. 어제 12등이었는지 2등이었는지에
따라 같은 3등이 전혀 다른 이야기다. 전일 `rankings.json` 의 같은 표(`key` 로
짝짓는다)에서 같은 이름을 찾아 뺀다.

부호는 **올라간 쪽이 양수**다. 순위 숫자는 작아지는 게 좋은 방향이라 그냥 빼면
부호가 뒤집힌다.

어제 표에 없던 섹터는 **0 이 아니라 `None`** 이다. 구성종목 수가 하한(5개)을
넘나들면 섹터가 표를 드나드는데, 그걸 '변동 없음' 으로 적으면 없는 사실을
단정하는 것이다(규칙 1). 화면은 `None` 을 '–' 로 두고, 전일 파일 자체가 없으면
칸을 비운다.

## D-068. 일봉을 읽는 방법을 세 갈래로 나눈다

`all_series` 는 전 종목 일봉을 한 dict 에 올린다. 420일 x 2,800종목 = 120만 행이라
지금은 견디지만, **한 종목씩 보고 버리면 되는 자리**(`suspect_codes`)와 **열 몇
개만 보는 자리**(`confirm_splits`)까지 그걸 쓰고 있었다. 매 daily 마다 120만 행을
두 번 더 올린 셈이다.

- `iter_series(conn, upto)` — `(code, 일봉)` 을 코드 순서로 흘려보낸다. 쿼리는
  이미 `ORDER BY code` 라 커서를 끊어 주기만 하면 되고, 쿼리 횟수는 그대로 한 번이다.
- `series_for(conn, codes, upto)` — 지정한 종목만. SQLite 변수 한도(999)를 넘지
  않게 500개씩 나눠 묻는다.
- `all_series` — 전 종목을 동시에 들고 있어야 하는 `engine/build` 만 쓴다.
  이제 `dict(iter_series(...))` 한 줄이다.

세 갈래가 **같은 결과를 준다**는 것을 `tests/test_series_read.py` 가 지킨다.
메모리를 아끼려다 판정이 달라지는 것이 여기서 제일 위험하다.

## D-069. 우선주·스팩·리츠를 빼지 않고 나눈다

우선주는 유동성이 얇아 하루 몇 %가 쉽게 나오고, 스팩은 합병 기대만으로 오르며,
리츠는 배당락 주기로 움직인다. 셋 다 '오늘 이 산업에 무슨 일이 있었나' 와 무관한데
신고가 표의 자리를 차지한다.

그렇다고 빼면 안 된다 — 리츠만 보고 싶은 날이 있다. 그래서 **표시만 붙이고
화면에서 끈다**(`보통주만` 알약).

판정은 `engine/kinds.py` 한 곳에서 하고, universe.json 의 각 행이 `kind` 를 싣는다.

- **우선주** — 코드 끝자리가 0 이 아니고(보통주는 0) 이름이 `우` · `우B` ·
  `2우B` 로 끝난다. **둘 다 맞을 때만** 단정한다. 코드만 보면 신주인수권증서가
  섞이고, 이름만 보면 끝 글자가 '우' 인 보통주를 잘못 읽는다. 한쪽만 맞으면
  보통주로 둔다 — 틀린 표시는 빈칸보다 나쁘다(D-066 과 같은 이유).
- **스팩** — 이름에 `스팩`. 국내 SPAC 는 예외 없이 상품명에 넣는다.
- **리츠** — 이름이 `리츠` 로 끝난다. `리츠상사` 같은 이름을 잡지 않으려고
  끝일 때만 본다.

## D-070. 근접 표가 로드되자마자 통째로 숨고 있었다

`board.js` 의 필터가 `#p1 tbody tr` **전체**에 '고른 기준의 라벨이 없으면 숨김'을
걸고 있었다. 달성 표의 행은 `data-hi` · `data-cl` 을 싣지만 **근접 표의 행은 라벨
자체가 없다** — 근접은 아직 신고가가 아니라 갭이 좁다는 뜻이니 당연하다. 그래서
근접 행이 전부 `!kind` 로 떨어져 `display:none` 이 됐다.

라벨 검사를 `'hi' in tr.dataset || 'cl' in tr.dataset` 인 행으로 제한했다. 근접
행은 거래대금·시총·보통주 필터만 받는다.

자바스크립트는 테스트에서 돌릴 수 없으므로, 그 조건이 소스에 남아 있는지와
근접 표가 라벨 속성을 싣지 않는다는 것을 `tests/test_kinds.py` 가 함께 본다.

## D-072. 시가총액 1,000억 하한을 생성 단계에서 건다

사용자 요청이다. 보드에 시총 1,000억 미만 종목이 올라오지 않게 한다.

**화면 토글이 아니라 `newhigh.json` 을 만들 때 건다.** 토글로 두면 파일에는 그대로
남아서 엑셀·텔레그램·아티팩트가 각각 다른 목록을 들고 나간다. 화면에서만 안 보이고
파일에는 있는 상태가 제일 나쁘다 — 어느 쪽이 맞는지 물어볼 곳이 없어진다.

세 하한을 같은 값으로 맞췄다. 한 화면에서 표마다 하한이 다르면 같은 종목이 어떤
표에는 있고 어떤 표에는 없는 이유를 설명할 수 없다.

    display.min_mktcap_eok      1,000억  (신설 — 신고가 달성·근접 표)
    proximity.min_mktcap_eok      200 → 1,000억
    rankings.min_mktcap_eok       300 → 1,000억

`proximity` 를 200 으로 두면 근접 판정은 200억으로 해 놓고 표에서 1,000억으로 다시
거르게 되어, 화면 머리말의 '시총 200억 이상' 이 거짓이 된다. `rankings` 를 올린
것은 섹터 등락률의 모집단도 함께 바뀐다는 뜻이다 — 대형주 비중이 올라간다.

**하한 미달과 시총을 모르는 것을 따로 센다** (`n_below_mktcap` / `n_mktcap_unknown`).
합쳐 세면 소스가 시총을 안 준 날에도 '하한으로 걸렀다' 는 회색 안내만 나가고 진짜
실패가 묻힌다. 배너도 앞은 회색(집계 범위), 뒤는 빨강(빠진 데이터)으로 나눠 싣는다
(규칙 1·6, D-064).

알약의 라벨별 종목수도 걸러낸 뒤의 모집단으로 센다. 전 종목으로 세면 알약의 숫자와
표의 행수가 어긋난다.

화면의 '시총 1,000억↑' 토글은 없앴다. 표에 실린 종목이 이미 전부 하한 위라 할 일이
없다.

## D-073. 탐지기 6의 숫자는 '몇 종'이 아니라 '어느 등급 이상'이다

D-071 로 20일을 빼면서 탐지기 6이 잡는 것이 조용히 바뀌었다. 고쳐서 되돌린다.

**라벨은 중첩이다.** 52주를 뚫으면 60일도 자동으로 뚫리고, 역사적을 뚫으면 둘 다
뚫린다(CLAUDE.md 4장 '상위가 하위를 포함'). 그래서 `multi_label_min` 은 실제로는
등급을 고르는 손잡이고, 라벨을 하나 빼면 같은 숫자가 다른 등급을 가리킨다.

    20일이 있던 시절(4라벨)  3 = 52주 이상    ← 원래 동작
    20일을 뺀 뒤(3라벨)      3 = 역사적만
                             2 = 52주 이상    ← 되돌린 값

실측으로 확인했다. 300일 정상 시계열이 52주를 뚫으면 `hits=['w52','d60']` 두 개다.
옛 구성에서는 여기에 `d20` 이 붙어 셋이었고 3 을 넘겨 이벤트가 났다. 새 구성에서는
둘이라 3 을 못 넘긴다 — 어제까지 잡히던 것이 오늘부터 안 잡힌다는 뜻이다.

네 가지 경우(60일만 / 52주 / 역사적 / 이력이 짧아 52주를 못 센 역사적)에서 옛
구성(4라벨·3)과 새 구성(3라벨·2)이 같은 집합을 낸다는 것을 테스트가 지킨다.

**교훈은 D-010 과 같다.** 창을 늘리거나 줄일 때 `MULTI_LABEL_SET` 만 맞추면 되는
줄 알았는데, 임계값도 함께 봐야 한다. 중첩된 라벨을 세는 임계값은 라벨 수에
매달려 있다.

## D-074. 화면 임계값은 서버가 실어 보낸다

`board.js` 에 `TURN_MIN = 50` 이 박혀 있고 `settings.yaml` 에는
`display.min_turnover_eok: 5.0` 이 따로 있었다. 둘은 이어져 있지 않았다.

- 설정을 고쳐도 화면이 꿈쩍하지 않는다 (CLAUDE.md 3장 위반)
- 값이 10배 다른데 어느 쪽이 맞는지 물어볼 곳이 없다
- 알약에 '50억' 이라 적어 놓고 다른 숫자로 거를 수 있다 — **화면이 거짓말을 한다**

`build` 가 `newhigh.json` 에 `min_turnover_eok` 을 싣고, `_pills` 가 그 값으로
문구와 `data-min` 을 함께 만들고, `board.js` 는 알약에서 읽는다. 문구와 판정이
한 값에서 나온다.

설정값은 실제로 돌던 50.0 으로 맞췄다. 사용자가 지금까지 본 화면이 그쪽이다.
주석의 '기본 숨김' 도 실제 동작(기본 꺼짐, 눌러야 걸림)으로 고쳤다.

## D-080. '종가' 는 KRX 정규장 종가다

**사용자 결정(2026-09-17).** BACKLOG 에 '당일 종가가 잠정치로 판정됨' 으로 올라와
있던 항목의 답이다. 두 선택지(① 정규장 종가로 고정 ② 16:07 초안 → 익일 확정 재판정)
중 ①을 골랐다. 재판정 경로는 만들지 않는다.

### 무엇이 문제였나

2026-09-01 state 의 종가를 9/7 시점 네이버 siseJson 일봉과 대조하면 유니버스
2,686종목 중 **2,369종목(88.2%)** 이 다르고 |차| 중앙값 0.67%, 3% 초과가 108종목이었다
(롯데렌탈 -4.7%, 자이에스앤디 +5.2% — 양방향). 달성 표 안에서만 14건이 종가 기준
라벨을 바꿀 크기였다(위더스제약 9,090→8,320, 헝셩그룹 3,800→3,500,
SK케미칼 54,700→54,100).

**고가는 전부 일치했다.** 판정 로직이 아니라 수집 시점의 문제다. 네이버 siseJson 의
당일 행은 NXT 애프터마켓(15:30~20:00)과 시간외 단일가가 끝날 때까지 계속 움직인다.
16:07 크론이 받는 값은 종가가 아니라 그 시각의 중간값이다. 이튿날 `--daily` 가 최근
15일을 다시 받으므로 DB 는 스스로 고쳐지지만, **그날 낸 state·보드·라벨·엑셀·텔레그램은
잠정치로 남는다.** 고쳐진 값은 아무 데도 반영되지 않는다.

### 어떻게 고쳤나

KRX 오픈API `stk_bydd_trd`·`ksq_bydd_trd` 가 정규장 확정치를 하루 1회로 준다.
(D-011 에서 인증이 풀렸고 2,686종목을 준다는 것을 이미 확인했다.)

- `pipeline.krx_regular_day()` 가 기준일의 확정 시세를 받는다. 최대 7일을 뒤로 훑되
  **찾은 공표일이 기준일도 아니고 DB 의 마지막 장 세션도 아니면 쓰지 않는다.**
  그건 '오늘 것이 아직 안 나왔다' 는 뜻이고, 그 값으로 오늘 스냅을 덮으면 보드가
  조용히 어제 값으로 나간다 — 잠정치보다 나쁜 실패다.
- `_apply_krx_bar()` 가 일봉의 **당일 행**을 덮는다. `roll_alltime` **앞**이다.
  뒤에 덮으면 사상 최고가·사상 최고 종가가 잠정치로 굳은 채 이튿날에도 안 고쳐진다.
  소스가 못 준 칸은 원래 값을 남긴다 — None 으로 덮으면 일봉에 구멍이 뚫린다.
  네이버에 당일 봉이 아예 없는 종목은 확정치로 채운다.
- `_apply_krx_snapshot()` 이 스냅샷의 종가·등락률·거래량·시가총액·거래대금을 덮는다.
  KRX 는 거래대금을 실제로 주므로 그날의 `turnover_is_estimate` 가 False 가 된다.
- 재수집 경로(`refresh_suspects` · `repair_alltime` → `_refetch_full`)에도 같은
  확정치를 넘긴다. 안 넘기면 그 종목만 조용히 네이버 잠정치로 되돌아간다.

### 못 받은 날

조용히 넘어가지 않는다 (CLAUDE.md 2장 1·6번). 인증키가 없거나 확정치가 아직
안 나왔으면 네이버 값을 그대로 쓰되 **잠정으로 표시한다.**

- `run_log` 에 `close_krx` 실패와 사유를 남긴다.
- `build` 가 스냅샷의 `source` 로 판정한다 — 수집이 덮었으면 `krx` 가 찍혀 있다.
  `universe.json`·`newhigh.json` 에 `close_source`·`close_confirmed` 를 싣는다.
- 보드 머리에 '종가 잠정' 이 붉게 붙고 배너에 사유가 올라간다. 확정이면 '종가 확정'.
  **옛 state 에는 이 키가 없다. 그때는 아무것도 적지 않는다** — 모르는 것을
  '확정' 이라고 쓰지 않는다.

### 딸려 오는 것

- `DATA_VERSION` 3 → 4. v3 DB 의 당일 종가는 NXT·시간외가 섞인 잠정치이고
  종가 기준 라벨과 alltime 스칼라가 그 위에서 굳어 있다. 고친 코드가 그 DB 위에서
  돌면 안 된다 (D-039 가 정확히 그 사고였다).
- `flowlab verify` 의 '유니버스 당일 종가 대조' 는 이제 WARN 이 아니다.
  보드 종가는 KRX 정규장, flowlab 이 읽는 네이버 siseJson 은 NXT·시간외 포함이라
  **정의상 다르다.** state 가 `close_confirmed: true` 면 사실만 적는다.
  고가 쪽 차이는 그대로 WARN 이다 — 고가는 두 정의가 같아야 한다.
- 발송 시각은 그대로다(16:07 수집 · 17:15 초안 · 18:00 발송). 20:00 이후로 옮기는
  선택지는 버렸다. 마감 코멘트가 20시에 나가면 당일 리포트로서의 가치가 없다.

## D-081. KIS 시장 전체 수급은 파라미터 문제가 아니었다 — 이 앱키가 못 받는다

CLAUDE.md 9장 2번을 2026-09-17 Actions 실측 네 번(run 97·99·100·101)으로 닫는다.
**`mode=kis-probe` 격자가 답한 것은 "어느 조합이 맞다" 가 아니라 "조합의 문제가
아니다" 였다.** 그것도 답이다.

### 무엇을 재 봤나

`inquire-investor-daily-by-market` (tr_id `FHPTJ04040000`) 를 세 축으로 흔들었다.

| 축 | 후보 | 결과 |
|---|---|---|
| `FID_COND_MRKT_DIV_CODE` | `U` · `J` | **`U` 확정.** `J` 는 rt_cd=2 `ERROR INVALID` |
| `FID_INPUT_DATE_1/_2` | 당일~당일 · 3일 · 30일 | **무시된다.** 어느 쪽이든 같은 300행 |
| `FID_INPUT_ISCD` / `_1` / `_2` | `0000`·`0001`·`2001` × `''`·`0000`·`1000`·`9000` × `''`·시장코드 (24조합) | **전부 rt_cd=0 · 300행 · ntby 살아있는 키 0** |

### 무엇이 사실인가

1. **질의는 처음부터 성립하고 있었다.** rt_cd=0 이고 300행이 온다.
2. **지수 시세는 정확하다.** `bstp_nmix_prpr` 가 6715.41 로 그날 코스피 종가와
   같다. `FID_INPUT_ISCD` 를 `0000` 으로 바꾸면 다른 지수 계열이 온다 —
   파라미터가 실제로 먹히고 있다는 뜻이다.
3. **필드 이름도 틀리지 않았다.** `prsn`·`frgn`·`orgn_ntby_tr_pbmn` 가 응답에
   있고, 증권·보험·투신·은행·종금·기금·사모·기타법인·기타기관·등록/미등록
   외국인까지 주체별 칼럼 30개가 다 있다.
4. **그 30개가 300행 전부 0 이다.** 어느 조합에서도 하나도 살아나지 않는다.

### 그래서 앞선 진단 둘이 틀렸다

- ~~D-032 "이름은 알고 값은 모른다"~~ → 이름도 값도 맞다.
- ~~D-037 "빈 값으로 채워 불러서 0 이 온다"~~ → 값을 채워도 0 이다. 빈 값이
  원인이 아니었다.

두 문장이 1년 가까이 백로그에 '파라미터 값을 확정할 것' 으로 남아 있었는데,
그 방향으로는 답이 없었다. 격자를 한 번 돌려 보는 것이 문서를 다시 읽는 것보다
빨랐다.

### 남은 결론

같은 앱키로 **종목별 수급(`inquire-investor`, FHKST01010900)은 실제 숫자를
준다.** 계정이 투자자 데이터를 아예 못 받는 것은 아니다. 시장 **전체** 집계만
0 으로 온다. 코드로 더 좁힐 곳이 없다 — 남은 것은 KIS 쪽 권한·서비스 신청이다.

그래서 이 항목은 코드 백로그에서 내리고 두 갈래로 적어 둔다.

- **KIS 에 확인한다** (사용자만 할 수 있다). 시장별 투자자매매동향이 개인
  앱키(custtype=P)에 열려 있는지, 별도 신청이 필요한지.
- **다른 소스를 찾는다.** 네이버 폴백
  (`sise/investorDealTrendDay.naver`)은 **HTTP 410** 으로 없어졌다. D-079 가
  종목별에서 한 것과 같은 작업 — 시장 전체판 trend JSON 주소를 찾아야 한다.

그때까지 보드는 지금처럼 **`market.has_flows: false` 로 두고 초안 머리의
'빠진 것' 에 사유를 적는다.** 0 을 숫자로 내보내지 않는다 (CLAUDE.md 2장 1번).
진단기(`--kis-probe`)는 남겨 둔다. KIS 가 권한을 열어 주면 한 번 돌려 확인하는
자리다.

## D-082. 시장 전체 수급을 새 주소로 옮긴다 — 구분은 셋, 단위는 검산으로 정한다

2026-09-18 보드 머리말에서 개인·외국인·기관계·기타법인이 통째로 사라지고
'투자자별 수급 — 소스 미확보' 한 줄이 됐다. 두 갈래가 같은 날 함께 막혔다.

- **KIS** — D-081 에서 닫혔다. 파라미터 문제가 아니라 이 앱키가 시장 **전체**
  집계를 못 받는다. 남은 것은 KIS 권한·서비스 신청이고 사용자만 할 수 있다.
- **네이버 폴백** — `sise/investorDealTrendDay.naver` 가 **HTTP 410** 이다.
  맨 요청·UA·UA+Referer·UA+Referer+Accept 네 조합 전부 410 이라 헤더 문제가
  아니다. 410 은 영구 삭제다. 종목별이 하루 먼저 같은 길을 갔다(D-079).

### 공식 소스 두 곳도 닫혀 있다

근본 해결이 될 뻔했으나 둘 다 없었다. 각각 대조군을 함께 걸어 '경로가 없다' 와
'키가 막혔다' 를 구분했다 — 이걸 안 나누면 다음 수를 못 고른다.

| 소스 | 대조군 | 투자자별 | 읽는 법 |
|---|---|---|---|
| KRX 오픈API | `stk_bydd_trd` 200 | 후보 10개 전부 404 | 키는 멀쩡, 그 서비스가 없다 |
| 공공데이터포털 | `getStockPriceInfo` 2,870종목 | 후보 3개 400 | 같음 |

공공데이터는 1차 진단에서 대조군까지 403 이 났는데 그건 **진단의 결함**이었다.
`datago` 는 인증키를 디코딩·원본 두 형태로 눌러 보는 `call()` 이 따로 있는데
진단이 `key_forms()[0]` 만 썼다. 본 코드와 다른 방식으로 부르면 무엇을 확인한
것인지 알 수 없다.

### 새 주소

    https://m.stock.naver.com/api/index/{KOSPI|KOSDAQ}/integration
    → dealTrendInfo {bizdate, personalValue, foreignValue, institutionalValue}

`/trend` 도 같은 셋을 주지만 `/integration` 을 쓴다. 같은 응답에 `totalInfos`
가 들어 있고 거기 거래대금이 **단위를 글자로** 달고 온다 — 단위 검산에 그게
필요하다.

이걸 찾는 데 한 번 헛걸음했다. 2차 진단이 형제 엔드포인트를 훑을 때 금액
키워드(VALUE·AMOUNT·TRADING…)로 걸렀는데 `dealTrendInfo` 에는 그 단어가 없어
목록에서 이름만 스쳐 갔다. **필터가 답을 가렸다.** 모르는 응답을 훑을 때 키워드로
좁히면 찾으려던 것을 그 키워드가 지운다 — 그래서 3차는 거르지 않고 통째로 찍었다.

### 바뀐 것 셋

**1. 구분이 넷에서 셋으로 줄었다.** 기타법인을 새 소스가 안 준다.
**역산해 채우지 않는다.** 네 구분의 합이 0 이라는 항등식은 그 넷이 전체를 나눌
때만 성립하고, 새 소스가 같은 방식으로 나눈다는 보장이 없다. 머리말에서 조용히
사라지면 '오늘은 0 이었나' 로 읽히므로 `columns_absent` 로 실어 보내 집계 범위
배너에 사유를 적는다(규칙 6).

**2. 단위 표기가 없다.** 옛 페이지는 머리말에 '백만원/억원' 을 적어 줬는데 새
JSON 은 맨 숫자다. 짐작하지 않고 **거래대금으로 상한을 건다** — 한 사람이 산
만큼 다른 사람이 팔았으므로 순매수 절대합은 거래대금의 두 배를 넘을 수 없고,
눈금이 100배 어긋나면 이 상한을 바로 넘는다. 2026-09-18 실측으로 억원이 맞음을
확인했다: 코스피 거래대금 255,634억(`25,563,397백만`), 순매수 절대합 55,476억
(21.7%). 같은 값이 백만원이었다면 555억 — 25조 거래대금 대비 0.2% 로, 전일까지
옛 소스가 주던 조 단위와 두 자리가 어긋난다.

거래대금을 못 읽은 날은 검산을 건너뛰되 그 사실을 `scale_note` 로 남겨 빨간
배너에 올린다. 조용히 통과시키면 다음에 눈금이 바뀌어도 모른다.

**3. 하루치뿐이다.** `pageSize`·`page`·`size`·`count`·`limit` 일곱 가지를 다
걸어도 103바이트·1일치다. 옛 페이지는 며칠치를 줬다. 과거가 필요하면 매일 받아
쌓는 수밖에 없다.

### 지운 것

HTML 표 파서 전체가 죽었다 — `_table_rows` · `_header_cols` · `_text` ·
`shape` · `market_params` · `_today_kst` · `_check_zero_sum` 과 그 시험 7클래스.
읽을 표가 더는 없다. **`_check_zero_sum` 을 남겨 두는 것이 특히 나빴을 것이다** —
네 구분의 합으로 열 밀림을 잡던 가드인데, 구분이 셋이 되어 아예 돌지 않는다.
그대로 두면 보드에 가드가 있는 것처럼 보인다. 열이 이름으로 오는 새 API 에서는
열 밀림 자체가 불가능하고, 그 자리를 `_check_scale` 이 대신한다.

## D-083. KIS 가 23시 전후 접속 불가 — 빠른 실패 + 네이버 종목 수급 폴백

2026-09-21 예약 실행(board.yml run 109)의 '종목 수급' 단계가 22:59~23:09 KST 에
돌았고 **11종목 전부** `ConnectTimeout ... openapi.koreainvestment.com:9443 ...
connect timeout=25` 로 실패했다. 같은 날 17:20 KST 수동 실행(run 108)과 9/17
18:27 KST 실행은 **11/11 성공**이다. 같은 코드·같은 앱키·같은 러너에서 시각만
다르다.

읽는 법 — 인증이 아니라 **TCP 가 안 붙었다.** rt_cd 도 HTTP 상태도 없이 접속
단계에서 끝났고, 열한 번이 같은 25초 타임아웃이다. 원인은 KIS 쪽 점검 시간대로
**추정**한다. 실측이 하루치뿐이라 단정하지 않는다 — 몇 시에 열리는지, 매일인지,
주말도 그런지 모른다. 계기는 GitHub 크론 지연이다. 16:07 KST 잡이 그날 ~5시간
밀려 23시에 돌았다(8장 — 크론은 제때를 보장하지 않는다).

### 그날 실제로 나간 것

- 종목당 25초 × 재시도 2회 → 11종목에 **9분**을 쓰고 전부 비었다.
- `missing` 사유가 종목마다 requests 스택 500자였다. 배너와 텔레그램에 그게 그대로
  실렸다 — `↳ 수급 못 받음` 11줄.
- 시장 전체 수급(market.json)은 네이버 폴백(D-082)이 있어 정상이었다. **종목별에는
  폴백이 없었다.**

### 바꾼 것

**1. 빠른 실패.** `stockflows.collect` 가 KIS 호출이 접속 단계에서 실패하면
(`kis.connect_failed` — ConnectTimeout·ReadTimeout·ConnectionError·'Max retries'·
'timed out'. `HTTP 5xx · …` 처럼 상태코드가 있는 실패는 붙은 뒤라 제외)
그 자리에서 'KIS 접속 불가' 로 판정하고 **나머지 종목은 KIS 를 부르지 않는다.**
시도는 2회(재시도 1회)로 줄였다(`KIS_RETRIES` — http.get 의 시도 횟수다). 붙지
못한 것은 다시 불러도 붙지 않지만, 정상 시간대의 일시적 실패 한 번에 하루치를
추정치로 바꾸지는 않는다. rt_cd 오류·파싱 실패는 붙은 뒤의 실패라 지금처럼
**종목 단위**로 남긴다.

사유는 한 줄이다 — `KIS 접속 불가(연결 시간 초과, 23:02 KST) — 23:00 KST 전후
점검 시간대로 추정`. 실패 시각을 적고, 22~00시에 났을 때만 '추정' 을 붙인다.
다른 시각에 안 붙은 것은 이유를 모르는 것이라 짐작을 적지 않는다.

**2. 네이버 폴백.** `m.stock.naver.com/api/stock/{code}/trend?pageSize=N`
(D-079 에서 찾아 둔 주소. `flows.fetch_stock` 이 파싱한다). KIS 접속 불가면 전
종목에, KIS 가 종목 단위로 실패한 종목에도 건다. 이 값은 KIS 와 성격이 다르다.

| | KIS | 네이버 trend |
|---|---|---|
| 값 | 순매수 **금액**(억원) | 순매매**량**(주) |
| 구분 | 기관·외국인·개인 | 기관·외국인. **개인은 응답에 없는 날이 있다** |
| 저장 | `unit='억원'`, `source='kis'` | `unit='주'`, `source='naver'`, `close` |

개인은 **응답에 있으면 담고 없으면 만들지 않는다.** 없는 것을 0 으로 쓰면 '개인이
안 샀다' 가 된다(2장 1번). 금액이 필요하면 순매매량 × 종가 ÷ 1e8 을 **별도 키**
`amt_est` 에 `is_estimate: true` 와 함께 넣는다(억원 소수 4자리 = 만원 자리까지.
1자리에서 자르면 1천만원 미만이 0.0/-0.0 이 된다). 실제 순매수 금액은 체결가
가중이라 이 값과 다르다.
텔레그램은 `기관 +63,482주(추정 +18.6억) · 외국인 -12,000주(추정 -3.5억) (네이버)`
로 적는다 — 출처와 '추정' 이 줄마다 보인다.

**3. 사유를 종목별로 찾을 수 있게 구조를 바꿨다.** `stockflows.json` 에
`failed: {code: 한 줄 사유}` 와 `kis_down`(접속 불가 사유, 정상이면 null),
`n_naver` 가 생겼다. `by_code` 항목에 `source` 가 붙고, 종목 단위 KIS 실패 뒤
네이버로 채운 종목은 `kis_error` 를 함께 갖는다. `_as_of`·`missing`·`unit`
규약은 그대로다. `unit` 은 KIS 와 네이버가 섞이면 `mixed` 다 — 원래 있던 규칙.

**4. 배너(`flow_missing`)는 같은 사유를 한 줄로 묶는다.**
`KIS 접속 불가(…) — 11종목 → 네이버 폴백 9종목 성공 · 2종목 실패(이름(코드), …)
· 네이버 사유: HTTP 500 · 본문 없음`. 접속 불가가 몇 종목 뒤에 왔으면 `KIS 로
3종목 받은 뒤 8종목 → …` 로 실제 분기 수를 적는다. 폴백이 성공해도 `네이버 폴백
N종목은 기관·외국인 순매매량(주)이고 개인은 응답에 없습니다 — 억원 표기는 종가
환산 추정치입니다` 한 줄을 남긴다(구분은 실제로 받은 것을 적는다). 조용히 바꾸지
않는다(2장 6번). 그래서 이 목록에는 못 받은 것과 **대체한 것**이 함께 든다 —
대시보드 배너 제목도 '종목별 수급 — 못 받은 것·대체한 것' 이다.

**5. `--check` 에 폴백 프로브.** 삼성전자(005930) trend 를 받아 파싱 행수·최신
bizdate·개인 유무를 PASS/FAIL 로 찍는다(`stockflows.probe`). KIS 가 막힌 시각에
이 경로마저 죽어 있으면 그날 종목 수급이 통째로 비는데, 점검에 없으면 다음 daily
의 배너에서야 안다.

### 하지 않은 것

- 크론 시각을 옮기지 않았다. 지연은 GitHub 쪽 사정이고(8장) 재시도 크론과
  `repository_dispatch` 가 이미 있다. 이 결정은 '늦게 돌아도 비지 않게' 다.
- 앱키가 없을 때도 네이버로 간다(인증이 없으니 받을 수 있다). 사유 '앱키 없음' 은
  그대로 배너에 남는다.
- 점검 시간대의 폭(22~00시)은 실측 하나로 잡은 값이다. 다른 시각에 같은 증상이
  반복되면 `MAINT_HOURS` 를 고치거나 문구를 지운다. 추정을 사실로 승격하지 않는다.

### 검토에서 잡혀 같은 날 고친 것

- **투자자 구분이 없는 행을 '성공' 으로 셌다.** `flows.fetch_stock` 은 bizdate 만
  있으면 close·volume 만 든 행도 돌려주고, `_latest` 는 그걸 그대로 골랐다 — 네이버가
  키를 바꾸는 날 배너는 '폴백 N종목 성공', 텔레그램은 사유 없는 '수급 못 받음'
  N줄, `--check` 는 PASS 였다. 이제 `_latest` 는 구분이 하나라도 있는 행만 고르고,
  없으면 사유(받은 키)와 함께 종목 단위 실패로 간다(KIS 면 네이버 폴백, 네이버면
  failed). `fetch_stock` 은 어느 행에도 구분이 없으면 Fetch 를 올리고, `probe` 는
  FAIL 을 낸다.
- **`_latest` 가 기준일 뒤 날짜를 골랐다.** 지난 기준일을 다시 만들면(재발송·
  아카이브 복구) 8일 뒤 값을 '직전 영업일 값' 이라 적었다. 기준일 이하만 후보다.
  `NAVER_DAYS` 는 5 → 20 (그래야 재실행 창이 남는다). 배너는 실제 날짜를 괄호에 적는다.
- **`amt_est` 를 억원 소수 1자리에서 잘라 저장했다.** 1천만원 미만이 0.0/-0.0 이 되고
  텔레그램 `_eok` 는 `-0.0 >= 0` 을 참으로 봐 매도가 '+0만' 으로 나갔다. 4자리(만원)
  로 저장하고 -0.0 은 0.0 으로, 표기 함수 셋(`_eok`·`net_amt`·`netAmt`)은 0 에
  부호를 붙이지 않는다.
- **파일 머리의 `source` 가 항상 'kis' 였다.** 항목이 전부 네이버여도 그랬다.
  이제 실제로 쓴 소스 — 'kis' / 'naver' / 'mixed', 받은 값이 없으면 null (unit 규칙과
  같다).
- **`connect_failed` 의 'Timeout' 이 너무 넓었다.** `HTTP 504 · Gateway Timeout` 도
  접속 불가로 읽어 한 종목의 504 로 전 종목이 KIS 를 건너뛰었다. 상태코드가 있는
  실패는 제외하고 예외 이름을 정확히 나열한다. ReadTimeout 은 남기되 사유를
  '응답 시간 초과' 로 구분해 적는다.
- **배너 문장.** 접속 불가 앞에 KIS 로 받은 종목을 폴백 수에 섞어 '4종목 중 3종목
  성공' 이 됐고, 그 앞의 종목 단위 실패 → 네이버 대체 줄은 kis_down 이 서면 통째로
  빠졌다. '개인은 없습니다' 는 개인이 온 날에도 그렇게 적혀 텔레그램 줄과 모순됐다.
  셋 다 실제 수·실제 구분으로 적는다.
- **화면.** payload 는 `source`·`amt_est` 를 실었는데 app.js·render.py 가 둘 다 무시해
  네이버 값에 출처도 '추정' 도 없었다. 칸에 '(네이버)', 툴팁에 종가 환산 추정 금액을
  붙인다.

## D-084. 텔레그램 초안은 표를 빼지 않고 행마다 한 줄로 푼다

`draft_message` 가 draft.md 의 마크다운 표를 통째로 빼고 꼬리에 '표 N행은 모바일에서
읽히지 않아 뺐다' 만 적고 있었다. telegram.py 첫 단락('전체 표를 옮기지 않는다')과
PIPELINE.md 2장('매체가 잘하는 것만 준다', 일간 코멘트 = 요약 + 링크)을 초안에도
그대로 적용한 결과다.

초안은 랭킹과 성격이 다르다. 랭킹은 알림이라 3초에 읽히는 것만 남기는 게 맞지만,
17:15 초안은 **검수 대상**이다(CLAUDE.md 1장). `#기타 테마 (수치만)` 표는 스무 행까지
간다(`engine/facts.py`). 검수자가 그 표를 보려면 엑셀을 열어야 했고, 텔레그램만 보고
승인하면 그 스무 행은 검수를 건너뛴 채 18:00 에 나갔다. 검수 대상에서 내용을 고르면
검수할 것이 사라진다.

그래서 초안은 문단과 마찬가지로 표도 전부 보낸다. 표는 모바일 폭에서 읽히지 않으니
행마다 한 줄로 푼다 — `• 철강 +15.07% · 신고가 2 · 거래대금 1,234억`.

- 첫 칸은 행의 이름이라 열 이름을 안 붙이고, 나머지 칸은 열 이름을 앞에 적는다.
  헤더가 사라지면 '2' 가 무엇의 2인지 알 수 없다. 예외는 이름 옆의 등락률 하나 —
  이 레포는 어디서나 '이름 +x%' 로 적으므로(7장 문체·랭킹 줄) 그 자리는 이름 없이
  읽힌다. 둘째 칸이 신고가 종목수 같은 다른 열이면 이름을 단다.
- `–` 는 계산되지 않은 값의 표식이라 지우지 않는다(2장 1번·6번). 빈 칸만 뺀다.
- 헤더보다 칸이 많은 행은 넘친 칸을 이름 없이 싣고 표 끝에 그 사실을 한 줄 적는다.
- 길어지면 `send()` 가 줄 경계에서 나눠 보낸다. 한 화면에 맞추자고 본문을 깎지 않는다.

랭킹 메시지(`rankings_message`)는 그대로다 — 상위 5 · 하위 3, 교차 종목, 52주 이상
신고가만. telegram.py 모듈 docstring 을 랭킹·초안으로 갈라 적었고, PIPELINE.md 2장
표의 텔레그램 '일간 코멘트' 칸을 '전문' 으로 고쳤다.

## D-085. 종목별 트리거(재료) — 소스 넷, X 는 포워딩 인박스만, 링크 없이, 금지 문구는 기계로

2026-09-21 초안은 테마마다 "트리거는 확인되지 않음" · "테마 전체 상승 트리거로 단정하긴
어려움" 을 그대로 찍었고, 52주 이상 신고가 11종목 줄에는 재료가 한 줄도 없었다.
사용자 요구는 둘이다 — 그런 문장을 빼라, 검색 범위를 뉴스 기사와 트위터까지 넓혀
종목 줄에 붙여라.

### 왜 종목 단위인가

`news.py` 는 **테마** 단위다. 테마명과 거래대금 상위 종목 셋으로 묻는다. 신고가를 낸
종목은 대개 그 셋에 없고(2026-09-21 의 케이씨·비엠티·레이언스·지어소프트), 있어도
테마명 질의가 스친 기사를 앞에 세운다(D-044 의 문제). 그래서 신고가 종목의 재료는
따로 **그 종목 이름과 코드로** 묻는다. 대상은 `stockflows.targets` 와 같은 집합 —
고가·종가 어느 기준으로든 52주 이상. 60일까지는 넓히지 않는다(BACKLOG).

### 소스와 우선순위 — dart > telegram_x > naver_news > google_news

| 소스 | 무엇 | 확정한 사실 |
|---|---|---|
| DART `list.json` | 종목의 당일 공시 | **corp_code 로 종목별** 호출. 기존 `disclosures()` 는 `corp_cls='Y'`·1쪽이라 코스닥이 빠진다 — 고치지 않고 docstring 에 적었다. 접수 **시각**이 없어 '공시는 HH:MM 접수분까지' 로 적는다 |
| 텔레그램 인박스 | 사용자가 X 게시물을 봇에 공유한 것 | **X 를 무료·합법·자동으로 검색하는 길은 없다.** 공식 API 유료, Nitter·syndication 규약 위반·불안정, 쿠키 GraphQL 은 계정 정지 위험. 남는 것은 사람이 고른 포워딩뿐이다. 수집기(`tg_inbox.py` → `state/inbox.json`)는 별도 작업이고 여기서는 **읽기만** 한다. 파일이 없으면 '인박스 없음' 을 결손에 적는다 |
| 네이버 검색 API | 기사 | 기간 필터가 없어 `pubDate` 로 당일만. **매체명을 주지 않는다** — `originallink` 도메인이 매체고 표시명은 설정의 도메인 표(`finance_outlets`·`outlets`)로 바꾼다. `'{이름} 주가'` 질의는 자동 생성 시세 기사(topstarnews·joongangenews·job-post)를 맨 위로 끌어와 쓰지 않는다 — 기본은 `'{이름} {코드}'`·`'{이름} 신고가'` |
| Google News RSS | 기사 | 키 없는 비공식 경로. **러너에서 미검증** — 2차 소스로만 두고 실패는 결손으로 적되 단계를 막지 않는다. `--trigger-probe` 가 200·XML·한국어·5회 연속 내성을 찍는다 |

공시가 제일 확실하고, 포워딩은 사람이 골랐고, 뉴스는 잡음이 섞이므로 이 순서다.
종목당 셋(`per_stock_items`)을 우선순위 순으로 채우고 정규화 제목으로 중복을 뺀다.

### 채택 규칙 — 제목에서 본다

- 이름 다음 글자가 한글·영문·숫자면 불일치(케이씨 ≠ 케이씨텍·케이씨씨). 조사는 붙어도
  되되 그 뒤가 다시 어절 글자면 불일치(케이씨 ≠ 케이씨에스). 앞 글자도 같다.
- 유니버스에 그 이름을 접두로 갖는 더 긴 이름이 제목에 있으면 제외.
- 3자 이하·일반명사 이름(`generic_names`)은 제목에 이름이 있고 (요약에 주식어 or 매체가
  금융지)일 때만 채택 — '대상' 하나로는 기사가 종목 얘기인지 알 수 없다.
- 우선주는 `engine/kinds.of`(코드 끝자리 + 이름 접미 `\d?우[A-Z]?`)로 판정하고 접미를 뗀
  보통주로 묻고 `matched_by: pref_common`. 제목이 우선주 자체를 부르면('S-Oil우, 사상
  최고가') `pref_self`. 보통주가 없으면 `skipped: 우선주` 로 남긴다 — 조용히 빼지 않는다.
- **items 가 빈 종목은 결손이 아니다.** 그날 기사·공시가 없었다는 사실이다. 검색 범위
  ('질의당 상위 20건 · 당일만')는 `sources` 에 남긴다. 결손은 소스를 접은 것·예산
  초과·인박스 없음·공시 접수 시각 한계다.

### 시간 예산

전체 240초 데드라인 + 소스별 상한(네이버 90·구글 60·DART 60·인박스 20) + 호출 timeout
8초·재시도 1회. 소스가 접속 단계에서 실패하거나 401·403·429 면 그 소스를 접는다 —
D-083 이 KIS 에 쓴 패턴을 소스별로 쓴 것이다. DART 의 키·한도·IP·점검 status
(010·011·012·020·021·800·901)와 Google News 의 consent 페이지(200 + HTML, `gnews.parse`
의 'RSS 가 아니다' 류)도 다음 종목에서 똑같이 나므로 접는다. 종목 하나의 실패(013·
파싱·HTTP 5xx)는 그 종목만의 일이라 접지 않되, **소스별 'N/M 종목 조회 실패 (첫 사유)'
한 줄로 결손에 남긴다** — 카운트에만 두면 전 종목이 실패한 날도 '그날 공시 없음' 으로
읽힌다. 데드라인을 넘긴 종목은 `skipped: 시간 예산 초과` 로 남고 결손에 몇 종목인지
적힌다. `http.get` 에 `timeout` 인자를 뚫었다 — 25초 × 3회를 종목마다 기다릴 수 없다.

### 링크는 텔레그램에 넣지 않는다

4,096자에서 URL 하나가 종목 한 줄만큼 길고, 레거시 Markdown 은 괄호가 든 URL 에서
링크를 못 닫는다. 텔레그램 줄은 `↳ 재료: <제목 60자> (매체 · M/D)` · `↳ 공시: …
(DART · M/D)` · `↳ X: … (@계정 · M/D)` 종목당 두 줄까지. 링크는 대시보드 payload 의
`achieved[].trigger[].link` 로 가고 **실시간 보드(app.js)가 신고가 행 아래 재료 줄로
그린다** — 구운 HTML 은 툴팁뿐, 엑셀에는 재료 열이 없어 생략 안내는 '재료 전체는
대시보드에 있다' 라고만 적는다. 길이가 넘치면 **어느 구획보다 먼저, 뒤 종목의 재료
줄부터** 뺀다 — 그래서 구획의 항목을 종목 단위 엔트리로 들고 있다가 편다(`_drop_one`).
drop_rank 순으로만 고르면 섹터·교차 구획이 재료 줄보다 먼저 통째로 빠져 '등락률 Top
랭킹' 이라는 제목 아래 랭킹이 없었다. 재료는 대시보드에 있지만 종목·수급 줄은 여기서만
붙여 주는 것이라서다. 머리의 '공시는 HH:MM 접수분까지' 는 DART 를 실제로 부른 날
(`sources.dart.ok`)에만 붙고, X 포워딩은 인박스 창(`inbox_hours`)이라 '당일' 이 아니라
'최근 24시간' 으로 적는다.

### 금지 문구는 기계로 막는다

프롬프트의 규칙 3 이 "모르면 '트리거는 확인되지 않음' 이라고 적고 넘어가라" 였다 —
그 문장을 시킨 것은 우리였다. 규칙을 '모르면 트리거 문장을 아예 쓰지 마라' 로 바꿨고,
`verify.py` 에 `kind='phrase'` 검사를 넣었다: 어휘(트리거·재료·뉴스·호재·원인·촉매) +
조사 + 부정·미확인(없·미확인·불명·확인되지·부재·단정하긴·알 수 없). 그날 초안의 실제
문장 여섯이 전부 걸리고 '트리거는 DART 공시 — …' 는 안 걸린다. **예외는 문체 규칙이
요구하는 문장이다** — "단독 보도나 미확인 루머가 트리거면 그 사실을 함께 적는다"(STYLE
규칙 5). '재료는 미확인 루머 — X 포워딩의 지분 인수설'·'확인되지 않은 지분 인수설'
처럼 같은 절에 루머·보도·소식·풍문·~설 이 이어지면 통과시키고, 술어형('확인되지 않음'·
'트리거 미확인.')은 그대로 걸린다. compose 는 이 종류만
남으면 **한 번 더** 부르고, 그래도 남으면 그 문장만 지우고 '문장 N개 제거(금지 문구)'
를 결손에 적는다 — 종목명·수치 위조와 달리 이 문장은 지워도 없는 사실이 생기지
않으므로 초안 전체를 막지 않는다. 문장 경계가 마침표라 쉼표로 이어진 등락률·거래량이
같이 나갈 수 있어, 지운 문장에 `이름(값)` 짝이 있었으면 결손에 그 수를 따로 적는다.

같이 고친 것 둘. `FIELD_LEAK` 의 경계가 `\w`(유니코드)라 조사가 붙은
`stages_new_today가` 를 못 잡았다 — 그날 초안에 실제로 샜다. ASCII 경계로 고쳤다.
그리고 기사·재료 제목에 등장한 다른 상장 종목명은 검사 3(팩 밖 종목명)에서만
관용한다 — `이름(값)` 짝에는 여전히 팩의 종목만 허용되고, 중첩된 trigger 의 수치는
그 종목의 값으로 등록되지 않는다(`name` 키를 넣지 않는다). 관용은 **자리**로 본다:
제목 '한국전력기술, 웨스팅하우스 …' 의 '한국전력' 은 더 긴 유니버스 이름의 일부라
관용하지 않고(초안의 '한국전력도 동반 강세' 가 걸린다), '웨스팅하우스' 처럼 유니버스에
없는 낱말의 일부('웨스팅')는 관용한다. 검사 3 의 '더 긴 이름의 일부' 규칙도 같은
자리 기준이다. trigger 제목의 **수치**는 허용 집합에 넣지 않는다(`NUMBER_SKIP_KEYS`) —
프롬프트가 옮기지 말라는 것을 검사 2 도 막는다. 테마 `news` 제목의 수치는 예전대로다.

### 산출과 소비자

`state/<asof>/triggers.json` — `by_code.{code}.items[{title, link, publisher,
published_at, source, kind?, matched_by, query?}]`, `sources.{소스}.{ok, failed, skipped,
cut, error, scope}`(error 는 접지 않은 종목 단위 실패의 첫 사유), `missing[]`,
`collected_at`, `inbox_hours`. **단계가 예외로 죽어도 파일은 남긴다** (sources 전부
failed + missing 한 줄 + `failed` 키 — 텔레그램은 이 파일에 재료 머리를 붙이지 않는다).
파일이 없으면 사실 팩·텔레그램·payload·구운 HTML(render.from_state 도 `TR.load`) 네
소비자가 같은 문장 '재료: 수집되지 않음(단계 실패)' 을 결손에 넣는다(`triggers.load`).
배너 합류는 `render.notices(…, triggers)` 한 곳이다.
사실 팩은 종목마다 `trigger=[{title, publisher, date, source, kind}]` 를 붙이고, 테마
결손 조건은 '테마 news 도 종목 trigger 도 없을 때' 다.

### 검토에서 잡혀 같은 날 고친 것

- **종목 단위 실패가 결손에 없었다.** DART 020(일 한도)·010(키 무효), 네이버 5xx,
  Google consent 페이지는 `cut_reason` 이 None 이라 종목마다 `failed` 에만 쌓였고 세
  소비자는 `missing` 만 읽는다 — 전 종목이 실패한 날도 '그날 공시 없음' 으로 읽혔다.
  DART status·consent 는 소스 컷으로, 나머지는 `_finish` 가 'N/M 종목 조회 실패 (첫
  사유)' 로 적는다.
- **텔레그램 머리가 안 본 공시를 봤다고 했다.** `failed()` 파일·DART 를 접은 날에도
  '공시는 HH:MM 접수분까지' 가 붙어 결손 줄과 모순됐다. `sources.dart.ok` 일 때만,
  `failed` 파일에는 재료 머리 자체를 안 붙인다. 'X 포워딩' 은 '최근 24시간' 으로.
- **우선주 판정이 이름만 `우[BC]?$` 로 봤다.** '현대차2우B' 의 보통주를 '현대차2' 로
  찾아 못 찾았고, 끝이 '우' 인 보통주를 우선주로 오판할 수 있었다. `engine/kinds.of`
  + `common_name`. 우선주 자체를 부른 기사('S-Oil우, 사상 최고가')는 보통주 이름
  경계와 접두 제외에 이중으로 걸려 절대 채택되지 않았다 — `pref_self`.
- **`_fit` 이 재료 줄보다 섹터 랭킹을 먼저 버렸다.** 위 '링크는 텔레그램에 넣지 않는다'.
- **PHRASE 가 규칙 5 의 문장을 지웠다.** 위 '금지 문구는 기계로 막는다'.
- **`mentioned_names` 가 부분 문자열이었다.** 위 '같이 고친 것'.
- **'전체는 대시보드와 엑셀에 있다' 가 사실이 아니었다.** app.js 가 `achieved[].trigger`
  를 안 그렸고 엑셀에는 열이 없다. app.js 에 재료 줄을 넣고 생략 안내는 있는 곳만 적는다.
- **구운 HTML 배너에 재료 결손이 없었다.** render.from_state 가 `read()` 로 읽어 파일
  없으면 None, notices 가 triggers 를 합치지 않았다. payload 와 같은 입력·같은 합류.

돌면 매번 난다.

**창을 100건으로 넓혀 봤고, 안 됐다.** 다음 실행(09:28)에서 11종목 × 2질의로
**2,124건**을 받아 **한 건도** 기준일 기사가 아니었다. 큰 응답을 스물두 번 받아

자동 생성도 아니지만 그날 주가의 재료는 아니다. 제목만으로는 가릴 수 없어 두었다.

## D-086. 텔레그램 인박스 — X 게시물은 사용자가 봇에 공유하고, 봇이 getUpdates 로 읽는다

CLAUDE.md 3장 state 목록에 `state/inbox.json`(루트) 을 넣은 근거다. 계약은 여기 산다 —
모듈 docstring 은 이 항목을 옮겨 적은 것이고, 바꿔야 하면 여기에 먼저 적는다.

**X 를 무료·합법·자동으로 검색하는 길이 없다.** 공식 API 는 유료이고 스크래핑은 규약
위반이다. 유일한 길은 **사용자가 X 앱에서 게시물 → 공유 → Telegram → 보드 봇**으로
넘기고, 봇이 `getUpdates` 로 그 대화를 읽는 것이다. 검색·스크래핑은 하지 않는다.
외부 호출은 공식 oEmbed(`publish.twitter.com/oembed`, 인증 없음) 하나만 더 쓰고,
그것도 본문이 URL 뿐일 때 게시물 본문·작성자를 채우는 데만 쓴다. t.co 는 풀지 않는다.

### 파일과 필드

`state/inbox.json` 은 **날짜 디렉터리가 아니라 state 루트**다. 날짜별 산출이 아니라
'최근 14일치가 쌓이는 것' 이고, Actions 캐시 `board/state` 에 실려 실행 사이에 남는다.
offset 은 `state/.inbox_offset.json` 으로 **따로** 둔다 — inbox.json 안에 두면 소비자가
그 파일을 고쳐 쓸 때 잃는다.

    {"source":"telegram","updated_at":"<KST ISO>","chat_ids":[…],
     "items":[{"update_id":int,"chat_id":int,"date":"<KST ISO>","text":str,
               "urls":[str],"x_ids":[str],"author":str|null,
               "kind":"x"|"other","text_via":"message"|"oembed"|null}]}

- `update_id` 로 중복 제거. `settings.yaml inbox.keep_days`(14) 가 지난 항목은 버린다.
- `kind:'x'` = x.com / twitter.com / t.co 링크가 있는 메시지. `x_ids` 는 `/status/<id>` 의
  id — x.com·twitter.com 링크에서만 뽑는다(`i/status`·`i/web/status` 포함).
- `author` 우선순위는 **링크 계정 → oEmbed 작성자 → forward_origin 이름**. 전달자
  (텔레그램 채널·사람)는 게시물을 쓴 사람이 아니라 맨 뒤다 — 앞에 두면 X 게시물을
  텔레그램 채널이 쓴 것처럼 보인다(출처 오기).
- `text` 는 메시지 본문(캡션 포함). URL 뿐이면 oEmbed 로 채우고 `text_via:'oembed'`,
  실패하면 URL 그대로 두고 `text_via:null` — **지어내지 않는다**(2장 1번).
- 일반 메시지도 `kind:'other'` 로 남긴다. 무엇을 붙일지는 소비자가 정한다 — 수집기가
  미리 거르면 왜 안 붙었는지 알 길이 없다.

### 순서 — 페이지마다 디스크가 먼저다

텔레그램은 갱신을 서버에 **24시간**만 두고, 더 큰 offset 으로 부르는 순간 앞 갱신을
지운다. 그래서 페이지를 받을 때마다 다음 호출 전에 inbox.json 에 먼저 쓰고 offset
파일은 그 뒤에 갱신한다. 둘 사이에서 죽으면 같은 페이지를 한 번 더 받지만 중복
제거가 흡수한다. 반대 순서면 받았다고 확인한 갱신이 디스크에 없다.

같은 이유로 24시간 안에 실행이 한 번은 있어야 한다. 평일은 daily 와 파일 발송
재시도가 맨 앞에서 읽고, 주말은 인박스 크론이 하루 **두 번**(09:23·20:23 KST) 읽는다.
한 번(21:23)으로는 금 20:23 → 토 21:23 이 25시간이라 창을 넘겼다. 그래도 크론이
큐에 밀린 만큼은 잃을 수 있다 — 크론은 제때를 보장하지 않는다(8장).

손상된 inbox.json 은 삼키지 않는다. `inbox.json.bad` 로 옮기고 사유를 로그에 적은
뒤 빈 것에서 시작한다 — 멈추면 새 갱신까지 24시간 뒤에 사라지고, 조용히 덮어쓰면
14일치가 로그 한 줄 없이 사라진다(2장 6번). 옛 항목은 `.bad` 에 남는다.

### 소비자

같은 날 D-085 의 트리거 단계(`ingest/triggers.py`)가 붙었다. `state/inbox.json` 을 읽어
본문에서 종목명·코드를 찾고, 그 종목이 52주 이상 신고가면 `source: telegram_x` 항목으로
`triggers.json` 에 넣는다. 텔레그램 줄은 `↳ X: <본문 60자> (@계정 · M/D)`, 시간 창은
`triggers.inbox_hours`(24시간). 이 결정과 D-085 는 같은 워크트리에서 따로 만들어져
번호가 겹쳤고, 머지하며 이쪽을 D-086 으로 옮겼다.

## D-NEXT-C. X 다이제스트 수집원을 블루스카이로 바꾼다

`XDIGEST.md` 3-1 은 (a) 텔레그램 공유 경로로 적혀 있었다. 그 경로를 쓰지 않는다.

- 사용자가 손 공유를 하지 않기로 했다(8장 9번 답).
- 대신 정한 (b) 계정 타임라인은 2026-09-22 러너 실측에서 **아홉 경로가 전부
  실패**했다. `xcancel.com` 은 HTTP **451 Unavailable For Legal Reasons** 였다 —
  법적 이유로만 쓰는 상태코드다. 규약 위반을 수용하느냐와 무관하게 **위반할

- 같은 프로브에서 블루스카이 `app.bsky.feed.searchPosts` 는 HTTP 200 JSON 25건을
  줬다. **인증 없이 공개 데이터를 주는 것이 AT Protocol 의 설계**라 규약 위반이
  아니고 키·계정·비용이 없다. 로그인하지 않으므로 계정 위험도 없다.

그래서 `ingest/bsky.py` · `config/xdigest.yaml` · `--xdigest-collect` 로
구현하고 3-1 절을 블루스카이 기준으로 다시 썼다. 1장 계약(구획·기호·분할)과
4~7장은 그대로 쓴다.

바뀐 규칙 넷.

1. **창·기준일을 `posted_at` 으로 정한다.** (a) 는 `forwarded_at`(공유 시각)
   이었다. 이 경로에는 그 값이 없다 — 아무도 공유하지 않고 코드가 검색해 받는다.
   뜻도 다르다: (a) 는 "사용자가 오늘 공유한 것", (b') 는 "지난 24시간에 올라온
   것" 이다. 그래서 `(게시 9/18)` 표기도 이 경로에는 나오지 않는다.
2. **창 밖은 버리지 않고 `in_window: false` 로 남긴다.** 검색은 타임라인을 훑는
   것이라 창 밖이 섞여 온다. 버리면 "왜 그 글이 안 실렸나" 를 파일에서 확인할
   길이 없다.
3. **`└` 출처는 블루스카이 핸들이다.** X 핸들을 적지 않는다 — 그 계정이 X 의
   누구인지 코드가 아는 길이 없다.
4. **계정별 수집은 없다.** 예시 12계정 중 10개가 블루스카이에 없고, 있는 둘도
   팔로워 0·35 라 그 사람의 계정으로 볼 수 없다. `getAuthorFeed` 를 부르지
   않고 `■ <계정>의 24시간 인사이트` 구획도 없다(8장 12번).

질의는 `[HBM, semiconductor, DRAM, TSMC]` 넷이다. 실측 24시간 물량은
semiconductor 99 · foundry 94 · DRAM 64 · TSMC 33 · AI datacenter 29 ·
SK hynix 24 · HBM 20(합 363, 중복 포함)이다. **물량 2위인 foundry 를 빼고
물량 최하위인 HBM 을 넣었다** — 예시의 `■ 공통 테마` 첫 소주제와 삼성 HBM4
증산 항목이 그 말로 걸리는 것들이라, 물량 순으로만 고르면 다이제스트의 중심
주제가 빠진다. 일곱을 다 쓰지 않는 이유는 호출 한도다.

검색 호스트는 `api.bsky.app` 이 먼저고 막히면 `public.api.bsky.app` 으로 한 번
더 본다. 실측에서 `public` 쪽 `searchPosts` 만 403 + HTML 이었고 같은 호스트의
`getProfile` 은 200 JSON 이었다 — **엔드포인트별로 열린 호스트가 다른 것**이지
IP 차단이 아니다. 한 호스트로 뭉쳐 두면 검색이 조용히 0건이 된다.

`board/.gitignore` 의 `state/*/` 에 `!state/xdigest/` 예외를 넣었다. 이 경로는
state 캐시를 복원하지 않는 별도 워크플로가 돌리므로(`XDIGEST.md` 3·4장) 보관처가
캐시가 아니라 커밋이다.

### 검토 뒤 고친 것 — 판정에 쓰는 값을 따로 둔다 (스트림 C)

리뷰에서 나온 것 중 계약이 바뀐 자리 둘이다.

1. **`sources.bluesky.failed` 를 더했다.** 워크플로의 '전부 실패' 판정이
   `len(errors) >= queries` 였는데, `errors` 에는 질의별 실패 줄 말고 파싱에서
   뺀 건수 줄도 들어간다. 질의 하나가 200 으로 받아 온 응답에 `record.text` 없는
   항목이 한 건만 섞이면 줄 수가 질의 수에 닿아 **수집이 된 날도 exit 1 · '질의가
   전부 실패했다'** 가 됐다(단일 질의 설정이면 완전 성공한 날에도 그렇다). 로그
   문장이 사실이 아니어서 `CLAUDE.md` 2장 1번에도 걸렸다. 판정은 `failed`
   (200 JSON 을 못 받은 질의 수)로 하고 `errors` 는 사람이 읽는 사유 목록으로
   둔다 — 길이를 세지 않는다.
2. **창의 끝을 배타로 바꿨다**(`start <= posted_at < end`). 양끝 포함이면 창이
   24시간 + 1초이고 08:45:00 정각 게시물이 D·D+1 두 창에 동시에 들어 이틀 연속
   본문에 실린다 — `XDIGEST.md` 10장 T5 의 '중복 0' 과 모순이었다. 계약 3-1 의
   문장도 함께 고쳤다.

나머지 넷은 구현만 바뀌었다. `blocked` 를 누적 플래그가 아니라 호스트별 판정의
AND 로 계산한다(한 호스트만 403 이면 막힘이 아니다 — 전송 오류를 '막힘' 으로
라벨하지 않는다). 폴백 호스트가 받아 준 날도 앞 호스트의 429·403 사유를
`errors` 에 남긴다(받았으므로 `gaps` 에는 넣지 않는다). `parse` 는 핸들 없는
항목과 빈 `text` 를 뺀다(빈 출처·null 링크가 창 안 건수에 들어가면 안 된다).
`coverage.gaps` 에는 결손만 넣고 파싱 드롭·폴백 사유는 `errors` 몫으로 둔다 —
머리 3행이 gaps 에서 만들어지므로 정상적인 날의 발송문에 파서 내부 문구가
나가면 안 된다.

`--check` 프로브도 고쳤다. 판정을 '24시간 안 건수가 있는가' 에서 **'200 JSON 을
받았는가'** 로 바꾸고, 누르는 질의를 `probe_query`(기본 semiconductor · 실측
물량 1위)로 뺐다. HBM 은 24시간 20건이라 평균 72분에 1건이고, 새벽에 누르면
경로가 멀쩡한데도 0건이 나와 막힌 날과 같은 빨강이 됐다 — 이 경로가 경계하는
'막힌 것과 없는 것 섞기' 를 진단 쪽에서 저지르고 있었다.

## D-NEXT-A. claude.py 인자 확장 — 기본값은 그대로

`writer/claude.py` 의 세 함수에 인자를 더했다. `XDIGEST.md` 3-2 가 계약에 적어 둔
변경이고, 착수하며 그대로 넣었다.

```
ask(..., max_tokens=None, model=None)                    None 이면 예전 값 (narrate · 8000)
ask_many(..., schema=None, model=None, max_tokens=None)  ask 로 통과
ask_json(..., max_tokens=None, model=None)               None 이면 예전 값 (4000)
```

**왜 필요했나.** 셋 다 다이제스트 분석(`xdigest/analyze.py`)이 막힌 자리다.

- `ask()` 가 `model=m['narrate']` 고정이라 ① 배정을 Haiku(`models.cluster`)로
  돌릴 수 없었다. ① 은 게시물 전부를 한 번에 읽는 호출이라 모델이 곧 비용이다.
- `ask_many()` 가 `schema` 를 넘기지 않아 병렬 호출에 JSON 스키마를 강제할 수
  없었다. ② 는 소주제 8개를 병렬로 부르고 전부 스키마 응답이어야 한다.
- `ask_json()` 이 `max_tokens=4000` 고정이었다. ① 은 게시물 150건의 배정을
  돌려주므로 4000 에서 잘리고, 잘리면 `json.loads` 가 터져 3-6 의 '분석 실패'
  경로로 빠진다 — **매일 사실 없는 빈 다이제스트가 나갈 수 있었다.** 지금은
  건수에 비례해 `1,000 + 30 × 건수` 로 잡는다(3-2).

**기본값 불변.** 인자를 안 주면 예전과 같은 값이라 보드 호출(`writer/compose.py`
의 `ask` · `extract_claims` 의 `ask_json`)은 한 글자도 달라지지 않는다. 상한을
`ASK_MAX_TOKENS`(8000) · `JSON_MAX_TOKENS`(4000) 상수로 빼 두었고,
`tests/test_xdigest_analyze.ClaudeDefaults` 가 모델·상한·`output_config` 부재를
값으로 확인한다. `config/settings.yaml` 의 `writer.max_tokens`(16000)는 예전처럼
코드가 읽지 않는다 — 이 변경으로 조용히 읽기 시작하면 보드 동작이 달라진다.

## D-NEXT-A2. ① 배정 호출의 게시물 키는 AT-URI 가 아니라 `p001`

`XDIGEST.md` 3-2 표는 ① 의 입출력을 게시물 `id` 로 적었다. 수집원이 블루스카이로
바뀌면서 그 `id` 가 **AT-URI**(`at://did:plc:…/app.bsky.feed.post/…`, 60자 남짓)가
됐다 — 3-2 의 토큰 계산(`1,000 + 30 × 건수`)은 19자리 X id 를 전제한 값이다.

그래서 프롬프트에서만 `p001` 꼴 짧은 키를 쓰고, 코드가 키↔AT-URI 를 되돌린다.
저장되는 `themes.json` · `facts.json` 에는 **AT-URI 만** 들어간다.

- 출력이 4~5배 짧아진다. 잘림은 D-NEXT-A 가 고친 그 사고다.
- 모르는 키는 그 자리에서 버려진다(`_apply`). AT-URI 를 모델이 한 글자 고쳐
  돌려주면 실재하는 다른 게시물을 가리킬 수 있는데, 짧은 키는 그럴 여지가 없다.
- 단위마다 키를 다시 매긴다(②③ 은 그 소주제 안에서 `p001` 부터). 단위 밖 게시물을
  가리킬 수 없으므로 3-3 6번("그 단위에 배정된 id")이 구조로 지켜진다.

3-2 표의 '입력 (id · account · text)' 한 줄은 머지할 때 이 결정에 맞춰 고친다.
① 출력의 `focus` 도 스키마에서 빼 두었다 — ⑤ 계정 인사이트는 대상 계정이 없어
만들지 않기로 했고(8장 12번), 쓰지 않을 배정을 모델에 요구할 이유가 없다.

## D-NEXT-A3. 다이제스트 검증 사전은 `xdigest_names.yaml` 커밋 파일

`knowledge/xdigest_names.yaml` 을 새로 뒀다. 표제어(우리말 종목명)마다 코드와
별칭(영문명·약칭·한글 변형·코드)을 적은 커밋 파일이다. 근거는 3-3 4번 그대로 —
`state/*/universe.json` 은 보드 실행이 만드는 캐시 산출물이고 `state/*/` 는
`.gitignore` 라, 캐시를 복원하지 않는 다이제스트 워크플로에는 어느 날도 없다.
휴장일에는 보드도 만들지 않는다.

초안은 반도체·AI 밸류체인 36종목이었다. **근거를 `sector_map.yaml` 의 `why`
문장으로 적은 것은 틀렸다** — 그 파일은 코드→섹터 표이고 `why` 문장에 회사 이름이
없는 항목이 36종목 중 19건이었다(예: 042700 → 'KSIC 29271은 반도체 제조 장비·
서비스로 테스트·후공정 추정', 098460 → 'KSIC 29271은 전기배분장치 제조'). 즉 그
19건의 이름↔코드 짝은 레포 안에 근거가 없었고, 렌더가 표제어 뒤에 6자리 코드를
사실처럼 붙이므로 한 건만 틀려도 지어낸 식별자가 다이제스트에 실린다(2장 1·4번).
이 문장은 2026-09-22 에 D-NEXT-A4 로 고쳤다.

대조는 NFKC·공백 제거·소문자 뒤 부분 문자열이다. 짧은 별칭을 관용 쪽에 두었던 것도
D-NEXT-A4 에서 되돌렸다 — 관용의 결과로 **틀린 종목코드가 붙는다**.

## D-NEXT-A4. 다이제스트 검증·분석의 검토 반영 — 수치는 토큰 집합으로 본다

2026-09-22 검토(findings 21건)를 반영했다. 고친 것과 이유만 적는다.

### 1. 수치 검증을 부분 문자열에서 **토큰 집합**으로 (`xdigest/verify.py`)

3-3 1번을 '정규화 후 부분 문자열' 로 적은 것이 화근이었다. 실측으로 통과했던 줄:

```
원문  August HBM average export price $73.39, index 6,808.21, capex $80.4B.
통과  '단가 $73.3 로 하락'    (절단)
통과  '지수 6,808.2 로 마감'   (절단)
통과  '캐펙스 $80.4 로 제시'   (단위 탈락 — 10억 배)
원문  Micron posted record revenue of $46.7B
통과  '매출 $46.7M 기록함'     (자릿수 스왑 — NUM 의 `$…` 갈래가 단위를 먹었다)
```

베끼겠다고 한 `writer/verify.allowed_numbers` 는 처음부터 **집합**으로 봤다
('73.3' not in {'73.39'}). 같은 방식으로 맞췄다.

- 토큰은 `(부호, 숫자, 단위 반열)`. 쉼표는 지우고 소수점은 남긴다. `+` 는 버리고
  `-` 는 남긴다(부호 뒤집힘은 다른 사실이다). `$` 는 버린다(자릿수를 바꾸지 않음).
- 자릿수를 바꾸는 단위는 반열이 다르다 — `M`↔`만` 은 환산이라 위반, `million`↔`M`
  은 표기 차이라 같은 반열. `만`·`천`·`bn`·`mn`·`tn`·`k`·`million`·`billion`·
  `trillion` 을 단위 목록에 더했다.
- `년`·`개월`·`장`·`대`·`건`·`개` 는 자릿수를 바꾸지 않아 단위 없는 수치와 같은
  반열이다. 원문 `2030` 을 `2030년` 으로 적는 것은 환산이 아니다.
- **원문 쪽만 넓게 뽑는다** — 단위 없는 정수(`2030`)와 영어 수사(`five months`)까지.
  위반 판정은 출력 쪽 토큰으로만 하므로, 대조 대상을 넓히면 원문을 그대로 옮긴 줄이
  오탐으로 빠지지 않고 원문에 없는 수치는 넓게 뽑아도 생기지 않는다. 그래서 지어낸
  연도(`2030` → `2031년`)와 환산(`3 million` → `300만`)이 이제 걸린다.

계약 3-3 1번의 '부분 문자열' 문언도 함께 고쳤다. 1장 문체("`+3.6%` 를 `약 4%` 로
바꾸지 않는다")를 기계로 막지 못하는 문언이었다.

### 3. 막힌 것과 틀린 것을 섞지 않는다 (`xdigest/analyze.py`)

- ④ 를 부르지 않은 사유도 '사실 줄이 없음' 과 '②③ 이 막힘' 을 가른다.

### 4. 상한을 적용한 뒤에 소주제 자격을 본다

`unit_ok`(3-3 8번)를 사실 줄 상한 5 보다 **먼저** 부르고 있었다. 잘려 나간 줄이
유일하게 대던 계정이 함께 빠지면 출처 계정 1개짜리 `▸` 소주제가 살아남는다(실측:
7건 중 5건만 남아 `└ @a.bsky.social` 하나). 순서를 상한 → 계정 재계산 → 판정으로
바꿨다. 소주제 순서도 검증이 끝난 뒤 남은 줄로 다시 잡는다(계약 1장 표). 키
(`t1`·`t2`…)는 `verify.json` 의 단위 이름과 짝이라 배정 순서 그대로 둔다.

### 5. ① 출력이 잘렸을 때 상한을 올려 다시 부른다 (`writer/claude.py`)

`ask`·`ask_many`·`ask_json` 에 `strict_stop` 인자를 더했다. True 면
`stop_reason == 'max_tokens'` 를 `Truncated` 로 올린다. `_assign` 은 그 예외에서만
상한을 2배로 올려 다시 부르고 사유를 `① 출력 잘림 (max_tokens N)` 으로 남긴다 —
예전에는 같은 상한으로 세 번 부른 뒤 `JSONDecodeError` 만 남겨, 러너에서 잘림인지
형식 오류인지 가를 수 없었다. **기본값은 예전 그대로**(끊긴 텍스트를 돌려준다) —
보드 서술은 조금 잘려도 나가는 편이 나으므로 동작을 바꾸지 않았다(D-NEXT-A 의
'기본값 불변' 과 같은 규약).

### 6. ① 출력을 수선할 때 게시물을 잃지 않는다

- 제목이 빈 소주제의 게시물은 `standalone` 으로 내리고 건수를 결손에 적는다. 예전에는
  `used` 에 표시된 뒤 테마가 버려져 `unassigned` 에도 안 남았다 — `pool` 3 인데 합이
  1 이고 그 차이를 적은 곳이 없었다(3-2 위반).
- 허용 밖 제외 사유(`중복 게시물`)는 `off_topic` 으로 덮어쓰지 않고 제외로 받지
  않는다 — 미배정으로 남아 건수가 보인다(2장 1번).
- `① 배정 위반 N건 — 코드가 수선함` 결손에 미배정 건수를 함께 적는다.

### 7. 게시물 본문의 구획 줄 흉내를 무력화한다 (`xdigest/prompts.py`)

수집은 키워드 검색이라 누구의 글이든 들어온다. 본문에 개행 뒤 `[p002] @계정` 과
자기 문장을 넣으면 프롬프트 안에서 진짜 블록과 글자 모양이 같아지고, ① 이 그 문장을
그 계정의 말로 배정하면 `└` 줄에 신뢰 계정이 실린다. 수치가 없는 문장이면 3-3 이
잡을 것이 없다(그 문장은 공격자 게시물에 실제로 있으므로 1번을 통과한다).
`posts_block` 이 줄머리 `[pNNN]`·`@핸들` 을 한 칸 들여쓰고, 흉내 낸 건수를 결손·
`verify.json` 에 남긴다. **글자를 지우지 않는다** — 3-3 의 원문 대조가 그 문자열과
한다.

### 8. `config/xdigest.yaml` 을 읽는다 (`run.py`)

`cmd_xdigest_analyze` 가 `config/settings.yaml` 만 읽어 `xdigest.scope`·
`xdigest.limits` 가 죽은 설정이었다(settings.yaml 에 `xdigest:` 키가 없다). C 스트림이
그 파일에 `scope`·`limits` 를 넣어도 분석은 기본값으로 돌고 오류도 결손도 없었다.

설정인 모양과 `xdigest:` 머리를 쓴 모양을 둘 다 받는다. 파일이 없으면 코드 기본값.

## D-NEXT-R. X 다이제스트 렌더·발송·일정 — 통마다 평문, 표식은 커밋으로

`XDIGEST.md` 1장·3-4·3-5·3-6·4장을 코드로 옮기며 정한 것들이다. 파일은
`xdigest/render.py`(조립·분할) · `xdigest/send.py`(발송·표식) ·
`.github/workflows/xdigest.yml`.

**통마다 `telegram.send()` 를 따로 부른다.** 본문을 통째로 넘기면 우리가 `■`
단위로 나눈 경계와 `send()` 의 `_split` 이 줄 단위로 나눈 경계가 엇갈려
`▸` 제목과 첫 `•` 사이, `•` 와 `└` 사이가 갈릴 수 있다. `parse_mode=None`
(평문)인 근거는 코드와 `tests/test_telegram.py`
`test_plain_mode_sends_no_parse_mode` 다 — `send()` 의 docstring 은 낡았고
미국장 발송은 실제로 `HTML` 이다(1장 '파스 모드'). `telegram.py` 는 고치지
않았다.

**나누는 입력은 `digest.txt` 하나다.** `split(text)` 가 본문을 다시 읽어 통을
만든다. 발송 재시도는 다시 렌더하지 않고 같은 규칙으로 같은 목록을 얻어야
`sent.json` 의 통 번호가 뜻을 갖는다(3-5). 그래서 렌더는 통 목록을 상태로
들고 있지 않다.

**`message_id` 는 `sent.json` 에 적지 않는다.** `telegram.send()` 가
`(ok, 사유)` 만 돌려주고 그 파일은 다른 경로가 쓰는 것이라 고치지 않았다 —
3-5 가 적은 세 값 중 우리가 아는 것은 통수와 시각뿐이고, 모르는 값을 지어내지
않는다(2장 1번).

**T4 허용 차이에 한 줄을 보탰다(7장 10번).** 1장 소주제 정렬(출처 계정 수
내림차순 → 게시물 수)을 예시에 적용하면 예시의 소주제 순서와 다르다 — 예시
8개 중 1·4번째만 계정 4개다. 예시 순서는 사람이 쓴 것이고, 정렬은 코드가 하는
일이라 규칙을 예시에 맞춰 비틀지 않았다. 대신 `test_example_diff_is_zero` 는
순서를 빼고 **어느 줄이 나가고 어느 줄이 빠졌나**만 보고, 순서는 따로 시험한다.

**state 커밋은 `if: always()` 이고 `git add -f` 다.** 실패한 실행도
`sent.json` 을 남겨야 다음 `send` 가 몇 통까지 갔는지 안다(3-5). `board.yml`
'결과 커밋' 의 `if: success()` 와 다른 이유가 그것이다. `-f` 는
`board/.gitignore` 의 `state/*/` 가 이 디렉터리를 통째로 빼기 때문인데,
그 파일은 이 경로가 고칠 파일이 아니라 워크플로에서만 강제했다.

**아티팩트 업로드 단계를 두지 않는다.** 계정 저장 한도를 넘겨 어떤 업로드도
통과하지 못한다(0장). 대신 `digest.txt` 앞 40줄과 `verify.json`·`sent.json` 을
`$GITHUB_STEP_SUMMARY` 에 찍어 텔레그램 없이도 런 페이지에서 읽히게 했다.

**크론은 뒤받침이다.** `'23 1 * * *'` · `'23 3 * * *'` 두 줄을 두되 정시는
외부 스케줄러가 `repository_dispatch`(`xdigest-daily` 23:45 UTC ·
`xdigest-send` 00:15 UTC)로 맞춘다 — GitHub 크론은 이 계정에서 다섯 시간씩
밀렸다(`GITHUB.md` 5-2 실측표). 5-2 의 `event_type` 표에 두 줄을 보탰다.

**재시도는 통 번호가 아니라 통 목록의 지문을 믿는다.** `sent.json` 에
`fingerprint`(통마다 길이+본문의 sha256 앞 16자)를 함께 적고, `done()` 은 그것이
지금 통 목록과 같을 때만 '앞 실행에서 보냈다' 로 건너뛴다. 번호만 믿던 앞 판에는
조용히 아무것도 안 나가는 경로가 있었다 — 부분 발송으로 끝난 날 크론 `daily` 가
다시 렌더해 통이 3→1 로 줄면, 새 1통이 `n=1` 이라 건너뛰어지고 보낸 통이 0인데
`ok` 가 참이 되어 표식까지 찍혔다(실측: 보낸 통 0 · ok True · 표식 True). 지문이
다르면 재시도가 아니라 새 발송이라 1통부터 보낸다 — 1통을 두 번 받는 편이 하나도
못 받는 것보다 낫다(3-5). 지문이 없는 낡은 `sent.json` 도 '다르다' 로 본다.
'이번 실행이 보낸 통 0' 을 실패로 만들지는 않았다. 지문이 같은 기록으로 전부
보낸 재시도(표식만 못 남긴 날)가 그 모양이라 실패로 두면 그날 표식이 영영 안
찍힌다. 대신 `sent_now` 를 적고 사유를 로그에 남긴다.

**자동 경로는 표식을 보고 갈린다.** `daily` 가 표식을 보지 않고 늘
collect→analyze→render 를 돌면 4장 '중복 방지' 표 1행을 어긴다 — 하루 Claude
호출이 1회가 아니라 3회가 되어 5장 비용표가 깨지고, **이미 보낸 digest.txt 를
새 내용으로 덮어** 커밋에 남은 본문이 실제 발송본과 달라진다(7장 완료 기준 3번의
사후 대조가 불가능해진다). 워크플로에 '표식 확인' 단계를 두고 `--once` 가 붙은
실행에서만 본다: 표식이 오늘이면 수집만, 표식이 없고 오늘 `sent.json` 이 있으면
재렌더 없이 `send` 만.

**`repository_dispatch.types` 에 `xdigest-collect` 를 보태고 모드 결정을 `case`
로 바꿨다.** `types` 에 없는 `event_type` 은 GitHub 가 204 를 주면서 아무 일도
하지 않아, 6장 6번이 등록하라는 20:45 중간 수집이 실패도 로그도 없이 안 돌았다.
반대로 타입만 보태면 `[ … ] = xdigest-send && MODE=send || MODE=daily` 가 그것을
`daily` 로 떨어뜨려 20:45 에 창이 반만 찬 판을 발송하고 표식까지 찍는다. 이름이

이면 로그 한 줄 없이 체크아웃 시점의 값으로 판단해 들어가, 그 사이 `daily` 가

보내는 편이 두 번 보내는 것보다 낫다.

**`actions/cache/restore` 단계를 지웠다.** `xdigest-state-` 접두사를 저장하는
워크플로가 없어(board.yml·us-board.yml 은 `board-db-v<N>-`) 첫 실행부터 늘
미스였는데 주석은 'board.yml 과 같은 캐시를 읽는다' 고 단정했다. 실제 보장은
커밋뿐이라 그 한 줄만 남겼다(2장 1번 — 추정을 단정으로 적지 않는다).

**모델이 준 문자열은 줄에 넣기 전에 한 줄로 누른다.** 수집원이 블루스카이 키워드

## D-NEXT-X. 블루스카이 호출은 한 벌이다 — 실측과 수집이 같은 문을 쓴다

사용자가 "코드를 실행하고 API를 직접 호출할 수 있는 에이전트에는 기존 API를 다시
감싼 MCP 서버가 불필요하다"는 논리로 코드 전체를 보라고 했다(2026-09-22).

### 1. 이 저장소에는 MCP 가 없다

실측: `mcp` / `MCP` / `modelcontextprotocol` 을 `*.py *.yml *.yaml *.json *.md`
전부에서 찾아 **0건**이다. `.mcp.json` 없음, `fastmcp` 없음. Anthropic 호출
(`writer/claude.py`)에 `tools=` · `tool_choice` 도 0건이라 모델에 스키마를 실어
보내는 경로 자체가 없다. 외부 호출은 전부 `ingest/http.py` 를 거치는 직접
HTTP 다. `web/serve.py` 는 API 재포장이 아니라 `file://` 의 CORS 때문에 두는
로컬 정적 서버다. **그 논리가 지우라고 하는 계층이 여기 없다.**

지어낼 리팩터를 만들지 않았다. 대신 그 논리가 실제로 물리는 자리 하나를 고쳤다.

### 2. 같은 호출을 두 벌 두면 고침도 두 번인데 한 번은 잊는다

`xsource._bsky`(설계 실측)와 `bsky.search`(수집)가 블루스카이 호출을 각자
구현하고 있었다. 워크플로 지시서에서 내가 "그 헬퍼를 재사용하지 말고 같은
규칙으로 새로 쓰되"라고 적은 결과다. 그래서 적대적 검토가 **수집 쪽에서 잡아
고친 결함 둘이 실측 쪽에는 그대로 남아 있었다**:

- 막힘을 누적 플래그(`blocked = blocked or code in BLOCKED`)로 둬서 '앞 호스트
  403 + 뒤 호스트 전송 오류' 를 `blocked=True` 로 라벨했다 — 모르는 것을 판정한
  것이다(2장 1번).
- 뒤 호스트 사유로 앞 호스트 사유를 덮어 'api 429 · public 403' 이 '둘 다 403'
  과 로그에서 같아졌다(2장 6번).

### 3. 고친 모양

`bsky.call(method, params, s, timeout, retries, hosts, gap)` → `(js, ok, blocked,
why)` 하나로 모았다. 호스트 목록·403/429/503 판정·호스트별 사유·막힘의 AND 판정이
전부 여기 있다.

- `bsky.search` 는 `call('app.bsky.feed.searchPosts', …)` 뒤 `posts` 만 꺼내는
  어댑터가 됐다.
- `xsource._bsky` 는 `call(…, retries=0, gap=2)` 를 부르고 이 모듈 호출부가
  기대하는 3튜플로 바꾸는 어댑터가 됐다. 실측은 재시도하지 않는다 — 잰 값이
  '한 번 눌러서 무엇이 왔나' 여야 한다. 호스트를 바꿀 때 2초 쉰다.
- `gap` 은 호스트를 바꿀 때 쉬는 초다. 기본 0 이다 — 수집은 질의 사이에 이미
  2초를 쉬고(`PER_CALL_SLEEP`) 폴백은 드물어 4장 수집 예산에 넣지 않았다.
- `xsource.BLOCKED` 는 없앴다. 상수가 두 곳에 있으면 또 갈린다.
- 어댑터를 쓰며 **같은 결함을 다시 만들 뻔했다**: 처음 판은 `ok` 일 때
  `(js, None, False)` 로 돌려 폴백 사유를 버렸다. 이 모듈 호출부는 `why` 가
  있으면 '못 받았다' 로 읽어 반환에 실을 수 없으니 `log` 로 내보낸다.

### 4. CLI 는 이 저장소의 유일한 문이다

같은 논리 3번("최신 모델은 `--help` 로 CLI 를 탐색한다")으로 재니, `--help` 의
**아홉 플래그에 설명이 없었다**: `--check --init --daily --engine --render --test
--demo --verify-adjust --no-render`. `board.yml` 의 mode 가 전부 이 플래그로
내려오는데 목록에 이름만 있고 뜻이 없었다. 각 `cmd_*` 의 실제 동작만 보고 적었다
(지어내지 않는다 — 2장 4번).

파서를 `main` 에서 `build_parser()` 로 떼어냈다. 그러지 않으면 '설명 없는
플래그' 를 시험이 잡을 수 없다 — 파서를 만들려면 `main` 을 돌려야 했다.

### 5. 시험

## D-NEXT-Z. 리포트는 리포트의 말만 한다 — 검증·산출 절차의 말을 갈라 낸다

2026-09-22 발송된 보드 메시지에 우리가 **산출·검증하며 쓰는 말**이 섞여 나갔다.
사용자가 그것을 짚었다.

```
빠진 데이터 6건 — … · 산출물 정합성 위반 — 상위 라벨인데 하위가 미갱신
1종목: 00050… · 산출물 정합성 위반 — 역사적 최고가가 창 최고가보다 낮음 5종목: 0…
- 수정주가 미반영 의심 7종목 — 역사적 신고가 판정 제외
- 5종목은 계단이 있었지만 공시가 없어 실제 등락으로 보고 판정에 포함
- 장 흐름 섹션 생성 실패 — 검증 실패 1건
기준일 2026-09-22 · 종가 기준 · 수치는 board 엔진이 계산한 값이고 서술은 …
```

읽는 사람은 '산출물 정합성 위반' 이 무엇인지, '판정' 에 무엇이 들고 나는지 알
도리가 없다. 종목코드 `00050…`, `board 엔진`, '신고가 판정 계산을 확인하세요' 는
고치는 사람에게 할 말이다.

### 1. 지우는 것이 아니라 갈라 담는다

2장 6번은 **빠진 데이터**를 적으라는 규칙이지 처리 경위를 적으라는 규칙이 아니다.
둘은 독자가 다르다.

| | 무엇 | 어디로 |
|---|---|---|
| 결손 `notes` | 무슨 데이터가 없나 | 배너·리포트 |
| 진단 `diagnostics` | 엔진이 자기 산출을 의심하나 | `universe.json` · `run_log` · 로그 · `--check` |

`engine/build.py` 가 처음부터 두 목록으로 모은다. 진단으로 간 것: 산출물 정합성
검사(`consistency_notes`), 거래대금 단위 의심(`unit_sanity`), `DB.missing()` 의
`step:` 접두사(파이프라인 단계 이름은 읽는 사람에게 뜻이 없다 — 사유만 싣는다).
`rankings.build` 는 `notes` 만 배너로 올린다.

### 2. 결손 문구에서 내부 용어를 뺀다

- `수정주가 미반영 의심 N종목 — 역사적 신고가 판정 제외`
  → `N종목은 역사적 신고가를 내지 못했습니다 — 수정주가가 반영되지 않은 것으로 보입니다`
- `N종목은 계단이 있는데 공시를 대조하지 못해 역사적 판정에서 뺀 채로 뒀습니다`
  → `N종목은 역사적 신고가를 내지 못했습니다 — 주가에 계단이 있는데 액면분할·병합 공시를 대조하지 못했습니다`
- `n_split_cleared`(계단을 보고 공시를 찾아봤더니 없어서 실제 등락으로 처리했다)는
  **결손에서 뺐다.** 결과적으로 빠진 데이터가 없는 **처리 경위**다.

### 3. 섹션 실패와 검수 메모

- `장 흐름 섹션 생성 실패 — 검증 실패 1건` → `장 흐름 섹션은 이번 회차에 없습니다`.
  사유는 `meta.skipped` 와 로그에 그대로 남는다.
- 금지 문구 메모(`문장 N개 제거(금지 문구)`)는 검수용이라 리포트에서 뺐다. 다만
  `_one` 이 `{note, lost}` 로 돌려주게 해서 **종목 사실이 함께 지워진 수**만
  `섹션에서 종목 사실이 담긴 문장 N개가 빠졌습니다` 로 올린다 — 그건 진짜로
  리포트에서 빠진 데이터다. 사실이 함께 나간 문장이 없으면(`lost=0`) 결손도 없다.

### 4. 꼬리말

`기준일 … · 수치는 board 엔진이 계산한 값이고 서술은 그 수치를 옮긴 것이다.`
→ `2026-09-22 · 종가 기준`. 우리가 어떻게 만드는지는 리포트에 실을 말이 아니다.
언제 무엇을 기준으로 한 값인가만 남는다 — 그건 읽는 데 필요하다.

### 5. 시험

`tests/test_reader_voice.py` 12건이 **금지어가 독자 경로에 흐르지 않는가**를
기계로 본다(`산출물 정합성 위반` · `검증 실패` · `생성 실패` · `금지 문구` ·
`board 엔진` · `판정 제외` · `판정에 포함` · `확인하세요`). 동시에 '버리지 않았는가'
도 본다 — 진단이 `run_log` 와 페이로드에 남고, 섹션 사유와 검수 메모가 `meta` 에
남는지. 문구의 품질은 사람이 본다.

실측 **1,181건 통과**. 같은 배너를 다시 그리니 `빠진 데이터 4건` → `2건` 이고
남은 둘은 종가 잠정치와 공시 마감 시각이다.

### 6. 뺀 것을 볼 곳을 안 만들었다 (D-NEXT-Z 정정)

위 1번에서 진단을 배너에서 빼며 '`--check` 가 그것을 읽는다' 고 적었다. **거짓이었다**
— `cmd_check` 는 `universe.json` 을 아예 열지 않는다. 소스 프로브만 돈다. 그래서 한동안
진단은 파일을 직접 열지 않으면 아무도 못 보는 상태였고, 그건 갈라 담은 것이 아니라
숨긴 것이다(2장 6번).

`--check` 끝에 `산출 진단` 단계를 만들었다. 마지막 산출의 `diagnostics` 를 전부
찍고, 없으면 `OK 모순 없음` 이라고 **말한다** — 조용하면 '안 봤다' 와 '봤는데 없다'
가 같아진다. 아직 산출이 없으면 실패가 아니라 `아직 산출이 없다` 다.

종료코드는 바꾸지 않는다. 소스가 살아 있는지(`--check` 가 답하는 질문)와 엔진 산출이
스스로 모순인지는 다른 질문이고, 종료코드는 앞의 질문 것이다.

`tests/test_reader_voice.py` 에 6건을 더해 그 주장이 코드와 어긋나지 않게 고정했다.
실측 **1,187건 통과**.

## D-NEXT-Q. X 다이제스트에 별도 구획 둘 — AI 최신 뉴스 · 퀀트·백테스트

2026-09-23, 사용자가 "AI 최신 뉴스와 퀀트·백테스트 내용이 빠져 있다, 그것도 모아
정리해서 보내 달라" 고 했다. 질의 넷(`HBM · semiconductor · DRAM · TSMC`)이 전부
반도체·AI 인프라라 그 밖은 애초에 수집되지 않았다.

### 새 경로를 만들지 않고 있는 경로에 구획을 더했다

수집(`ingest/bsky.py`) → 분석(`xdigest/analyze.py`) → 렌더(`xdigest/render.py`) →
발송(`xdigest/send.py`)은 그대로 한 벌이다. 바뀐 것:

| 단계 | 무엇 |
|---|---|
| 설정 | `config/xdigest.yaml` `sections:` — 구획마다 `key · title · label · scope · queries · limit · keywords · max_items · max_pool`. 코드에 질의를 박지 않는다(CLAUDE.md 3장). `bsky.sections()` 하나가 수집·분석이 같이 읽는 정규화 함수다 |
| 수집 | 질의 계획(`bsky.plan`)이 기본 구획 질의를 먼저, 구획 질의를 뒤에 누른다. 게시물마다 `topic`(처음 잡힌 질의의 구획 키)을 적고 `sources.bluesky.by_topic` 에 구획별 창 안 건수를 남긴다. 호출 규약(질의당 1회 · 사이 2초 · 호스트 폴백 · 재시도)은 그대로다 |
| 분석 | ①~④ 는 기본 구획 게시물만 받는다. 구획 게시물은 **새 호출 ⑥** 하나가 구획마다 받아 `relevant`(범위에 맞는 키)와 `items`(`•` 줄)를 돌려주고, ③ 과 같은 검증(3-3)을 거친다 |
| 렌더 | 투자 인사이트 뒤에 `■ AI 최신 뉴스` · `■ 퀀트·백테스트`. 줄은 `• 사실 (@계정)`. 2행은 `반도체·AI 68건 · AI뉴스 5건 · 퀀트 3건 분석`. 0건이면 제목 아래 `해당 없음 — 수집 구간 내 게시물 0건` 한 줄 |

### 구획을 모델이 아니라 질의가 가른다

① 에 전부 넣고 모델에게 구획까지 고르게 하는 길도 있었다. 쓰지 않았다 — 기본
구획의 범위가 '반도체·AI' 라 AI 뉴스 글이 반도체 소주제로 새거나 그 반대가 되어도
코드가 되짚을 근거가 없고, ① 의 입력이 수백 건 늘어 Haiku 출력이 잘리는 자리
(D-NEXT-A)로 다시 간다. 질의가 정하면 `posts.json` 한 파일로 어느 글이 왜 그
구획인지 보인다. 두 구획에 걸린 글은 앞 구획(기본 구획이 먼저)으로 간다.

### 광고·잡담을 거르는 두 겹

1. `keywords` — 본문(소문자)에 하나도 없으면 ⑥ 에 넣지 않는다. 검색이 본문 밖
   (핸들·표시 이름)에서 걸린 글이다. 거른 건수는 `themes.json` `sections[].filtered`.
2. ⑥ 의 `relevant` — ① 의 `excluded` 와 같은 일을 모델이 한다. 머리 2행 구획
   건수는 `relevant` 와 남은 줄이 댄 게시물의 합집합을 **코드가 센 값**이다.

### 판정 경계 — 막힌 것을 없는 것으로 적지 않는다

- '분석 실패'(3-6)는 ②③④ 만 보고 판정한다. ⑥ 이 성공한 날 ②③④ 가 다 막혔는데
  실패로 치지 않으면 기본 구획 셋이 '해당 없음' 으로 나간다.
- ⑥ 이 막히면 그 구획 아래 `해당 없음 — 게시물 N건을 받았으나 분석하지 못함`,
  결손 줄에 `<구획> 분석 실패 — <사유>`. 기본 구획은 그대로 나간다.
- ① 이 죽으면 ⑥ 을 부르지 않는다. 결손 경로의 URL 목록이 구획을 가리지 않고 창 안
  게시물 전부라 구획 글도 거기 있다.
- `facts.json` 에 `sections` 가 없는 옛 파일은 예전 모양 그대로 그린다 — 9장 예시
  스냅숏이 한 글자도 안 바뀐 것이 그 증거다.

### 물량은 재지 못했다

이 작업을 한 컨테이너는 `api.bsky.app` · `public.api.bsky.app` 둘 다 프록시가
CONNECT 403 으로 막았다. 질의(`OpenAI · Anthropic · LLM · AI agent` /
`quant · backtest · 퀀트 · 백테스트 · factor investing`)는 **재지 않고 고른
것**이다. 러너에서 `mode=collect` 한 번이면 `by_topic` 과 질의별 로그가 남는다 —
그것으로 고친다. 호출은 하루 4 → 13회, 질의 사이 대기 6 → 24초다. D-NEXT-Y 의
403 은 30여 회 연달아 부른 날이었다.

- 구획에 `sort`·`lang` 을 둔다. `sort: top` 이면 수집기가 창을 since·until(UTC)
  로 함께 준다 — 안 주면 몇 달 전 인기글이 섞인다(`bsky.collect`).
- 호출은 그대로 하루 13회. `max_posts` 850 → 1,300(4×100 + 4×100 + 5×100).
  AI 구획 `max_pool` 150 → 250.

  한 줄이 정상이다.
- 이미 보낸 날에도 실물을 볼 수 있게 `--xdigest-preview`(xdigest.yml
  `mode=preview`)를 더했다. 임시 디렉터리에서 돌고 표식·state 를 건드리지 않으며
  첫 통 머리에 '🔎 미리보기' 를 붙여 보낸다. `bsky-probe` 는 board.yml `codes`

### 미리보기 실물에서 고친 것 (같은 날)

`mode=preview` 첫 실물: 3통 발송 OK, `■ AI 최신 뉴스` 8줄. 그런데 셋이 틀렸다.

1. **한도.** 그날 실측·프로브로 50번 가까이 부른 뒤라 질의 13개 중 뒤 7개(LLM ·
   AI agent · 퀀트 다섯)가 403 이었다. 퀀트 0건은 '없어서' 가 아니라 '막혀서' 였다.
   → 막힌 질의는 `block_cooldown_sec`(45초) 쉬고 한 번 더 누른다. 한 실행에
   `block_cooldowns`(3회)까지. 질의 사이 2 → 3초.
2. **3행에 403 HTML.** 막힌 질의마다 호스트별 HTML 이 gaps 와 errors 로 두 번씩
   실려 1통이 6,272자였다. 사용자가 전에 '검증·산출 과정 내용이 섞여 들어가지
   않게' 하라고 한 것이다. → 질의 결손은 이름만 모아 `접속 제한으로 못 받은 질의
   N개: …` 한 조각. 폴백으로 받은 줄은 결손이 아니라 뺀다. 파싱 드롭은 `형식이
   맞지 않는 응답 N건 제외`. 원문 사유는 posts.json 과 실행 로그에 그대로 있다.
3. **③ 재시도 잘림.** `max_tokens` 4,000 에서 잘렸다 → 8,000.

### 블루스카이 로그인을 선택지로 (같은 날 19:13)

`bsky-probe` 에서 질의 넷이 **첫 호출부터** 두 호스트 다 `403 · HTML(앞단 차단)`
이었다. 마지막 호출 뒤 90분이 지난 때라 호출량 탓이 아니다 — GitHub 러너의 공용
IP 대역이 공개 검색에서 걸러진 것이다. 그러면 질의를 `OR` 로 묶어 줄이는 것도,
쉬고 다시 누르는 것도 첫 호출을 못 살린다.

남은 무료 길은 계정 로그인 하나다. 앱 비밀번호로 `createSession` 을 하면 요청이
계정의 PDS 를 거쳐 가고 한도가 계정 단위가 된다. 예전 규칙('인증하지 않는다')의
근거는 '인증 없이 공개 데이터를 주는 것이 설계' 였는데, 앱 비밀번호 로그인도
블루스카이가 문서로 안내하는 공식 방식이라 규약 위반이 아니다. 그래서 **키가
있을 때만** 로그인하도록 바꿨다 — 시크릿이 없으면 동작은 예전과 같다. 쿠키·
그래프QL 경로는 여전히 없다. 계정 만들기와 시크릿 등록은 사용자 몫이다.

### 보드에 섞지 않고 한 통을 더 보낸다

보드 메시지(랭킹 요약)는 '오늘 무슨 일이 있었나' 이고 시그널은 '내일 무엇을 보나'
다. 한 통에 넣으면 4,096자 절단 규칙(D-084)이 어느 쪽을 먼저 버릴지 다시 정해야
하고, 시그널이 실패했을 때 보드까지 막힌다. `--send signals` 로 떼고 daily 사슬 맨
끝에 두어 실패해도 경고만 남긴다.

### 값은 전부 `config/signals.yaml` — 표시를 지우지 않는다

원문의 `[복원]`·`[2차]` 와, 원문이 원전값이 아니라고 밝힌 값(`비원전`), 원문에 없어
이 저장소가 정한 값(`새정의`)을 값마다 적었다. 새정의를 원작의 규칙처럼 읽으면
원문 CLAUDE.md 4번(재량 프록시를 원문 규칙과 분리)을 어긴다.

종가 확정값" 인 자리로 직접 꼽는다. 모든 판정을 장 마감 확정값으로 하고 체결은 다음

원문이 서로 부딪히는 근거를 함께 적었다 — #178 은 급등 이력 종목을 피하라고 하고
