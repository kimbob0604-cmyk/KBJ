# 수급 리포트 (monitor/flow)

**52주 신고가가 서고 거래량이 평소보다 는** 종목의 **최근 한 달 투자자별 수급**을
분석해 차트와 숫자표를 텔레그램으로 보낸다. 하루 다섯 종목이다.

## 대상을 어떻게 고르나

0. **종가 기준이다.** 고가 기준은 장중에 잠깐 뚫고 종가는 전일보다 낮게 끝난
   날도 신고가로 잡는다. 그런 종목이 수급 리포트로 오면 '일간 수익률은
   마이너스인데 52주 신고가' 가 되어 매번 멈춰서 따져 보게 된다. 종가 기준은
   그런 날이 없다 — 오늘 종가 > 과거 종가 최고 ≥ 어제 종가라 등락률이 반드시
   플러스다. 보드의 기본 기준도 종가로 맞춰 뒀다
   (`board/config/settings.yaml` `default_basis: close`).

   본문은 `52주 신고가(고가·종가 기준)` 처럼 **어느 기준으로 섰는지**를 적고
   (고가로도 뚫었는지가 그 줄에서 보인다), 수익률 줄에 `장중 고가 +5.3%` 를
   같이 실어 그 날의 모양을 보여 준다.

   신고가 판정일(보드)과 이 리포트의 마지막 거래일(수급·가격)이 다르면 본문이
   `기준일이 다르다 — 신고가 09.15 · 수급·가격 09.14` 라고 적는다. 서로 다른
   날의 사실을 같은 날로 읽지 않게 한다.

1. **신고가** — 보드가 만든 `newhigh.json` 에서 `hits['w52']` 가 선 종목이다. 보드
   화면의 '52주' 알약과 **같은 규약**이라 둘의 대상이 어긋나지 않는다. **역사적
   신고가도 여기 든다**(역사적으로 최고면 52주로도 최고다). 고가 기준과 종가 기준
   중 하나만 서도 대상이다 — 보드가 둘을 다 담으므로 고가만 보면 종가로만 뚫은
   종목이 조용히 빠진다. `--kind hist|w52|d60|all` 로 바꾼다.
2. **거래량** — 그날 거래량이 20거래일 평균의 **2배 이상**(`--vol-mult`). 보드가 매
   종목에 실어 보내는 `vol_mult` 를 그대로 쓴다. 여기서 다시 계산하면 화면의 '거래량
   N배' 와 대상이 갈린다.
3. **많이 는 순서로 다섯**(`--top`). 문턱을 끄면(`--vol-mult 0`) 보드가 매긴 순서를
   그대로 쓴다.

신고가만으로 고르면 '조용히 신고가를 낸' 종목이 섞인다. 수급 리포트는 누가 사고
팔았는지를 보는 것이라, 평소와 다르게 손이 바뀐 날이어야 읽을 거리가 있다. 문턱은
보드의 이상 탐지(`detect.volume_anomaly_mult` = 5.0)보다 낮다 — 저쪽은 '이상하다'
고 경보를 울리는 선이고 여기는 '볼 만하다' 는 선이다.

거래량을 못 구한 종목(분할 가드로 구간이 잘렸거나 원자료 결측)은 뺀다. 0배로 치면
없는 사실을 지어내는 것이다. 몇이 어느 단계에서 빠졌는지는 실행 로그가 매번 적는다.

신고가는 났는데 문턱을 넘은 종목이 하나도 없는 날은 **사고가 아니다.** 그런 날은
리포트 대신 '대상 없음' 한 줄을 보낸다 — 안 온 것과 못 온 것이 구분돼야 한다.
반대로 신고가 달성 자체가 0건이면 목록을 못 꺼낸 것이므로 실행을 실패로 끝낸다.

사용자가 준 KRX 워크북(실제 종목 한 개, 2026.08.18~09.14 20거래일)을 사양으로 삼았다.
[KBJ P1] 공개 레포에는 그 실데이터 대신 같은 형태의 합성 종목·합성 수급 골든을 둔다
(`tests/fixtures/golden.json` ← `tests/fixtures/make_synthetic.py`, 기대값은 워크북 정의의 독립 계산).

```bash
python -m monitor.flow.run                  # 52주 신고가 + 거래량 2배 이상, 5종목
python -m monitor.flow.run --vol-mult 3     # 거래량 문턱을 높인다
python -m monitor.flow.run --vol-mult 0     # 문턱 없이 보드 순서대로
python -m monitor.flow.run --kind all       # 라벨을 가리지 않는다
python -m monitor.flow.run --codes 092870   # 종목 지정
python -m monitor.flow.run --dry-run        # 보내지 않고 그림만
python -m monitor.flow.run --check          # KRX 접속만 확인
```

## 왜 KRX 인가

KIS 는 개인·외국인·기관 **3구분**만 준다. 워크북이 요구하는 투신·사모·연기금 같은
**기관 내부 7구분**은 KRX 정보데이터시스템에서만 나온다.

| 구분 | |
|---|---|
| 기관 7 | 금융투자 · 보험 · 투신 · 사모 · 은행 · 기타금융 · 연기금 등 |
| 그 밖 | 기타법인 · 개인 · 외국인 · 기타외국인 |

**로그인은 필요할 때만 한다.** `board/docs/APIS.md` B1 이 "KRX 는 로그인 필수화"라고
적어 뒀지만 그건 화면의 엑셀 다운로드 얘기다. 화면이 표를 그릴 때 쓰는 `getJsonData.cmd` 는
대개 인증 없이 열린다. 그래서 **익명으로 먼저 찌르고 막힐 때만** `KRX_ID`/`KRX_PW` 로
로그인해 재시도한다 — 비밀정보를 덜 쓰는 쪽이 안전하고 계정은 폴백으로 살아 있다.
어느 경로로 받았는지는 `--check` 가 찍는다.

## 만드는 것

**차트 4장** (`chart.py`, matplotlib PNG)

1. 투자자별 누적 순매수 — 개인 · 외국인 · 기관합계
2. **일봉 (원) + 거래량** — 캔들, 수정주가. 오르면 빨강 내리면 파랑
3. 외국인·기관 일별 순매수 (막대)
4. 기관 세부 누적 — 투신 · 사모 · 연기금 등 · 금융투자

2번은 원래 '기준일=100' 선 하나였다. 기준일이 매일 밀리니 같은 종목을 이틀 연속
받아도 선의 모양과 눈금이 달라져 어제 그림과 겹쳐 읽을 수 없었다. 가격 자체는 언제
그려도 같은 그림이라 실제 일봉으로 바꿨다. 일봉을 못 받으면 종가 선으로 물러서고,
그것도 없으면 그리지 않는다 — 빈 축은 '가격이 없었다' 로 읽힌다.

**표 2개 + 문장** (`narrative.py`) — 투자자 표(한 달·최근5일·순매수 주·매수일수),
기관 구분 표(한 달·기여율), 그리고 계산된 사실을 끼운 문장 6줄.

**수익률 한 줄** — `수익률 일간 +10.0%(09.14) · 1개월 +37.5%(08.14) · 연초 대비
+65.0%(25.12.30)`. 기준일을 괄호로 같이 적는다 — 어느 날과 견줬는지 확인할 수
있어야 한다.

| 항목 | 기준 |
|---|---|
| 일간 | 직전 거래일 종가 (종가끼리) |
| 장중 고가 | 직전 거래일 종가 대비 **그날 고가** |
| 1개월 | 달력으로 한 달 전, 그날 또는 그 이전의 마지막 거래일 종가 (21거래일이 아니다) |
| 연초 | **작년 마지막 거래일** 종가. 올해 첫 거래일로 재면 1월 2일 등락이 통째로 빠진다 |

못 재는 항목은 적지 않는다. 올해 상장한 종목은 작년 종가가 없으므로 연초 대비를
내지 않는다 — 상장 후 수익률을 끼워 넣으면 받는 사람은 그것을 연초 대비로 읽는다.
그래서 일봉은 **작년 12월 1일부터** 한 번에 받아 온다(차트는 그중 조회 구간만 쓴다).

**머리 두 줄** — 왜 뽑혔는지(`52주 신고가 · 거래량 20일 평균의 14.2배`)와 덩치 대비
거래(`시총 3.20조 · 거래대금 1,840억 = 시총의 5.8%`). 같은 1,000억이라도 시총 3천억
종목에서는 손이 통째로 바뀐 것이고 10조 종목에서는 평상시다. 시총·거래대금은 보드가
이미 잰 값을 그대로 옮긴다. 거래대금이 종가x거래량 추정치면 `(추정)` 을 붙인다.

## 확정한 계산

워크북과 대조해 확정한 것들이다. 짐작이 아니다.

| 항목 | 규칙 |
|---|---|
| 누적 순매수 | 조회 시작 **직전 거래일**을 0 으로 놓고 쌓는다 |
| 가격 Base100 | 같은 직전 거래일 종가 = 100 (문장·표에서 쓴다. 차트는 실제 일봉) |
| 매수일수 | 순매수 > 0 인 날. **보합(0)은 매수로 세지 않는다** |
| 기관 기여율 | 각 구분 ÷ 기관합계. 기관합계가 0 이면 내지 않는다 |
| 집중 구간 가격 | 구간 시작일의 **직전 거래일** 종가 기준 |

마지막 항목에서 한 번 틀렸다. 워크북이 9/1~9/4 구간을 8/31 종가 → 9/4 종가로 적는데
구간 시작일 당일(9/1) 종가를 기준으로 재니 절반 남짓한 값이 나왔다.
그날의 매수는 그날 장중에 일어났으므로 그 구간의 가격 변화에 포함돼야 한다 —
누적선을 직전일 0 에서 쌓는 것과 같은 이유다. 시험으로 박아 뒀다.

## 검산이 깨지면 보내지 않는다

워크북의 '대조 항목' 블록을 그대로 옮겼다. 일별 합이 KRX 기간합계와 **원 단위로** 맞아야 한다.

```
기관 금액 vs 기간합계 · 외국인 금액 · 개인 금액 · 기관 수량 · 외국인 수량 · 순매수 금액 전체(=0)
```

하나라도 벌어지면 어느 쪽이 틀렸는지 모른다. 그 상태의 리포트는 틀린 숫자를 사실처럼
보내는 것이므로 **그 종목을 건너뛰고** 무엇이 얼마나 어긋났는지 로그에 남긴다.

## 문장은 규칙 기반이다

`board/CLAUDE.md` 2장 3번(LLM 에 숫자를 계산시키지 않는다)을 따라 **LLM 을 아예 안 쓴다.**
집중 구간·교차·전환·쏠림은 전부 코드가 판정하고, 문장은 그 결과를 끼운 틀이다.
같은 입력이면 같은 문장이 나오고 전부 시험할 수 있다.

**인과로 쓰지 않는다.** '동행' 이라고 쓰고 '때문에' 라고 쓰지 않는다 — 이 데이터로는
어느 쪽이 원인인지 식별되지 않는다. 리포트 하단에 한계 두 줄을 항상 싣는다.

## 한글 폰트가 없으면 만들지 않는다

matplotlib 은 글리프가 없어도 **조용히 두부(□)를 그린다.** 차트는 만들어지고 전송도
되는데 읽을 수 없는 그림이 간다. 그래서 폰트를 고를 때 실제로 '가나힣' 글리프가 있는지
확인하고 없으면 예외를 낸다. CI 는 `fonts-nanum` 을 깐다.

## 색

dataviz 스킬의 검증된 기본 팔레트에서 슬롯 순서대로 가져왔고, 쓰는 조합을 전부
`validate_palette.js` 로 돌려 통과를 확인했다(차트1 3색 · 차트3 2색 · 차트4 4색).
색은 **주체에 고정**한다 — 개인은 어느 차트에서나 파랑이다.

대비 검사에서 일부 색이 3:1 미만 WARN 이 났다. 규약대로 구제 수단을 붙였다 —
마지막 점에 값을 직접 찍고, 텔레그램 본문에 같은 숫자를 표로 싣는다.

## 지금은 KIS 3구분으로 낸다

KRX 가 막혀 있는 동안(위 표) **개인·외국인·기관 3구분**으로 리포트를 만든다.
`--source auto` 가 기본이고, KRX 를 한 번 찔러 보고 막히면 KIS 로 간다.
어느 쪽으로 만들었는지는 리포트 본문에 `출처: kis` / `출처: krx` 로 실린다.

```bash
python -m monitor.flow.run --source kis     # KRX 를 건너뛴다
python -m monitor.flow.run --source krx     # 막히면 그냥 실패
```

**빠지는 것** — 차트 4(기관 세부 누적)와 기관 구분 표. 없는 줄을 'N/A' 로
남기지 않고 **아예 뺀다**. 'N/A' 는 '0 이었나?' 로 읽힌다.

### 검산을 못 하는 것을 숨기지 않는다

KIS 에는 KRX 의 기간합계에 해당하는 원자료가 없다. 그러면 '일별 합 = 기간합계'
대조를 할 수 없다. 일별 합끼리 비교하는 건 항등식이라 검증이 아니다.

그래서 **하지 않은 대조를 했다고 적지 않는다.** `verified=False` 로 두고 본문에
그 사실을 싣는다. 검산이 *깨진* 것과 검산을 *못 한* 것은 다르고, 앞은 리포트를
내지 않고 뒤는 내되 그렇게 말한다.

### 대신 단위를 확인한다

KIS 금액 필드가 **백만원**이라는 건 `board/ingest/kis.py` 가 그렇게 적어 둔
가정이고 실호출로 확정된 적이 없다. 자릿수가 틀리면 리포트의 모든 숫자가 100만
배로 틀린다.

그래서 받은 금액을 **수량 x 종가**와 대조한다. 순매수 금액은 체결가 가중이라
정확히 같지는 않지만 자릿수는 같아야 한다. 배수가 0.2~5.0 을 벗어나면 단위를
잘못 안 것으로 보고 **그 종목을 건너뛴다.** 시험으로 박아 뒀다(100만 배·100만분의
1 둘 다 잡는다).

| `dbms/MDC/STAT/standard/MDCSTAT02303` (일별) | 400 `LOGOUT` |
| 〃 `MDCSTAT02301` (기간합계) | 400 `LOGOUT` |
| 〃 `MDCSTAT02203` (전체시장) · `MDCSTAT01602` (시세) | 400 `LOGOUT` |
| **있을 리 없는 `MDCSTAT99999`** | 400 `LOGOUT` |
| 메뉴에서 긁은 진짜 menuId 4개로 로더를 열고 재시도 | 400 `LOGOUT` |
| 로더 HTML 에서 bld 문자열 찾기 | 19,404자에 `dbms/...` 0개 (JS 가 그린다) |

세 가지가 정리된다.

1. **전송은 멀쩡하다.** 같은 주소·같은 세션으로 finder 는 JSON 을 준다.
   https 로 바꾸고(301 이 POST 를 GET 으로 바꾸던 것) 화면을 먼저 여는
   것까지는 맞았다.
2. **`LOGOUT` 은 로그인하라는 말이 아니다.** 없는 화면코드도 똑같이
   `LOGOUT` 이 온다. 즉 '이 bld 는 안 준다' 는 뜻이고, 어느 쪽이 틀렸는지는
   이 응답만으로 가려지지 않는다.
3. **menuId 도 원인이 아니다.** 진짜 번호로 열어도 같다.

### 결론: KRX 가 이 실행 환경을 막고 있다 (코드 문제가 아니다)

브라우저 캡처가 답을 냈다. 잡은 요청은 0건인데, 그 이유가 화면이 아니었다.

```
메인 열림: '에러페이지 - 한국거래소 | 정보데이터시스템' · 요청 0건
메뉴 후보 0개
```

**브라우저로 메인을 열면 에러페이지가 온다.** 같은 주소를 `requests` 로 받으면
573KB 짜리 진짜 페이지가 오고 쿠키도 받는데, 크로미움으로 열면 에러페이지다.
여기에 '모든 STAT 화면이, 없는 화면코드까지, 똑같이 400 LOGOUT' 을 겹쳐 놓으면
설명은 하나로 모인다 — **KRX 가 GitHub Actions 러너 쪽 접근을 통계 서비스에서
걸러내고 있다.** finder 하나만 남겨 두고.

그래서 이건 화면코드·파라미터·로그인으로 풀 문제가 아니다. 코드를 더 고쳐서
될 일이 아니라 **어디서 요청하느냐**의 문제다. 갈 수 있는 길은 셋이다.

| 길 | 얻는 것 | 드는 것 |
|---|---|---|
| KRX 가 받아 주는 곳에서 실행 (자체 러너·국내망) | 기관 7구분 그대로 | 러너를 직접 띄워야 함 |
| KIS 3구분으로 낮춤 (개인·외국인·기관) | 오늘부터 발송 가능 | 기관 세부 차트 1장과 구분 표를 뺌 |
| 워크북을 받아서 넣기 | 예시와 똑같은 숫자 | 매일 손이 감 |

계산·차트·문장·검산·전송은 전부 완성돼 있고 시험 56건이 통과한다. 위 셋 중
어느 쪽을 고르든 **원자료를 넣는 자리만 바뀐다.**

### 캡처 도구는 그대로 둔다

`monitor/flow/capture.py` 가 KRX 화면을 진짜 브라우저(Playwright·Chromium)로 열고,
그 화면이 표를 그릴 때 보내는 `getJsonData` 요청을 그대로 잡는다. **KRX 가 받아 주는
곳에서 한 번만 돌리면** 실제 `bld` 와 파라미터가 나오고, 그걸 `krx.py` 의
`BLD`·`FIELD` 표에 옮겨 적으면 끝난다. 지금 환경에서는 에러페이지가 와서 0건이다.

```bash
python -m monitor.flow.capture                 # 투자자별 화면을 찾아 잡는다
python -m monitor.flow.capture --menu MDC0201020303
```

**쿠키는 적지 않는다.** 잡은 것을 그대로 로그에 찍기 때문에, 헤더는 이름을
허용 목록(`SAFE_HEADERS`)으로 걸러 `content-type`·`referer` 같은 것만 남긴다.
`flow.yml` 이 매 실행마다 이 단계를 돌려 결과를 `krx-request.json` 으로 보관한다.

그 전까지 `monitor/flow` 는 **계산·차트·문장·검산·전송이 전부 완성돼 있고
시험 53건이 통과하지만, 수급 원자료가 없어 리포트를 보내지 못한다.**

## 아직 안 된 것

- **KRX 실호출이 아직 안 붙었다.** 2026-09-15 첫 실행에서 `getJsonData` 가 JSON 을
  주지 않았다. 두 가지를 고쳐 다시 붙인다.

  1. 주소를 **https** 로 바꿨다. http 로 부르면 KRX 가 301 로 넘기고 requests 는
     301 을 따라갈 때 POST 를 GET 으로 바꾼다 — 파라미터가 통째로 빠진 요청이
     화면 HTML 을 받아 오니 파서가 죽는 게 당연했다. 이제 리다이렉트를 따라가지
     않고 어디로 보내려 했는지를 사유에 적는다.
  2. 실패 사유를 **본문에서 뽑아** 올린다. `JSONDecodeError` 한 줄로는 로그인
     화면인지, 차단인지, 화면코드가 없는 건지 구분이 안 됐다.

  3. **화면을 먼저 한 번 연다.** 고친 뒤 실호출에서 `HTTP 400 · LOGOUT` 이 왔다.
     계정 문제가 아니라 화면이 심어 주는 세션 쿠키가 없다는 뜻이다. 브라우저가
     화면을 열고 나서 표를 그리는 순서를 그대로 따라 `mdiLoader` 를 GET 한 뒤
     찌른다.

  화면코드(`BLD`)와 필드명(`FIELD`)은 여전히 규약 기준이다. 남아 있으면 `--check`
  가 이제 상태코드·Content-Type·본문 앞부분을 찍으므로 그 표만 고치면 된다.
