## 2. 서비스 구성

```
             ┌──────── scheduler (상태 머신, 마스터·월물리스트·KRX·분봉 적재, 리포트)
             │  pub session.events / Redis session:state
  auth ──► Redis kis:token, kis:ws_key ◄── 모든 KIS 호출자(읽기만)
             │
  poller ──► REST(레이트리미터 경유) ──► db(chain_snapshots, investor_flow, fut_board)
     │                                  └► pub chain.snapshot
  ws-gateway ──► KIS 웹소켓(단일 세션, 41건) ──► pub ws.raw / ticks.fut / ticks.opt
     │  재연결 뒤 REST 스냅샷(레이트리미터 경유)
  recorder ◄── sub ws.raw, rest.raw ──► db(raw_messages) ──(30일)──► Parquet
```

| 서비스 | 하는 일 | 장애 시 |
|---|---|---|
| `redis` | 토큰 캐시, 레이트리미터, pub/sub, 최신 상태 | 전 서비스 재시도 대기. 레이트리미터를 못 쓰면 KIS 호출을 멈춘다(한도 초과보다 결측이 낫다) |
| `db` | PostgreSQL + TimescaleDB (§8) | 쓰기 실패분은 서비스별 로컬 큐(디스크)에 쌓고 복구 뒤 재적재 |
| `auth` | 접근토큰·웹소켓 접속키 발급/갱신 → `kis:token`, `kis:ws_key`(TTL). 만료 1시간 전 갱신, 실패 시 **61초** 간격 재시도 | 기존 토큰이 살아 있는 동안 서비스는 계속 돈다. 만료 10분 전까지 실패하면 health 경고 |
| `scheduler` | 세션 상태 머신(§6) → `session:state`·`session.events`. 마스터(`PRE_DAY`·`PRE_NIGHT`), 월물리스트, KRX 일별(`PRE_DAY` 08:05~), 분봉 적재(`POST_DAY`·`IDLE`), 무결측 리포트 | 상태 발행이 멈추면 다른 서비스는 마지막 상태 + 시계로 계속, health 경고 |
| `poller` | REST 주기 수집(§5) | 호출 단위로 격리. 실패 호출은 다음 주기에 다시, 연속 실패는 health |
| `ws-gateway` | KIS 웹소켓 단일 세션 소유, 41건 예산(§4), ATM 회전, 세션 전환 시 구독 교체 | 지수 백오프(1s→60s) 재연결, 재연결 뒤 REST 스냅샷으로 상태 복구(§6.5) |
| `recorder` | 파싱 전 원본을 그대로 `raw_messages`에 저장(리플레이·골든) | 파싱과 분리돼 있어 파서 오류가 녹화를 막지 않는다 |

- **토큰 경합 방지**: 지금 probe(`data/kis/rest.py`)는 실행마다 토큰을 새로 받는다. Phase 1에서 토큰 제공자를 인터페이스로 빼서 서비스·probe 모두 Redis 캐시를 먼저 읽고, 없을 때만 발급한다(발급은 `auth` 기동 전 로컬 probe에 한해 허용).
- 모든 KIS REST 호출은 공용 클라이언트 한 곳을 지나며 레이트리미터·응답 검증(pydantic)·raw 발행(`rest.raw`)을 거친다. 검증에 실패한 레코드는 `quarantine`(§8, PLAN §6.1)에 쓰고 해당 산출은 `quality=invalid`. 웹소켓 파서도 같다
- 서비스 조립(2026-09-29, `python -m services.<서비스>`, `docker-compose.yml`)에서 정한 기본값 **[확인 필요]** — 설계에 없던 부분이다
  - Redis 계약(채널·키 이름)은 `services/bus.py` 한 곳. 마스터는 scheduler 가 `kis:master`(+sha)에 두고 poller·ws-gateway 가 읽는다. poller 는 체인 문맥(월물리스트·KIS 최종거래일·선물 순서)을 `poller:chain_context` 에 두고, ws-gateway 는 그것이 없으면 마스터 + 캘린더 계산 최종거래일로 대신한다(health `ws_context_fallback`)
  - 원문 발행(`ws.raw`·`rest.raw`)은 받는 쪽 수가 0 이거나 Redis 오류면 발행자가 직접 `raw_messages` 에 쓴다 — recorder 가 죽어도 잃지 않는다(digest 키라 겹쳐도 한 행). recorder 가 강제로 죽으면 쓰기 전 묶음(최대 1초·500건)은 잃는다
  - 로컬 디스크 큐(`data/spool.py`): 서비스마다 `state/spool/<서비스>/`, 상한 1 GiB(`SPOOL_MAX_MB`, 넘으면 오래된 세그먼트부터 버리고 critical health), 세그먼트 8 MiB, 백오프 1→30초, 재적재 한 번 2초. 스풀에 남은 동안 새 묶음도 뒤에 붙여 표마다 순서를 지킨다(DO UPDATE 표). 재적재 묶음이 데이터 오류로 거부되면 한 행씩 다시 보내 거부된 행만 `_dead/<표>.jsonl`(상한 1/8)로 — 스풀 없는 경로에서 호출자가 한 건씩 살리는 것과 같다. 녹화량 실측 뒤 상한 조정
  - scheduler 마스터 내려받기: 상태 루프(1초)를 막지 않게 데몬 스레드에서, 접속 5초·읽기 15초·전체 30초로 끊고 실패하면 60초 뒤 다시. 받는 동안 전이가 오면 끝난 뒤 다시 받는다. 배포 파일 크기·응답 시간은 미실측이라 보수적으로 잡았다
  - scheduler KRX 전일 적재(`services/scheduler/krx.py`, 2026-09-29): 거래일 D 의 08:05 부터(상태가 아니라 KST 날짜로 — PRE_DAY 에서 DAY 로 넘어가도 이어진다) 전 거래일 `prev_trading_day(D)`(월요일은 금요일, 09-28 은 추석 너머 09-23)의 코스피200 옵션·선물 일별을 종류마다 1건 불러 `krx_opt_daily`·`krx_fut_daily` 에(DO UPDATE — 다시 돌려도 행이 늘지 않는다). DB 에 이미 있는 종류는 부르지 않고(이어 받기 — 재기동 포함), DB 를 못 읽으면 부르지 않는다. 빈 응답·요청한 BAS_DD 가 아닌 행뿐이면 갱신 전 → 10분 뒤 다시, 다음 시도가 10:00 을 넘으면 그날은 그만 + health `krx_daily_missing`(HTTP·저장 실패는 그때마다 `krx_daily_failed`, 다 받으면 info `krx_daily_loaded`). 기동이 10:00 뒤여도 그날 한 번은 부른다. KST 하루 호출 상한 200(`KRX_DAILY_CALL_CAP`) — Redis `krx:calls:<YYYYMMDD>`(TTL 3일)에 세어 재기동해도 이어지고, 닿으면 그날은 그만 + `krx_daily_capped`. 평소 하루 2건, 재시도를 다 써도 24건(08:05~09:55 12회 × 2). 적재는 작업 스레드에서(상태 루프는 끝났는지만 본다), 쓰기는 스풀 없는 따로 된 DB 연결 — 스풀에 든 행은 `krx_loaded` 에 보이지 않고, 옵션 하루 약 16,700행 쓰기가 상태 루프 싱크의 잠금을 쥐지 않게. DB 장애면 실패로 보고 10분 뒤 다시. KRX 클라이언트는 접속 5초·읽기 30초·전체 120초·64 MiB, 오류 문구는 인증키를 가린다. scheduler 가 하루 넘게 멈춰 놓친 날은 되받지 않는다. `KRX_API_KEY` 가 없으면 끈다(health `krx_disabled`)
  - scheduler KIS 분봉 적재(`services/scheduler/minute.py`, 2026-09-29): 규칙·기본값은 §8 분봉 적재. 조립은 앱키당 하나인 Redis 레이트리미터(poller·ws-gateway 와 같은 버킷, 등급 P4 — 허가를 1초 안에 못 받으면 그 시도 실패)와 auth 가 둔 `kis:token` 읽기만(발급 없음). 근월물 최종거래일은 poller 문맥(`poller:chain_context`, 없으면 캘린더), 근월물 코드는 scheduler 가 Redis 에 둔 마스터. 쓰기는 상태 루프 싱크(스풀) — 한 번 102행 이하라 잠금을 오래 쥐지 않고 DB 장애에도 잃지 않는다. 원문은 `rest.raw` 발행 없이 곧바로 `raw_messages`(발행자 직접 쓰기와 같은 경로 — digest 키). 적재는 작업 스레드에서(상태 루프는 끝났는지만 본다), 그 단계의 오류는 health `minute_step_failed` 로 격리. `KIS_APP_KEY` 가 없으면 끈다(health `minute_disabled`)
  - scheduler 개장 이중 확인·무결측 판정(2026-09-29, §6·§9): 읽기·판정 교체는 스풀 없는 세 번째 DB 연결(`report_store`) — 상태 루프 싱크의 잠금을 쥐지 않고, 판정은 다시 계산할 수 있어 스풀에 쌓지 않는다. 둘 다 작업 스레드에서 돌고 오류는 health(`open_check_step_failed`·`gap_step_failed`)로 격리
  - 하트비트: Redis `health:heartbeat:<서비스>`(TTL 60초, 10초마다), compose healthcheck 는 나이 60초(auth 120초). Docker 는 unhealthy 컨테이너를 스스로 다시 띄우지 않는다(`restart: always` 는 종료에만) — 자동 재기동·외부 알림(PLAN §11.3)은 따로 정한다
  - ws-gateway: 받은 것은 큐(20만 건)로 작업 스레드에 넘겨 발행·저장(틱 500건·0.5초 묶음). 체결 시각은 원문 HHMMSS 를 수신 시각에 가장 가까운 날로 푼다 — 야간 웹소켓 체결 시각이 00~06시인지 24~30시인지 미실측이라 둘 다 받는다. seq 는 수신 순번 + 기동 초 × 10⁶(다시 기동해도 (ts, code, seq) 가 겹치지 않게), 재연결마다 순번 하나를 건너뛴다(끊김이 틱 스트림의 순번 공백으로 보인다 — engine HIRO-lite 리셋, metrics §6.1). 웹소켓 파서 실패는 원문(raw_messages)과 health 로만 남긴다 — quarantine 적재는 아직 없다. 멈출 때 작업 스레드가 큐를 비우길 40초까지 기다린다(compose `stop_grace_period` 60초 — SIGKILL 전에). 못 비우면 남은 큐·묶음 수를 critical 로 남긴다

## 3. REST 레이트리미터

- 앱키당 하나. Redis 토큰버킷(Lua로 원자 처리), 키 `rl:kis:<앱키 해시>`
- **설계값: 4.0건/초, 버킷 용량 1(호출 간격 0.25초 — GCRA와 같음).** 어떤 반열린 1초 창 [t, t+1)도 4건을 넘지 않는다. 근거: 무오류 상한 5/s(실제 5.4·5.5/s 2초 버스트 2회)·4.89/s 17초 연속 무오류, 10/s부터 매번 초과(#10). 5~10/s 사이는 미측정이라 버스트도 4건 안에 묶는다. 버킷 4로 두면 한꺼번에 4건 + 0.25초마다 1건이 나가 1초 창에 7건이 되어 측정 무오류 수준을 넘는다
- 수요(§4.4 표): 분당 159건 = 평균 2.65/s → 상한의 66%

## 4. 웹소켓 41건 예산

| 세션 | 선물 체결 | 체결통보 | 옵션 체결 | 여유 | 합 |
|---|---|---|---|---|---|
| 주간 | 1 (`H0IFCNT0`, 근월물) | 1 (`H0IFCNI0`) | 38 = ATM±9 × 콜·풋 (`H0IOCNT0`) | 1 | 41 |
| 야간 | 1 (`H0MFCNT0`) | 2 (`H0MFCNI0`·`H0EUCNI0`) | **34** = ATM±8 × 콜·풋 (`H0EUCNT0`) | **4** | 41 |

**야간 36 vs 34 불일치 해결.** PLAN §4.3의 "옵션 체결 36 (ATM±8 × 콜·풋)"은 계산 오류다. ATM±8은 행사가 17개라 ×2 = 34다. 36을 쓰려면 행사가 18개(ATM 기준 비대칭)가 필요해서 쓰지 않는다. `config/ws_budget.yaml`의 34가 맞고, 남는 2건은 여유로 돌려 야간 여유는 4다.

- yaml은 고정 `spare` 대신 최소 여유 `min_spare`(주간 1·야간 2)를 두고 `atm_range`를 식으로 도출한다: `atm_range = floor(((limit − futures − notices − min_spare) / 2 − 1) / 2)` → 주간 9, 야간 8. 실제 여유 = `limit − futures − notices − (2·atm_range+1)·2` → 주간 1, 야간 4
- 테스트로 고정: 합계 ≤ 41, 옵션 수 = (2·atm_range+1)×2, 대칭
- PLAN §4.3 문구(36 → 34, 여유 2 → 4)는 Phase 1 첫 커밋에서 yaml과 함께 고친다 — `claude/phase1` 304b102에서 고침
- 체결통보는 Phase 1엔 주문이 없어 등록하지 않지만 자리는 비워 둔다. Phase 8·9와 같은 구독 구성으로 녹화해야 골든 fixture를 그대로 쓸 수 있다
- 구독 만기: 최근접 만기(0DTE 포함). 만기일 15:20 이후 차기 만기로 전환
- ATM: 선물 근월물 최근 체결가에 가장 가까운 행사가(#11a — 전광판 표시 안 씀). 1분마다 재계산, 기존 중심과 2행사가 이상 차이 날 때만 회전(§4.3). 회전은 해지 먼저·등록 나중
- 등록·해지 속도 한도는 실측하지 않았다 → 0.1초에 1건으로 시작, 오류 응답이면 감속하고 health 기록
  - 구현(`services/ws_gateway/client.py`, `config/kis_ws.yaml` client)의 기본값 **[확인 필요]**: 오류 응답이면 간격 ×2, 상한 1.0초(0.1 → 0.2 → 0.4 → 0.8 → 1.0), health `ws_pacing_slowdown`. 감속 전에 보낸 요청의 오류는 같은 버스트로 보고 더 늘리지 않는다. 성공 응답 20건이 이어지면 ÷2 로 한 단계씩 0.1초까지(`ws_pacing_recovered`). 이미 등록됨·등록 안 됨(서버와 셈 차이)·접속키 거절(끊고 다시 붙음)은 속도 탓이 아니라 세지 않고, 응답 없음(ack 시간 초과)도 감속하지 않는다. 재연결해도 늘린 간격은 둔다. 상한 1.0초면 세션 전환(해제 39 + 등록 35건)이 약 74초 걸린다. KIS 가 속도 초과를 어떤 문구로 알리는지 미실측이라 알 수 없는 거절(`rejected`)·최대 구독 초과를 모두 오류로 친다

## 5. 수집 주기 (PLAN §4.4, 2026-09-28 실측 반영)

§4.4 표가 기준이다. 운영 세부:

- **전광판**(P1): 최근접·차기·월물 3건/30초. 위클리 전광판 스냅샷마다 ATM(선물가 기준)이 받은 행사가 범위 안인지 검사 → 밖이면 health 경고(급변 장에서 밖으로 밀릴 수 있다). 월물은 전광판이 늘 최고 행사가 100개라 ATM이 빠지므로(#11) 전광판+보강 1을 합친 범위로 검사
- **보강 1**(P3): 월물 ATM±20 × 콜·풋 = 82건/60초, 60초 안에 고르게 흩어 부른다(1.37/s)

  - 구현(2026-09-29, `services/scheduler/master_check.py` + scheduler KRX 구동 `KrxDaily`): 그날 PRE_DAY(08:00) 뒤에 받은 마스터(Redis `kis:master` — 재기동하면 거기 있는 것)와 전 거래일 `krx_opt_daily`(§2 KRX 전일 적재)가 둘 다 있으면 마스터 파일(sha)마다 한 번 — PRE_DAY 것, PRE_NIGHT 에 파일이 바뀌었으면 그것도 — 작업 스레드에서 대조한다. 만기 = (상품군, 6자리 만기), 코스피200 계열만, 둘 다에 있는 만기의 KRX (콜풋, 행사가)가 마스터에 모두 있어야 한다(콜·풋 한쪽이 통째로 없어도 빠진 것). 빠진 행사가 → health `master_krx_missing`(warning — 개수·시리즈 앞 3개·대조 만기 수), 모두 있으면 구조화 로그만(`master_krx_checked` — 신규 행사가·KRX 에만 있는 만기(전날 만기 지남)·마스터에만 있는 만기 수). 대조를 못 하면(DB·마스터 파싱 오류, KRX 상장 목록이 빔) `master_krx_check_failed`, 10분 뒤 다시
- **선물 근월물·ATM 기준가**: 최종거래일 15:20이 지난 종목(분기 만기일의 근월물)은 건너뛴다 — `ws-gateway` 구독 선물과 같은 규칙(`ChainContext.live_futures_codes`, 선물 최종거래일 = 같은 결제월 월물 옵션의 KIS 값, 없으면 캘린더). 마스터에 코스피200 선물이 있는데 없는 종목(만기 지나 새 마스터에서 빠진 근월물 — 야간 B는 선물 전광판을 부르지 않아 전광판 순서엔 남는다)도 건너뛰고, 마스터에 선물이 하나도 없을 때만 모르는 종목을 살아 있다고 본다. 15:20 뒤 선물 전광판·단건 응답에서 차월물을 기준가로 잡고, 그 시세가 올 때까지 보강 1·2는 쉰다(옛 근월물 가격으로 ATM을 잡지 않는다). 기초자산 조회·야간 선물 단건 `CM`도 차월물부터. 만기 지난 종목의 전광판 행은 그대로 적재한다. 만기일 전광판 잔존일수 표기·만기 뒤 옛 근월물 단건 응답·만기일 저녁 마스터에서 옛 근월물이 빠지는지는 미실측 **[확인 필요]**

## 6. 세션 상태 머신

순수 함수 `state_at(ts_utc, calendar) -> (state, trade_date, session)`를 중심에 두고 `scheduler`는 이것을 1초마다 평가해 바뀔 때만 발행한다. 시계는 주입(테스트용 가짜 시계).

| 상태 | 시간(KST) | 조건 |
|---|---|---|
| `PRE_DAY` | 08:00~08:45 | D가 거래일 |
| `DAY` | 08:45~15:45 | D가 거래일. `trade_date = D`, `session = day` |
| `POST_DAY` | 15:45~17:50 | D가 거래일 |
| `PRE_NIGHT` | 17:50~18:00 | 오늘 밤 야간장이 열릴 때 |
| `NIGHT` | 18:00~익일 06:00 | 오늘 밤 야간장이 열릴 때. `trade_date = next_trading_day(D)`, `session = night` |
| `IDLE` | 그 외, 휴장일 | — |

- 캘린더: `exchange_calendars` XKRX + `config/holidays_override.yaml` (Phase 1에 의존성 추가)
- **야간장 열림 규칙**(2026-09-29 실측으로 고침): 거래일 D의 밤은 **금요일이면 늘**, 월~목이면 **다음 날(D+1)이 거래일일 때만** 열린다 — 밤이 D+1 06:00에 끝나므로, 금요일 밤은 토 06:00에 끝나 월요일 휴장과 무관. 귀속은 늘 `next_trading_day(D)`(`core.calendar.night_session_opens`). 그 전 규칙 `next_trading_day(D) == next_weekday(D)` 는 월요일 휴장 앞 금요일 밤을 닫힘으로 보아 틀렸다
  - 실측(2026-09-28, CM 분봉): 금요일 09-18 밤 **열림, 토요일 06:00까지**(09-18 23:59 기준 `20260918` 22:19~24:00 봉, 09-21 05:59 기준 `20260918` 28:07~30:00 봉), 휴장 전날인 수요일 09-23 밤 **안 열림**(09-23 23:59 기준 최신 야간 봉이 09-22 밤의 30:00)
  - 실측(2026-09-29 15:52, probe `minute_paging`, `runs/20260929_1552`): 월요일 휴장 앞 금요일 밤 **열림** — `CM` (05-22, 23:59:59)·(08-14, 23:59:59) 모두 그 날짜의 22:19~24:00 봉 102개(05-25 월 휴장, 08-15 토 광복절·08-17 월 대체휴일), 대조군 목요일 05-21·08-13 과 같다
  - 미실측 **[확인 필요]**: 거래소 자체 휴장일(연말 휴장일 등) 전날 밤(규칙상 안 열림), 여러 날 연휴 앞 금요일 밤(규칙상 열림). 아래 이중 확인(닫힌 밤 구독·개장 3분 체결 확인)으로 틀리면 잡는다

- **분봉 적재**: `POST_DAY`에 당일 주간(`F`). 야간(`CM`)은 귀속 거래일 next_trading_day(D) 당일 `IDLE` 06:10에 (D, 300000)부터 확장 시각으로 18:00까지 한 줄(위 2026-09-29 실측) — 금요일 밤은 월요일 06:10(월요일 휴장이면 다음 거래일, 날짜 입력은 늘 금요일)
  - 구현(2026-09-29, `services/scheduler/minute.py` — 한 번의 시도 `MinuteLoader`, 하루 구동 `MinuteDaily`). 상태가 아니라 KST 날짜·시각으로 고른다. 기본값은 **[확인 필요]**(§12)
  - 언제: 거래일 T 의 16:00~17:50(POST_DAY 안 — 첫 입력 (T, 16:00:00)이 미래가 아니게 15:45~16:00 엔 부르지 않는다)에 T 주간, 06:10~08:00(IDLE — 08:00 PRE_DAY 마스터·08:05 KRX 전)에 T 로 귀속되는 밤 = prev_trading_day(T) 에 시작한 밤. 그 밤이 열리지 않았으면(`night_session_opens` 거짓 — 휴장 전날 밤·휴장일 밤, §6) 부르지 않고 로그 `minute_night_closed` 만. 그래서 금요일 밤은 월요일 06:10, 토요일은 비거래일이라 부르지 않는다. 월요일 휴장 앞 금요일 밤은 열리므로(2026-09-29 실측, §6) 화요일 06:10 에 (금, 300000)부터 받는다(시험으로 고정)
  - 근월물: 마스터(scheduler 가 Redis 에 둔 것)의 코스피200 선물을 결제월 순으로, 최종거래일(poller 문맥의 KIS 값, 없으면 캘린더)이 주간은 ≥ T, 밤은 > D 인 첫 종목. 분기 만기일 주간은 만기 종목과 차월물 둘 다(15:20 뒤 근월물이 차월물 — ws-gateway 구독 전환과 같게)
  - 창: 주간 `F` (T, 16:00:00) → 08:45, 야간 `CM` (D, 30:00:00) → 18:00 한 창. 다음 조회는 이 세션의 가장 이른 봉 − 1분(`continuation_hour`): 날짜는 창의 날짜 그대로(야간은 늘 시작일 D — 금요일 밤이면 금요일), 시각은 그 날짜 자정부터 잰 HHMMSS — 주간 13:53 → `135300`, 야간 22:18 → `221800`, 28:06(= D+1 04:06) → `280600`, 24:00 봉 다음 → `235900`(2026-09-29 실측 #17b)
  - 창을 끝내는 것: 세션 시작에 닿음(`complete`), 더 이른 이 세션 봉이 없음 — 새 봉이 없거나 앞 세션 봉(날짜 필드가 다른 봉)으로 넘어감(`exhausted`), 성공 조회 상한(`capped` — 주간 5, 야간 8). 가짜 KIS 기준 주간 411봉 5회, 밤 721봉 8회
  - 쓰기: 봉 날짜 필드가 세션 날짜(주간 T, 야간 D)인 것만 `MinuteBarRecord.from_kis`(위 야간 분봉 시각 변환 — `300000` → D+1 06:00, trade_date next_trading_day(D), session night)로 (code, market, ts) DO UPDATE — 다시 받아도 행이 늘지 않는다. 원문은 세션 태그로 `raw_messages`, 검증·변환 실패 행은 `quarantine`(나머지는 쓴다). 부르기 전 입력 (날짜, 시각)이 지금보다 뒤면 부르지 않는다(미래 날짜 금지)
  - 결과: 다 받으면 info `minute_bars_loaded`. 창이 상한에 닿았거나, 봉이 없거나, 더 이른 봉이 없어 끝난 창의 첫 봉이 세션 시작보다 10분 넘게 늦으면 warning `minute_bars_partial`. 실패(HTTP·KIS 오류·토큰 없음·저장 실패·P4 건너뜀·마스터 없음)면 그 시도를 멈추고 warning `minute_bars_failed` + 5분 뒤 멈춘 곳부터(받은 조회는 되풀이하지 않는다). 12회를 다 썼거나 다음 시도가 창 끝(17:50·08:00)을 넘으면 그 세션은 그만 + warning `minute_bars_missing`. 세션마다 구조화 로그 `minute_bars_session`(귀속 거래일·세션·상태·봉·호출), 조회마다 `minute_bars_page`
  - 재기동하면 창 안에서 그 세션을 처음부터 다시 받는다(멱등 — 행은 늘지 않고 호출만 주간 5·밤 8회 이하 더). 창을 통째로 놓친 세션(서비스가 멈춰 있던 날)은 되받지 않는다 — 필요하면 수동 백필(아래)
- **과거분 백필**(§0 — probe로 보관 한도 확인 뒤 결정): 한 번에 `F` 약 251거래일(2025-09-15~, 주간 약 410봉 → 102봉 4회로는 모자라 하루 5회) + `CM` 약 135밤(2026-03-04~, 휴장 전날 밤 제외, 밤 최대 8회) ≈ 2,300건 — P4로 1/s면 약 40분, 휴장일 `IDLE`에 돌린다
